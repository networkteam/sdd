The groom procedure returns the graph to a clean state without deciding anything new or implementing anything: find the constellations that point at non-clean state, present them with evidence, and turn the cleanups the user agrees to into ordinary captures. Nothing is edited in place — grooming records the closures, supersessions, and retirements the graph already implies.

## unit: sweep

Active WIP markers:

{{.viewLayout}}

Sweep for non-clean constellations — mechanical shapes first, judgment shapes after.{{if .focusHint}} The user pointed at a corner to groom: "{{.focusHint}}" — sweep there first, widen only if it comes up clean.{{end}} Use the free read tools — view lanes, search from several angles, chains — and inspect an entry in full before listing it. The recurring shapes:

- **Resolved but open** — an open gap, question, or commitment whose downstream entries, or the code and git history, show the work happened, with no closing entry recorded. Probe: the open-loops lane — view with `kind(plan,activity,directive,gap,question):active:rank(coldness(exp-30d)):n(10):expand(refs):as-list` — then show the coldest candidates' chains and check the repository history for the code side.
- **Stale markers** — a WIP marker whose entry shows no live work: the branch merged, the session long gone, or the closing done already captured. Probe: show each marked entry above with its downstream; a done signal or merged branch against an open marker is the candidate.
- **Superseded in practice** — an entry whose content a newer entry restates or replaces, without a supersedes edge making that official. Probe: search the entry's core claim in several phrasings; a newer hit restating it is the candidate pair — show both before listing.
- **Strained pairs** — directives that contradict each other, or a directive whose premise a later fact undercuts. Probe: pull one cluster at a time — view with `topic(<label>):active:as-list` — and read its directives side by side. These are dialogue candidates, not mechanical closures — name the tension, don't resolve it here.
- **Procedure forks** — a project procedure override competing with a shipped successor, waiting for a deliberate pick. Probe: host work — run `sdd lint`, which flags competing heads.

Report `candidates`: a numbered table — each candidate with its constellation, the evidence (entry IDs, marker IDs, commits), and a proposed cleanup drawn from graph material. Propose, don't perform. An empty table is a valid report: say the graph is clean rather than inventing work.

## unit: walk

Walk the table with the user in their language, most valuable first — not top to bottom. For each candidate the user takes up, the cleanup is an ordinary capture dispatched as a sub-move, seeded with the sweep's evidence: a done signal closing what completed, a directive retiring what no longer holds or answering a strained pair, a supersession where a newer entry replaces an older one. Stale WIP markers are host work — remove them with the CLI (`sdd wip done <marker-id>`) once the user agrees, and say so plainly. Relay the user's pick verbatim in `selectedCleanup`; return here after each capture — grooming iterates until the user concludes. A clean sweep concluded without captures is a valid outcome.
