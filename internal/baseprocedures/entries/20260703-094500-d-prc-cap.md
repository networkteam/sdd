The capture procedure is the shared spine for recording signals and decisions through dialogue: assemble a draft grounded in the graph, judge the writing guide's findings and fold them into the draft before it is shown, play the draft back for the user's explicit confirmation, write through the pre-flight gate — whose override is reachable only through the user — and verify the generated summary for fidelity. Supersede, close, and anchored captures are not separate moves; they are this procedure entered with start inputs (`supersedes`, `closes`, `anchor`, a pre-selected `kind`). The instruction units below are the authoritative capture guidance, served step by step against the running draft.

## unit: assemble

Draft one entry — one idea, dialogue first. Report the fields below (batching them all in one report is fine); the step re-serves naming exactly what is missing until the draft is complete and mechanically valid.

**Ground before you draft.**{{if .widenReport}} Grounding was inherited from the dispatching move — the searches and entries already inspected:

{{.widenReport}}

Extend it only if your draft reaches beyond what was already inspected — a new ref, a claim the inherited reads don't cover; append those searches to `widenReport`. If the draft stays within the inherited grounding, leave it as is.{{else}} Search the graph from several different angles — different phrasings, plus any known term or ID — and inspect the promising candidates in full before asserting what the graph holds. An existing entry may already cover this (ref it, or enter a supersede instead), and the right refs come from reading chains, not titles. Record the searches you ran and the entries you inspected in `widenReport`.{{end}} Inspection is checked mechanically, not on trust: every ID in `refs`, `supersedes`, and `closes` must have been served to this session in full — a show call, an injected chain's primary, or reads made by the move that dispatched this capture. **Lifecycle** (`closes`, `supersedes`). `closes` retires a target this work resolved; `supersedes` replaces an entry with this one. Either obliges the body, so settle it before writing: a retirement states why the target is retired, not merely that it is; a replacement carries the full current understanding on its own and says why each predecessor is replaced. A closure is often discovered while drafting — the retirement *is* the substance being recorded — so report it here when it surfaces, and report `null` to withdraw one you thought better of. Neither belongs in `refs`: an `addresses` ref reads as merely responding to the target, so the body claims a closure the entry does not carry and the target keeps deriving as open.

**Body** (`body`). The first sentence must work as a standalone summary — overview surfaces lead with it, so "Plan for X" tells a reader nothing; lead with what the entry is about. Fold the dialogue's substance into the description — trade-offs weighed, alternatives rejected, the why — so future readers get the reasoning, not just the conclusion. Every entry ID typed in the body must appear in `refs` (or be the supersede/close target), and every ref must be visible in the body's narrative.

**Kind** (`entryKind`). A signal records something noticed, a decision something committed to, and each kind answers one question. Unless the kind is already settled, pull the type-system fact `20260812-180000-s-prc-typ` before choosing — it carries each kind's question, the tests when two kinds compete, and where each kind's crafting guide lives.{{if .kind}} The target kind was pre-selected: **{{.kind}}**.{{end}}

**Layer** (`layer`): strategic — why, direction · conceptual — approach, shape · tactical — structure, trade-offs · operational — individual steps · process — how we work.

**Procedure drafts** (`canonical`, `class`, `procedureSpec`). A procedure additionally declares its identity and its workflow: `canonical` is the stable name everything binds to, `class` places how it enters (empty means move), and `procedureSpec` carries the workflow itself — `params`, `state`, and `steps` as the structured value this step's report schema describes, with the per-step `## unit:` guidance written into the body. Pull the spec reference fact `20260814-100000-s-prc-psr` before writing the workflow — it carries the field shapes, the gateable name vocabulary, and a worked example. The gate loads the declared workflow exactly as the engine will and names what fails.

**Refs** (`refs`, each `{id, kind, desc?}`, full entry IDs). The kind names why the pointer exists, chosen from what the body asserts — never a default: `grounded-in` (a basis reasoned from), `builds-on` (extending a closed line, or the next step after a finished chain), `refines` (sharpening an active target in place), `addresses` (responding to a gap/question/insight, or realizing a decision's commitment), `surfaces` / `surfaced-by` (this work produced the target / was produced by it), `depends-on` / `required-by` (prerequisite, from either side), `related` (the floor — a genuine sibling, only when nothing sharper fits). A terminal done signal is never "addressed" — reach for `builds-on`, `grounded-in`, or `surfaced-by`. The optional `desc` says why this ref exists in this entry's narrative.

A ref may point across a repo boundary, written as `<repo-id>:<entry-id>`. Resolve-or-block applies equally there: a cross-repo ref must resolve to a declared dependency of this graph, or capture blocks — so confirm the target resolves (via `show`) before drafting, and a bare foreign ID is stored in full prefixed form. The lifecycle fields `closes` and `supersedes` never cross the boundary — a decision retires only entries in its own graph.

**Topics** (`topics`). Labels are stable identifiers — reuse beats reinvention. Labels in use across active entries:

{{.viewLayout}}

Pick an existing label when one fits; a new label deliberately starts a cluster. Prefer hierarchical paths (`family/member`) for label families.

**Index** (`index`) optionally enrolls a `fact` in the retrieval index as `{title, topic}`. The title must stand alone as a retrieval cue, and the topic must also appear in `topics`. Omit it for every other kind.

**Confidence** (`confidence`) is honest: high — strong conviction · medium — reasonable but unvalidated · low — hypothesis.

**Intent** (`intent`) is required when the kind is directive and is never derivable: `pending` — demands follow-up (the default posture) · `guiding` — standing context that shapes later decisions without ever completing · `settled` — born terminal; the body must justify why no follow-up is needed.

**Attachments** (`attachments`). The description is the summary; the attachment is the record. When the dialogue produced design trade-offs, evaluation findings, exploration synthesis, or research, stage the full record (`stage_attachment`) and list the handles here — a compressed summary without the record loses the reasoning permanently. Skip only when the description alone carries the full substance.

- **Aliases** (`aliases`, optional) — the other names they appear under: a git author name, a chat handle, an external identity. List each once; they are read-side conveniences for mining and comprehension, never a second canonical.

## unit: guideFindings

The writing guide read the draft as a stranger to this dialogue — deliberately, since it runs the stands-alone test the drafting side cannot. Its findings are drafting input, not verdicts: there is no gate here and nothing to override. Weigh each one — the reasoning is the finding; fold in what improves the entry, dismiss what the dialogue's context refutes.

{{range .guideFindings}}- [{{.severity}}] {{.axis}} on '{{.quote}}' — {{.reasoning}} (repair: {{.repair}})
{{end}}
A `substantive` finding you act on — or dismiss — is named to the user in your own words when the draft is played back; a `minor` finding is yours to fold or ignore silently. The guide runs once per capture: it judged the draft, and it will not re-judge your repairs — a second pass reviews repairs instead of the draft and drifts toward escalation. Choose **revise** to fold findings in and continue to playback, or **proceed** to play the draft back as it stands. Only when you have reworked the draft so substantially that it is effectively a new one is **recheck** the right choice — it discards this run and judges the new draft fresh.

Target precedence is fixed: an explicit typed `captureBranch` wins; without one, the current session binding wins when the served session framing declares it; only an unbound capture uses the project's configured default branch. Do not invent a branch from cwd or substitute a CLI instruction for this served state.

This play-back recurs after every adjust. On the first presentation, show everything. After an adjust, a delta is enough — show the changed fields in full, name what is unchanged, and offer the complete entry on request. But a confirm must never bind to an unseen description: whenever the body changed since the user last saw it in full, show the full description verbatim again before asking — the user confirms what they see, not a memory of it.

Wait for the user's explicit answer — progress in the dialogue (answered questions, affirmations) is not confirmation; if unclear, ask. Relay the user's words verbatim with the answer. Confirm writes the entry; adjust carries revised fields back into the draft (any edit after a confirm reopens this play-back); abort abandons the capture.

Read each high finding as a prompt: what reasoning from the dialogue is missing from the entry text? Prefer **revise** — fold the missing context into the body rather than tweaking wording, adjust refs or topics, and the draft returns to play-back. Choose **override** only when a finding is genuinely wrong (for example, it argues against rationale the dialogue already settled). The override is the user's decision alone: present the findings to the user and relay their words verbatim with the choice.
