# Entry indexing adoption

`ApplicationOptions.PrepareSearch` is the single preparation extension point for application and MCP search. See the executable `SearchTarget` Go examples and the application/MCP composition tests. SDD selects authorized home and dependency snapshots before calling it. The consumer returns only an error. SDD then measures published coverage and retrieves against those snapshots.

An ordinary consumer wait-budget expiry returns nil. Parent cancellation, source errors, scheduling failures and preparation failures propagate. Always handle the error value from `SearchTarget.Entries(ctx)`: iteration may load attachments or publication state lazily. Stopping early does not reduce the coverage target. Semantic results carry SDD-owned `Coverage` and `Notice`; render the notice without replacing it with queue-state claims. Text-only searches have no embedding coverage.

With no callback, the existing explicit `none`, `local` and `all` synchronization policy supplies preparation. With a callback, that callback owns preparation policy; no implicit reconciliation follows it. Legacy index adapters remain usable without the callback but cannot provide coverage metadata. Custom preparation requires entry publication support for every selected project.

External consumer checklist:

- Supply the existing access resolver and project runtimes for every authorized dependency. Register preparation once on `ApplicationOptions`; MCP uses the same application.
- Implement `SnapshotReader` alongside the existing graph/read capabilities. Exact revisions must reproduce entry and attachment bytes. Retain each source until its jobs finish, including across process restarts. Release leases on all paths and propagate release errors.
- Use search `IncludesRevision` to request a snapshot containing a write. Use descriptor `SourceRevision` for the exact indexing input. These are distinct requests.
- Implement `SearchIndexEntryStore` over the index adapter. Publish the complete version and all vectors atomically, including versions with zero chunks. Completion reads and nearest retrieval must both exclude unpublished work. Validate before mutation and make repeated publication idempotent.
- Deduplicate durable work by the full `SearchEntryVersion`, including project, embedding fingerprint, metric, entry ID and hash. Do not shorten hashes. SDD includes the fixed derivation schema in its entry-state hash. A changed embedding configuration requires a distinct fingerprint.
- Stream discovery against a retained revision. Atomically persist each continuation cursor with durable enqueueing, or with the consumer's durable record that published work needs no enqueue. Resume only against the same revision and namespace. Handle iterator errors before advancing.
- Start write-triggered scheduling at the existing mutation finalizer and graph-write adapter. The consumer's write/recovery protocol must guarantee eventual durable scheduling after a committed mutation, including a crash between commit and scheduling. A best-effort finalizer callback alone is insufficient. No event subsystem is added.
- Supply exact-source runtimes to entry workers and call `IndexSearchEntry`. Retry according to consumer policy. Published state is authoritative after a lost acknowledgement; neither queue completion nor a successful wait proves coverage.
- Share one document batcher per embedding configuration and process. Route query requests separately with `EmbedderFunc`. Place `Bounded` and `Observed` inside the batcher for provider timeouts and once-per-provider-call usage. Use batch attribution to correlate participants; do not sum batch usage once per participant.
- Choose explicit item, byte, buffer, window and concurrency bounds. Supply `Measure` and `MaxUnits` for provider token limits where needed. Oversized entry requests span batches; an individual text beyond a configured bound fails explicitly. Cancel caller work independently, then close the batcher within the consumer's shutdown budget.
- Exercise the actual provider under indexing and concurrent queries before selecting settings. Cross-process concurrency remains a consumer limit. The local exercise favored one document call at a time for query latency; it is not a universal default.
- During adoption, deploy publication-aware retrieval before enabling asynchronous writers. The derivation schema changes entry hashes, so existing rows remain stored but current entries require fresh publication. Legacy manifest versions remain readable. Plan storage cleanup through existing retention/rebuild tools.

The local filesystem adapter retains immutable graph and attachment bytes in memory while leases are live. It supports synchronous preparation and concurrent writes during search. It does not persist historical source leases across restart. Memory scales with the bytes in live revisions; discovery itself hashes only each yielded entry and skips earlier cursor entries without rehashing them.

Persistent completion checks cache decoded manifests by file identity. Persistent retrieval caches a published-only collection per loaded store snapshot before selecting nearest results. Both caches consume memory proportional to stored published state. Publication still rewrites the manifest and reloads the local collection per entry; the adapter is not a substitute for a transactional database at large scale.
