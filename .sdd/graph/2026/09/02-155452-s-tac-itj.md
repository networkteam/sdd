Embedding batch size is a composition concern: commit `522ec3a3` on branch `worktree-llm-composition-surface` adds `Batched` to `pkg/llm/embed`, strips the splitting loops from the OpenAI and Ollama adapters so one `Embed` is one request, and recomposes the local embedder as `Batched(Observed(RateLimited(Bounded(adapter, timeout)), sink), size)`.

Every criterion of 20260902-154750-d-tac-o1s is met. `Batched(e, size)` serves one request as calls of at most `size` texts in order, concatenates the vectors, sums the usage, takes the identity from the first call, and returns the first failure as is; a request that fits passes through untouched. The adapters no longer hold a batch size or an HTTP client timeout; the per-request deadline is `embed.Bounded`, composed by the local factory together with the rate limiter, so both apply to each request rather than once per call. The factory still exports the resolved size, and the CLI hands the same value to `Batched` and to the indexer's progress buckets, so a bucket is at most one request. Local stats are back to one row per round-trip with `Items` equal to the request size. A live `sdd search` through the recomposed embedder recorded an `embed-query` row.

One detail beyond the directive's text: `Batched` panics on a non-positive size, since that is a composition error rather than a runtime condition. The indexer's bucket-size carrier struct stays, now holding the value the composition site owns. The commit follows `78346daa` on the same branch and awaits the merge into `main` with it.
