The MCP Go SDK the wrapper builds on, go-sdk v1.6.1, keeps Streamable HTTP sessions in an in-process map keyed by `Mcp-Session-Id`: a request with an unknown ID gets 404, there is no pluggable session store, and its `Stateless` option skips session validation but also drops the GET/SSE channel, so server-initiated requests are unavailable in that mode.

Verified on 2026-09-02 against the module source (`mcp/streamable.go`): the session map, the 404 path, the `Stateless` flag, and a `TODO(#148)` on session retention. The claim reached this graph through the first external consumer's handover and was re-checked here. The wrapper itself makes no server-initiated calls: no elicitation, sampling, notifications, or roots listing appear in `pkg/mcpapp`, so stateless mode loses nothing the wrapper uses.

What follows for hosting, as reasoning rather than measurement: a deployment of the wrapper behind more than one replica today needs session-affine routing, because the SDK's session state exists in one process only. What ties the wrapper to that state is not the SDK but the wrapper's own connection-keyed served-once memory. Once that memory is keyed to the session ledger, as the capability rebuild commits (20260828-165352-d-cpt-aen), no state the wrapper needs lives in the transport session, and stateless mode becomes viable.
