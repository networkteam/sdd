The host defines each operation boundary and assigns a single owner for its completion logging, so local and external consumers receive no duplicate completion events from nested layers. Repeated success messages make one operation look like several and obscure which event means the whole operation succeeded.

The owner reports success only after the entire operation returns successfully, including cleanup that can fail. Nested components may report distinct diagnostics and progress, but must not repeat that operation's completion event. Completion logging is optional. Ownership follows the invocation, not the component: publication invoked independently may own completion, while publication nested inside indexing leaves completion logging to the owner of indexing.

Progress may report that publication succeeded even if a later indexing step fails. Completion logs describe overall operation outcomes, not an exhaustive transaction audit. This preserves the separation of progress and operational logging established by 20260628-131545-d-cpt-dgk.

The host assigns this ownership when composing an invocation; the application's composition-root responsibility in 20260830-114446-d-cpt-xc3 does not make every reusable application command a completion-log owner.
