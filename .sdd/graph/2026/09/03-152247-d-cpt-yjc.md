The session handle is the session ID alone, the session and staged-blob stores move off the project runtime to the composition, and the application loads a session by ID, reads its home project from the session's own record, asks the composition whether the principal may continue it, and resolves every read and write by the project it targets. This answers the handle gap (20260903-113356-s-tac-ajf) and keeps the multi-project commitment of 20260902-000146-d-tac-1z6 intact; only the handle shape its closing run introduced changes.

The model. A project is a graph, its declared dependencies as its read horizon, and the ports that read and write it; the composition answers membership through `ResolveProject` on every call. A session is one subject's dialogue with a home project, recorded at creation and never changed. Sessions are scaffolding, not record (20260727-224047-d-cpt-u8o), so they belong to the composition, keyed by session ID and namespaced by subject, not to any project runtime. `ProjectRuntimeOptions` loses `Sessions`, `StagedBlobs`, and the clock; the application constructor takes them, the clock as a named `Clock` interface defaulting to the system clock. Both stores were already shaped this way: the session filter has a project field, the blob store enumerates by subject and session, and the local composition hands one store to every dependency runtime. This sharpens the port shape of 20260712-194427-d-tac-wjq.

The session door. Every session-addressed operation resolves the same way: load by ID, a keyed read with no policy; `AuthorizeSession` on the access resolver, asked with a request naming the actor, the session's owner as a principal, the session ID, and its home project; `ResolveProject` with read access on the home project; then the existing validation, ended check, and attachment stamp. The application is the single composition root (20260830-114446-d-cpt-xc3), so the door lives there. The MCP server deletes its handle composition and project fallback, `Session` in every result is the bare ID, and `Options.Project` goes, since a sole project is inferred and several are listed. Session-addressed application methods drop their project parameter; project-addressed ones keep it. Nothing is derived from the connection, so the capability rule of 20260828-165352-d-cpt-aen stands: possession of the ID authorizes continuing one dialogue within the authenticated principal's scope.

Authorization is three questions with three owners. Who is asking is `ResolvePrincipal`. Whether this principal may continue this session is the composition's, through the new `AuthorizeSession`, because the core does not own how a principal is authorized; SDD ships owner-only, a comparison of actor and owner, as the default the local composition and the example use, and sharing a session is a composition's rule. The request carries no verb, since continuing a dialogue is one act; a distinction between viewing and driving joins the request when a composition needs it. Whether this principal may read a project or write a mutation to a target stays with `ResolveProject` and the target's acquisition, asked per target on every call, so a shared session never admits someone into a project they are not a member of. A policy about a prepared mutation, such as per-kind write scopes or review before a strategic decision lands, has no seam yet; review before landing is a landing disposition rather than a denial and belongs with the logical-lineage gap (20260715-173711-s-cpt-e8x). This directive names that seam and does not build it. SDD's own invariants, not policy: a session's home project never changes, an ended session is never continued, a handle is required, every write names an explicit target. This continues the closed public-API plan (20260712-104530-d-tac-1mb), which kept application semantics with SDD and authorization with integrations.

Instances target projects. An instance's target is a project and a branch, resolved by the application and unknown to the engine, as branches are today. The project is an application-owned fact recorded in the session ledger as a typed event keyed by instance, the instance-level counterpart of the session's branch binding; procedure specs declare nothing for it. It becomes known from four sources, in order: an optional top-level `project` on the procedure start call, beside the procedure name, its params, and the parent, and parallel to the session start's own; the anchor, the entry a move such as engage or evaluate is started on, once it resolves to a foreign `<repo-id>:<entry-id>` form; the dispatching parent's project at dispatch; else the home project. The first two are recorded, the others derive. An instance's project may become known after its first step, which is wanted: a session opens at home, orients, and starts a move in another project.

Two grants gate a target, and they stay distinct. The closure is a graph fact: the target lies in the home project's declared dependency closure, transitively, computed from the configurations the composition can reach, because the result must be correct under the target project for every other principal. Membership is a principal fact: `ResolveProject` for the target with read access, asked again with write access at the write gate. Reading B inside A's view, which `ResolveDependency` grants, and being in B are different grants; a composition may allow the first and refuse the second, and the two resolver methods are not merged. A dependency a principal works in must therefore be resolvable as a full project. Locally that runtime is built from the dependency's cache, with its own declared dependencies and index namespace, while the horizon-member runtime that composes the home view stays as it is.

Being in B means the instance's operations resolve through B's runtime: its reads and their horizon, its writes and their authority, the participant name on entries it writes, the rules and actors it loads; target validation compares against the instance's project. The session, its ledger and staged blobs, the shell's framing, the branch binding, and any instance running at home stay with the home project. An entry captured in B may reference A only if B declares A; a session whose home is A grants nothing in B. Resolve-or-block runs on the instance's snapshot, B plus the parts of B's declared dependencies the composition can reach, and a reference B cannot resolve blocks the capture at the step that validates and applies the mutation, as an unauthorized dependency does today. Of 20260713-214523-d-cpt-n8z this settles where the per-instance target lives and how far it reaches; the ephemeral clone as local write authority for a connected repository stays with that directive, and until it exists a write to a dependency fails at acquisition naming the target. The session's branch binding is a fact about the home checkout and applies only there; elsewhere the instance's own branch field or that project's configured default applies, extending the branch precedence of 20260722-112853-d-tac-ln1 with the project dimension. Free reads take an optional project, defaulting to the home project and validated against the closure and membership; the never-ambient rule of 20260713-214050-d-cpt-65i applies to reads as it does to writes, and several moves may run at once, so the project is never derived from a running instance. Reads in B ground a capture in B through the existing read log, whose foreign IDs already carry their project. The instance's project is intent-bearing state and projects into step and resume serves.

Alternatives weighed. A locator port consulted only when no project is pinned: the smallest change, rejected as a second source for a fact the session record already holds. Probing every accessible project's store: no contract change, rejected because cost grows with the number of projects, which may be dozens. A bare authorization function in the options: rejected because it splits the authorization boundary the access resolver is declared to be. Passing only the session ID to `AuthorizeSession`: rejected because the application has just loaded the session and the shipped default would need the store wired into the resolver. A declared project state field in every procedure spec, or a host-owned slot on the engine instance: rejected in favor of the ledger event, which leaves specs and engine unaware. A composite handle only in multi-project compositions: rejected as two handle shapes with the redundancy kept.

Consequences. Collection of ended sessions and their staged blobs is an operator act on the composition's stores, without identity or project, and its enumeration is bounded and resumable: the session and staged-blob filters gain an ended-before bound, a session-ID cursor, and a limit, a pass processes one page and returns the cursor to continue from, and the store decides how it pages, so the sweep converges over repeated calls instead of loading every session. Every surface that names the handle or the new arguments changes in one delivery: tool descriptions, server instructions, tool-contract snapshot, CLI session listing, the composition example, the conformance suites. The design record with types, the door, target precedence, collection, and the weighed alternatives is attached: [design](./03-152247-d-cpt-yjc/session-model-design.md).
