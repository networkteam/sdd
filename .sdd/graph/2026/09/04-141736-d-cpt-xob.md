SDD's own terms ship as a base fact declaring `class: vocabulary`: one entry ID with one rendering per language, the graph language selecting which rendering is visible, primed in full at every session open, and replaceable by a project through ordinary supersession.

The question surfaced while scoping the v0.18.0 skill retirement (20260821-123832-d-tac-ip1), which removes the bundled legacy skill renders. The German vocabulary lives today as `references/vocabulary-de.md` inside the legacy `/sdd` skill bundle, and `Application.Vocabulary` reads it from that bundle by path — so removing the bundle degrades every non-English graph to a fallback string with no error. But the deeper point is that it was never skill knowledge: the engine uses it at runtime, so it needs a home of its own regardless of retirement. That extends what the multilingual delivery shipped (20260423-134628-s-cpt-duv) rather than undoing it — per-graph language, drift enforcement and German as first locale all stand; only the vocabulary's home moves.

**It is a dictionary, not a translation table.** English needs it as much as German does: `supersedes` and `kind` are only obvious to someone who already knows SDD, so every language ships the core meaning, and non-English renderings ship the translation plus that meaning stated in the target language. Each term gets one line — the core meaning, the words it displaces, and a pointer to the fact carrying its semantics. Naming the displaced words is what does the work: `entry: an immutable record in the graph` reads fine and does not stop an agent writing "document", while `entry (not: document, note, record)` does. In other languages it matters more, because German offers Eintrag, Datensatz and Notiz with nothing to choose between them until the vocabulary chooses.

The rule runs in both directions. A defined term displaces its alternatives, and it is also reserved: it is not used in its ordinary everyday sense where the collision would pass unnoticed. `kind` is the standing example — read in a sentence, it repeatedly leaves the reader unable to tell whether an entry kind is meant or merely a sort of thing. Where the loose sense is genuinely wanted, the sense is named rather than left to the reader to guess.

**Vocabulary is primed because it cannot be pulled.** Every other fact works on demand: the agent knows it is drafting a plan and reaches for the plan fact. Vocabulary has no such trigger — by the time anything would prompt a pull, the agent has already written a sentence in the wrong terms, and a later pull does not retract it. That is a stronger argument for always-on than the type overview has, whose reach call is still open (20260812-134549-d-tac-9be), and it operationalizes the priming mechanism (20260810-134906-d-cpt-a2a) with vocabulary as its second consumer. The consequence is a hard constraint rather than a licence: every project pays this at every open, English included, so one line per term is the budget and all depth sits behind the pointer.

Declaring a class on the fact does not reopen what that mechanism settled. It rejected a fact-side *priming selector* and kept one rule — the fact declares what it is, the shell declares what it needs. A class declares what the fact is; priming stays shell-side and topic-based, unchanged.

**One ID, many renderings.** The alternative of one entry per language was rejected because retrieval then returns the same meaning several times over. Renderings under a single ID avoid that and keep every existing reference valid. The accepted risk is that a ref made while the graph was English resolves to the German rendering after a language change; that is acceptable precisely because renderings are meaning-parity — a translation preserves the claim, so the pointer still points at what it meant.

That parity requirement is also why this stays scoped to term tables. A table's parity is checkable: same terms, same keys. Prose drifts — the German rendering picks up a clarification the English one lacks, and one ID quietly means two things. So multi-language *prose* facts, including the authoring facts, stay closed; whether framework knowledge at large can exist in more than one language is deliberately not decided here.

**A class, not a kind.** A new kind would put a term list through the type contract for something already a fact in the strict sense: a claim about what these words mean. Instead `fact` declares a class, reusing the field procedure already carries for the same question — which sub-form of this kind is this — with an empty class meaning ordinary knowledge, as an empty class on a procedure means move. A per-kind field name was considered and rejected: `intent` answers a posture question specific to directives and does not transfer, while a fresh name would mint a third word for an idea the type system has already named once.

The candidates weighed were `shape`, `form` and `class`, tested against the reserved-term rule above by counting loose prose use across this graph: `shape` 907 uses in 380 entries, `form` 356, `class` 344 — part of the last already the procedure field rather than prose. `shape` lost on exactly the failure that rule exists to prevent, the one `kind` demonstrates at 6608 uses. `vocabulary` was chosen over `dictionary` as the class name because the graph already says vocabulary for this everywhere — the ref-kind vocabulary, the view layout vocabulary, the topic label `graph/domain-vocabulary` — and those loose uses name the very things that would carry the class. "Dictionary" stays the word for the register these entries are written in, not for what they are.

Declaring a class also makes the same machinery serve framework and project vocabulary, which is the point of shipping it this way.

**Overriding is ordinary supersession.** A project supersedes the vocabulary fact with its own; resolution finds the head, and the head's renderings are what the graph has. There is no partial fallback to the base entry for a language the override omits — that condition fails loudly instead. The payoff runs past translation: a project that supersedes the fact primes its own house terms into every session, which answers the declaration half of the domain-vocabulary gap (20260818-143339-s-cpt-8h2) for terms, though not that gap's open question about typed relations over a domain.

This is one entry rather than two. The multi-rendering capability looks general enough to stand alone, but as decided it is scoped to renderings whose parity is provable, which today means vocabulary and nothing else — so it has exactly one user by construction, and a second user arrives with its own decision. This stays pending, and an implementation plan has to settle four things: where the class is declared and validated, how renderings are stored and selected, what the shipped term set covers, and how the migration off the bundled reference file lands before the legacy renders are removed.
