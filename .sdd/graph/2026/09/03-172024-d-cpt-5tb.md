An instance's project comes from the start call, the dispatching parent, or the home project; the anchor is not a source. Of the four sources 20260903-152247-d-cpt-yjc names, the second is dropped: an anchor never carries the `<repo-id>:<entry-id>` form, so it never selects the project. The engine types the anchor field as a full local entry ID, and 20260710-135610-d-cpt-z6h keeps it so because the type is shared with `closes` and `supersedes`, whose edges never cross the repo boundary; a foreign anchor fails type validation before the application sees it.

The agent resolves a foreign entry through the show read before anchoring, the read 20260710-135610-d-cpt-z6h already relies on: it runs without a move and resolves a bare ID across the declared dependencies, returning the full prefixed form, so the project is in hand when the move starts. It passes the project on the start call and anchors on the bare entry ID, which is local inside the target project's runtime. There the anchor reads through that project's own graph, so `entryChains`, `requireBody`, and the write gate need no prefix normalization.

The alternative was to accept the cross-repo form for every entry-id field, refuse foreign IDs on the lifecycle fields at write validation instead, and strip the prefix inside the target project. That would have superseded 20260710-135610-d-cpt-z6h and touched the engine's type layer, the model's validation, and the embedded base-procedure specs, for a case the resolve-first step already covers. Settled in the implementation dialogue of 2026-09-03, when the engine refused the foreign anchor.
