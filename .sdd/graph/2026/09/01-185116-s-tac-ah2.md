The exported `pkg/application` surface names `internal/` types in exported signatures, making parts of the public API unusable from an external Go module: `Application.Lint` takes `query.LintQuery` and returns `*query.LintResult`, so it cannot be called at all; `ViewRequest.Budget` (`query.ViewBudget`), `ShowRequest.Budget` (`model.ShowTreeBudget`), and `EntryDraft.FocusWhen`/`Involvement` (`internal/model` types) cannot be set; `WorkflowServe.InstructionLanes` and `Sizes` (`internal/engine` types) are readable but unnameable; `ValidationError.Warnings` carries `model.Warning`. Observed by code-grounding of the public surface at v0.17.0-alpha.4 by an external consumer building against it.

Expected: `pkg/` is the repo's only public Go surface (20260831-092538-d-tac-zhc), and the public runtime was validated as genuinely consumable by an independent external module (20260713-160800-s-tac-luv). An exported signature an outside module cannot name breaks that consumability in a way the compiler reveals only at the consumer's site, and nothing mechanical guards the boundary: the nested example module compiles without touching the affected members, so such leaks ship silently.

The deviation strains against the composition-root directive (20260830-114446-d-cpt-xc3), which commits the application surface to speaking the CQRS vocabulary by taking structs from `internal/command` and `internal/query` — followed literally, that rule is what produced the uncallable `Lint`. Candidate remedies from the dialogue, marked as such: move the needed leaf types into `pkg` so one definition serves both sides, as `pkg/llm` did for the LLM contract (20260830-234501-d-cpt-q6n, whose dialogue already rejected public aliases to internal types); and a mechanical guard — a test that loads `pkg/...` and fails on any exported signature or field naming an `internal/` type.
