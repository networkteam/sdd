Deleting index versions becomes a deliberate CLI command, `sdd index gc`, and `sdd index` never deletes.

The automatic collector in `sdd index` evicts the versions of any writer whose entry-hash rule differs from the collecting binary's (20260910-182907-s-tac-ecp), cancelling the multi-writer guarantee the shared store exists for (20260708-184318-d-cpt-6cq). The cost is asymmetric: a wrong eviction costs a full re-embed of the losing writer's namespace, a missed collection costs disk on a derived-data cache. So collection leaves the write path.

`sdd index gc` reports, and deletes only on request. Without a drop flag it lists, per store, the version groups with version count, entry count, age range and size: one group per derivation rule, the current rule split into current and branch leftovers. `--drop <group>` removes one group; `--drop stale` removes every version not current for the checkout. `--repo` and `--all-repos` select stores as on `sdd index`, which is why the umbrella is named `stale` and not `all`. `--force` on `sdd index` drops only versions under its own rule. The retention window goes; it existed to soften automatic collection.

Each stored version records its derivation rule beside the fingerprint. Versions written before this field are classified by chunk-ID shape: an eight-character version segment is the pre-derivation rule, a full hash the first derivation rule. Derivation does not partition the store. A fingerprint change makes vectors incomparable and keeps its own directory; a derivation change recuts chunks in the same vector space, so its versions coexist in one index. `sdd index` prints store size so manual cleanup has a prompt.

Liveness is the user's knowledge, not the store's. The report says which rule no current binary writes, never whether an old process still reads it; process scanning would lie.

Readers of every generation serve only versions under their own rule, so overlays never mix in results. A v0.17.0 server keeps working on its overlay until restarted. Its CLI still collects, so the remaining hazard is a v0.17.0 `sdd index` run against a store the new version has written to for longer than the old window; upgrading replaces the CLI and servers never collect, so that path closes in practice. The manifest gains one additive field, no file-level version bump and no store migration; older binaries drop the field on save, which the chunk-ID classification absorbs. This refines 20260716-235744-d-cpt-vri: the store is safe by construction under mixed hash rules, so its prompt-release rule narrows to changes an older CLI would still collect against. The manual command also answers the serve-only accumulation boundary recorded in 20260717-000200-s-tac-eyc. The [compatibility record](./10-183941-d-tac-c9c/index-gc-compat.md) carries the per-generation behaviour, the pairwise cases and the migration steps.

Rejected: automatic collection with a longer window, which delays and does not prevent; partitioning the store by derivation, which doubles disk and re-embeds for a change within one vector space; collection inside the running server, which is the long-lived old writer this protects.

Fulfilled when `sdd index` no longer deletes, `sdd index gc` ships as described, and versions record their derivation rule. On this machine the MCP server restarts on a main build now; the store already holds the new-rule overlay.
