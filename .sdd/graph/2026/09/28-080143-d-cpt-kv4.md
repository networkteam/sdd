The SDD application's exported surface returns structured results (typed entries, references, derived status, scores and coverage), and rendering them as text for an agent is a presentation concern of the shells over it, the MCP server's for agents and the CLI's for terminals, not of the application. Today `Application.View`, `Show` and `Search` return their payload as rendered text (`ViewResult.Sections`, `ShowResult.Entries`, `SearchResult.Results`) with only ID lists beside it, so a caller that is not an agent must either parse text meant for a model or rebuild the traversal itself, and either way drifts from the application's semantics.

This sharpens the composition-root directive (20260830-114446-d-cpt-xc3), whose exported surface already speaks command and query structs, by stating what comes back: data a shell presents, not presentation a shell passes through. It applies the split the output policy draws for the CLI (20260628-131525-d-cpt-owo), where machines get structured output and each audience gets its own rendering, one layer down, at the boundary every surface shares. It came up while designing a web surface that reads graph content through an external composition of the application: such a surface needs entries and references as data to lay them out.

Scope: the rule holds for everything the application exports. Engine serves are not held to it yet, but the expected direction is the same: the application and the engine work with structured data, and a serve is a view concern of the MCP adapter, which then becomes somewhat stateful, since it tracks what a session was already served, and does the capping and sizing. Sizing cannot move into that layer entirely, though: the whole serve has to stay under a limit, so procedures are already authored with their serve sizes in mind, and size budgets stay declared with procedures and queries rather than discovered at rendering.
