The implementation procedure's landing report fails once the work branch is gone: after merging into `main` and removing the worktree and branch, reporting `landed` returned `mutation target branch "worktree-llm-composition-surface" must have exactly one registered checkout (found 0)`. Seen twice in one session, on the runs closed by 20260902-125432-s-tac-sv0 and 20260902-155452-s-tac-itj; the report went through only after the branch was re-created at `main` in a worktree, then removed again.

Expected, per 20260713-214251-d-prc-pop: after host landing succeeds, the agent's report authorizes marker removal through the base authority. That report needs the base branch only. The served landing step does not say the work branch checkout must still exist, and "merge and remove the worktree" is the natural order for a user to ask for.

The deviation: the landing junction resolves the current graph on the work branch before it accepts `landed`, so the report depends on a checkout that landing makes disposable.

Candidate remedies, unsettled: resolve the landing step against the base branch, or have the step's instructions name the order, report landed before removing the worktree.
