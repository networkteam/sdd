The MCP server's session handle carries the project ID as a `<project>:<session-id>` prefix, encoding a fact the session's own record already holds and every tool result already returns as its own `Project` field, and it changed every local handle from a bare `s_…` to a project-prefixed one without a decision stating so.

Observed by the first external consumer, a multi-project composition, evaluating its integration against `main` after the capability rebuild: `composeHandle` in `pkg/mcpapp/handle.go` prefixes the project whenever one is known, and the local `sdd serve` always pins one, so a local handle now starts with the repository ID and the consumer's with its project identifier. The agent never parses the handle; it receives it from `start_session` and echoes it back to every tool. The application never sees a handle: every method takes project and session ID separately. Session IDs carry 128 random bits, the consumer's store keys sessions by ID alone and records the project on the session, and the local store lives under a machine-global root keyed by repository. The observation and its rationale are attached: [observation](./03-113356-s-tac-ajf/external-consumer-handle-observation.md).

Expected: the multi-project directive (20260902-000146-d-tac-1z6) says every tool takes project and branch from the session's immutable metadata and names no handle shape. The composed handle entered in the closing done (20260902-120853-s-tac-q5c) as a deviation settled during the run, chosen over probing every project's store, and its effect on local handles was not stated there. The capability rebuild (20260828-165352-d-cpt-aen) makes the handle the dialogue's identity and the thing agents carry and people copy between clients, so its shape is user-facing.

The deviation: the handle duplicates the project on the way out and makes every caller carry it on the way in, while the session's record already answers which project it belongs to. Candidates surfaced in dialogue, unsettled here: a locator port the application consults before resolving the project; probing each accessible project's session store; or moving the session store off the project runtime so the application loads a session by ID and reads its project from the metadata.
