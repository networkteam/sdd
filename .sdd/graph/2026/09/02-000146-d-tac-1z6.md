The MCP wrapper serves every project its principal can access through one endpoint, with the project chosen inside the dialogue instead of pinned per server instance.

The application is already multi-project: every `Application` method takes a project ID, and the access resolver lists a principal's projects with per-project actions. Only the wrapper pins one. `mcpapp.Options.Project` is required, twelve tool handlers pass that fixed project, and no tool lists projects or accepts one. A composition serving several projects therefore needs one server instance per project behind a mux, and a person working on four projects registers four connectors in their assistant, each exposing the same fifteen tool names. The first external consumer, a hosted composition built against v0.17.0-beta.1, surfaced this; it is the one upstream change that consumer's next delivery stage waits on. The public-API plan already stated that projects are selected explicitly in multi-project compositions and inferred only when exactly one is accessible, and that a session binds immutably to one project (20260712-104530-d-tac-1mb); the application delivered that rule and the wrapper never did.

The shape. `start_session` is the only tool that takes a project, as an optional argument. When the composition has more than one project for the principal and the argument is missing, the response serves the principal's projects instead of starting a session; a single-project composition, which is what local `sdd serve` is, infers its sole project. Every other tool carries a session handle and takes project and branch from the session's immutable metadata, the free reads (`search`, `view`, `show`, `read_attachment`, `info`, `vocabulary`) included. `Options.Project` becomes optional and, when set, keeps today's behavior. The tool-contract snapshot changes deliberately, for local users too: a read that works today without a session requires one. The application is untouched: the change is confined to the shell, which is where a shell-over-application layering puts it (20260830-114446-d-cpt-xc3).

The consumer proposed reads that take an explicit project argument, or derive the project from the session bound to the connection. Both give way to the one handle-carried path. The connection binding is what the capability rebuild deletes: nothing is derived from which connection a call arrived on (20260828-165352-d-cpt-aen), and the rebuild needs the handle on reads anyway, since today `show` logs each read against the connection's session for the evidence gate and takes the branch binding from that connection. A second, project-keyed path would double the resolution logic for the one caller who wants a lookup without a dialogue. That caller starts a session first; the cost is a session file, discardable when no move ran, and ad-hoc reads otherwise belong to the CLI and the hosted UI, the surfaces that know their principal. `list_sessions` is out of scope: the capability rebuild removes it.

The work opens with an inventory and closes only when every listed surface is adjusted. Before code changes, every surface that names a session tool, its arguments, or the wrapper's options is listed: the served step text of the session shell and the base procedures, the `sdd-engine` skill template with its installed renders, the MCP server instructions and tool descriptions, the open-threads and resume serves, the tool-contract snapshot, the external composition example, and the documentation site. Each listed surface changes in the same delivery, and the closing done names the inventory and what changed on each item. The demand answers a repeated observation: surfaces not known or not cared for at implementation time were left broken and rediscovered later in unrelated sessions.
