The configured graph language reaches each LLM surface by a different route, and one surface not at all: pre-flight checks entry bodies against it, the summarizer now writes summaries in it, and the writing guide judges drafts with no knowledge of it.

Observed by code reading during the provider evaluation (20260901-093840-s-tac-ahc): pre-flight receives the language from the finder's config; the summarizer receives it as a parameter threaded through the handlers and the application runtime since commit 3a004f70; the writing guide receives nothing — neither its finder nor its operation mentions language — and the engine's session opener is a fourth consumer served from runtime options. Expected: the configured language is a committed property of the graph governing all authored prose, so every LLM surface that writes or judges such prose receives it — an expectation the multilingual mechanism established for entry bodies and this gap extends to the surfaces built since.

This supersedes the one-sided-guard gap (20260605-140428-s-tac-lau): its summarizer half is resolved — the summary prompt now pins the output to the configured language, with unset meaning English, exactly the fix that gap proposed — and what remains is sharper than it could state. The writing guide, which did not exist then, judges drafts on a non-English graph against English-phrased criteria with no drift awareness. And the deviation is now a pattern, not one surface: each consumer acquires the language by its own plumbing (finder config, handler option, runtime option), so every new LLM surface re-invents the threading and can silently ship without it, which is how the writing guide did.

Reasoning from the dialogue, marked as such: candidate remedies are a single language-bearing seam — resolved once at composition and carried to all LLM operations — rather than per-surface threading, and a writing-guide language awareness mirroring pre-flight's drift check; neither is decided.
