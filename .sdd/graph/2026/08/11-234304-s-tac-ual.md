Capture-time LLM completions driven through the engine record no usage or cache metrics at all. Eight captures ran through the engine in one session, each invoking the writing guide, the pre-flight check and summarization; across all of them the recorded op counts moved on the embedding side only, while the pre-flight and summarize counts stayed exactly where they had been. No `writing-guide` op appears in the stats file at all, and none has since the guide shipped earlier the same day. The file was written during the session, so the process holds a working sink that embeddings reach and completions do not. Searching the source for the sink's uses finds it installed once, in the CLI entry point, with a single reader in the query layer.

What that costs, concretely. The writing guide's system block is small — well under the pre-flight preamble that cached well, and in the size class of the prompts that recorded no cache activity at all — while the comment above its renderer asserts byte-stability for prompt-cache reuse, naming that preamble as the same invariant. The rule the earlier cache measurements set was to scope caching per operation rather than assume it (20260604-195225-s-tac-jxr), and this is the path where that rule cannot be followed. So the constraint is honoured on faith precisely where its value is uncheckable.

Two things are not observed and are recorded as candidates only. Whether the guide's prefix truly falls under the floor is inferred from its size, not measured. And why completions never reach the sink is unestablished — one possibility is that the sink is attached somewhere the capture path's own calls never see it. Both resolve through the same act: record completions on this path, then read the numbers.

Nothing is breaking meanwhile. The guide runs on every capture and its prompt stability is covered by its own tests (20260811-154427-s-tac-yzg); what is missing is the ability to say what any of it costs.
