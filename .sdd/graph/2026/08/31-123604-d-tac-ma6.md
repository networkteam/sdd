Run a provider and model evaluation across the existing end-to-end LLM evals to select, per chat purpose, the fastest and cheapest configuration that is still capable enough: the eval suites measure capability, per-call usage measures timing and token consumption, and the choice rests on those recorded numbers.

The work: for each candidate configuration, run the live eval suites (the pre-flight calibration eval and the writing-guide evals, model-selectable via `SDD_EVAL_MODEL` and the llm config) and record each run's capability results alongside its timing and token counts; cost derives from the token counts and the provider's pricing. The eval harness records no usage today, its tests build a bare runner with no stats sink attached, so the work starts by wiring per-call measurement into the harness, attributed per provider, model, and variant as the stats path already does. Building the candidate selection is part of the work: a set of provider, model, and variant configurations worth comparing, with the incumbent configuration as the baseline and Ollama Cloud's `glm-5.3-flash:cloud`, under evaluation as of this dispatch, among the candidates.

One reading constraint is known going in: recorded usage undercounts semantic failures (20260831-093815-s-tac-k7d), so reliability is read from the eval harness results, not from the recorded rows alone.

Finished when the candidate selection stands and each candidate has completed the eval suites with capability, timing, and token results recorded per identity and the comparison lands in the closing done; anything the evaluation surfaces beyond the comparison is captured as its own entry.
