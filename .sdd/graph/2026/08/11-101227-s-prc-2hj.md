SDD v0.17.0-alpha.1 is published as the project's first prerelease, and cutting it exposed three places where the release path assumed every tag was stable, plus two habits in the notes themselves — all now closed. The tag sits at `8d319cec` and carries the engine session model, the session-subsystem rebuild, durable branch binding, base facts, the terminal output coordinator, engine bootstrap, supersede-aware ranking, and the config version-tolerance work (20260810-222521-s-tac-hdr), with hand-written notes, four platform archives, checksums, build provenance and `install.sh` attached.

The first gap was caught before shipping. `homebrew_casks` declared no `skip_upload`, whose GoReleaser default is `false`, so the cask would have been published from the alpha and the next `brew upgrade` would have moved every user onto an untested build. The tap was pinned at 0.16.2 and had no notion of a prerelease. Commit `d4b8028e` sets `skip_upload: "auto"`, which skips the tap for any tag carrying a prerelease segment (its comment trimmed in `8d319cec`, the commit the tag then landed on); the tap was confirmed unmoved after the run, still on 0.16.2 with its last commit unchanged.

The second was caught only by reading back what had already shipped. `gh release create --prerelease` set the flag, and GoReleaser's release step then wrote `false` over it — not ignoring the flag but actively applying its own default for `release.prerelease`. Nothing was materially at risk, because GitHub's `releases/latest` had already excluded the alpha and `install.sh` resolves through it, so stable consumers were never served the build. But the release contradicted its own prerelease note and rested on GitHub's latest-computation rather than on the flag that was supposed to guarantee it. `gh release edit --prerelease` corrected it in place — never a re-tag — and commit `8c75cc6f` sets `release.prerelease: auto` so the flag is derived from the tag and both settings key off the same signal. Worth noting for the next diagnosis: `skip_upload: "auto"` was unaffected throughout, because it inspects the tag independently of `release.prerelease`, which is exactly why the tap was correctly skipped during the window when the release flag was wrong.

The third is the mirror of the other two. Everything that makes a prerelease safe also makes it unreachable by the path users actually type, so its notes have to carry the deliberate command — and the first draft only gestured at one, assuming a reader who already had the installer. The published body now gives the exact command, confirmed by a dry run that resolved the tag and verified the checksum.

The notes then needed two further corrections, both about language rather than mechanism: they called the release a "soak build", a term used nowhere in this project's graph, docs or code, and they explained how the installer resolves a tag when a reader needed only the command. Christopher cut both after publication. Release notes are read outside this repo, which is what makes invented vocabulary and volunteered explanation costlier there than anywhere else — the reader has no context to repair either one against.

The release skill (20260508-102334-s-prc-lep) absorbs all of it across commits `d6cf9002` and `8b7a2e57`: `--prerelease` in the ship step; a verification block that reads back what a prerelease exists to protect — the flag, what `releases/latest` resolves to, and the tap version — instead of checking only that the body and assets survived; the prerelease opener with its install command; and a rule against invented vocabulary and over-explaining. The verification is the load-bearing part. The config change makes the flag failure unreachable, but no config change would have found it; reading the shipped state back did, and the previous cut (20260714-095002-s-tac-4oj) never surfaced any of this because every release before this one was stable. Because the skill is project-scoped rather than bundled, the edit is itself the source of truth. It remains a Claude Code skill pending its port to a graph-local procedure (20260707-143547-s-prc-tso), which now inherits the larger content.
