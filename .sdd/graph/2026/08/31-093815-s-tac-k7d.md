A chat call whose output cannot be used still records as a success: outcome classification in the recording path sees transport errors only, so a parse failure or an empty payload lands in the stats file as a success row with tokens and duration, indistinguishable from a call that worked.

Expected, per the written contract on `CallStat.Error` in `internal/llm/stats.go`: failed calls are recorded too, and unparseable responses are named there explicitly. Failure counts are one of the things the stats measure; a failure that never becomes a row hides exactly that.

Observed, by code reading during the engine-stats investigation (20260811-234304-s-tac-ual): recording runs inside `llm.Run` immediately after the transport returns without error, while parsing happens above it in the operations (for example `internal/llm/writingguide.go` parses the guide's JSON only after `llm.Run` has already recorded the call as a success). The gollm runner returns the provider's response content with no emptiness check, so an empty payload arrives as text "" with a nil error and records the same way. Only transport-level errors produce failure rows.

The deviation: the mechanism cannot see the failure class its own contract names countable. Everything semantic — unparseable JSON, an empty response, output the operation rejects — is counted as success.

Reasoning from the dialogue, marked as such: this matters most while provider and model evaluations read reliability from these rows, since a model that returns unusable output measures as reliable and cheap. And the boundary architecture (20260830-234501-d-cpt-q6n) does not resolve it by itself: the observing decorator sits below the operations where parsing happens, so a repair must carry the semantic outcome from the operation back into the record; how is undecided.
