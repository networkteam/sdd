The documentation site gives a newcomer enough to get started using sdd via the engine and to look up the type system, live when v0.18.0 ships; it deliberately does not wait on the full example world. It answers the practical half of the no-learning-path gap (20260715-172002-s-cpt-i5a): it is hard to build a working understanding of SDD from what exists today, a README, a partial site, and outdated artifacts under ./docs.

Why this is its own plan: the practical content has waited behind the example-world production of the seven-section docs plan (20260715-181235-d-tac-c7b), and producing those transcripts is slow. This plan carves out what v0.18.0 needs; the full plan stays untouched, and whether the material built here plus the live Vision section (20260818-190009-s-tac-8db) end up superseding it is a call for a later docs session. The timing comes from the transition decision (20260820-162456-d-tac-o2v): v0.18.0 removes the old skills, so the release that says the engine is SDD must have somewhere to send a newcomer.

Two content pieces. A getting-started path with concrete steps: install the sdd binary; run `sdd init`, which writes the project setup, the MCP server config, and the minimal skill that instructs the agent to use the MCP server; on a fresh project, run bootstrap, the dialogue that founds the graph and captures its first entries; then start a first working dialogue and use the system, for example to capture a new gap. The path stays deliberately minimal: it says what the user does, how the system is meant to be used, and how information and knowledge flow along the way, without reaching into example-world territory. And a card per entry kind, written for humans, explaining what the kind is for, when to pick it over its neighbors, and how it retires. The semantics already live in the shipped type-system facts (20260812-180000-s-prc-typ and the per-kind authoring facts behind it), but those are worded for an agent drafting an entry, so the cards are written, not generated. A documented recipe describes how a card is derived from its base fact, keeping the overlap deliberate and drift checkable when either side changes.

The implementation session develops the structure and wording of both pieces together with the user, in draft and feedback rounds, before anything publishes.

Out of scope: the example world, the remaining sections of the full docs plan, and any change to that plan's status.

## Acceptance criteria

- [ ] The published site carries a getting-started path a newcomer can follow end to end: install the binary, run `sdd init` (project setup, MCP server config, minimal skill), bootstrap a fresh project, then start a first working dialogue and capture a first observation.
- [ ] The path explains how information and knowledge flow through the system as the steps proceed, and carries no example-world material.
- [ ] Every entry kind has a card on the site, written for humans, covering what the kind is for, when to choose it over its neighbors, and how it retires.
- [ ] A documented recipe describes how a kind card is derived from the kind's base fact, so card and fact can be checked against each other when either changes.
- [ ] The structure and wording of the path and the cards went through draft and feedback rounds with Christopher, and he reviewed them on the rendered site before publishing.
- [ ] The getting-started path and the kind cards are live on the published site when v0.18.0 ships.
- [ ] The v0.18.0 release notes link the getting-started path.
