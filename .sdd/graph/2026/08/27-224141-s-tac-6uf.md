Step serves re-deliver, in full, entries this connection already read in full, even though the engine's own session ledger records those reads — the served-once memory dedups only what was previously served and never consults the read ledger. Observed at this session's implementation run: the contract step injected the anchor's full body and chains minutes after the same entries had been read in full through show at the user's instruction — the run's largest single duplication remaining after the static-serve dedup (20260826-172134-s-tac-3yc) — with those very reads sitting in the session ledger — the same record the engine consults to verify a draft's references were read in full before it writes. Verified in the source: the served-once memory records rendered lane bytes per connection and no serve path consults the read ledger.

Expected: an entry the session's own ledger records as read in full does not come back whole in a later serve. The capture-efficiency plan carries the principle — the engine never serves what this connection already holds (20260826-120330-d-tac-8f8) — and the read ledger is the engine's durable record of exactly that holding: it survives the process where the in-memory served-once memory does not; both shipped in one directive (20260705-010751-d-tac-dbk), and nothing since has joined them. Stated over the ledger, the expectation also reaches the reconnect seam already recorded from the other direction (20260826-173028-s-tac-1qr): a restarted server forgets what it served, but the ledger still knows what the session read.

Recorded as reasoning, not a commitment — two candidates that compose: per-inject opt-in exists today — the chain injection supports an onceFull argument that serves nothing when every entry was already served in full this session, and the implementation procedure's contract inject simply does not set it (20260706-170000-d-prc-imp); and the general repair, teaching the serve-side dedup to consult the read ledger, which would cover every injection without per-spec opt-ins. The general repair rests on an assumption settled in this dialogue: exactly one agent session drives an SDD session at a time — concurrent attachment must not happen and will not be supported, though nothing enforces that yet — so the ledger reads as the one consumer's holdings, and the mechanism amounts to syncing the agent's context with the session's record of what it read and was served. The divergence that remains is context loss on the agent's side, mainly compaction, which only the agent can detect and already declares through the full-replay escape (20260826-173028-s-tac-1qr). Whether onceFull's session-served check already counts ledger reads or only served lanes needs verifying in code before the cheap half is claimed.
