The writing guide's prompt cannot produce valid JSON for a draft containing an ASCII double quote, so a check that should only advise instead rejects the capture report carrying it. Observed three times in one client session on v0.17.0-alpha.3 against a German-language graph. Each failure surfaced as a rejected `next` call at the capture guide step, reported as `parsing writing-guide result`, and the drafted report was resent in full afterwards. One of the three failures printed the model's raw response, which showed the cause directly: the `quote` value reproduced a passage that mixed a typographic opening mark with a plain ASCII `"` as its closing one, and that character went unescaped, so the JSON string terminated inside the excerpt and the body prose after it was read as structure. The other two failed one token later in the same shape. Retrying the identical report sometimes succeeded, and replacing the passage's ASCII closing mark with a typographic one avoided the failure.

The expectation is plainly that the guide's response always parses. Nothing about it is written down, and it needs no commitment behind it: the guide is advisory by design, returning findings the drafting agent folds in by judgment with no gate on either severity level (20260810-141555-d-cpt-20r). A check that cannot refuse a draft should not be able to refuse the report carrying it.

The suspected cause, unsettled: the output-format section teaches avoidance where JSON requires escaping. It asks `quote` to carry the draft's words verbatim, then says never a literal `"` because it terminates the JSON string, and never mentions the backslash escape at all. On a draft containing that character the two instructions have no common satisfying output. Two further readings point the same way and are untested. The schema the prompt displays is not itself valid JSON, since its enumerated fields use union pseudo-syntax, so the model is shown no parseable instance to imitate and no example carrying an escape. And the same avoidance shape covers newlines, through an instruction to keep every value on a single logical line, while backslashes go unmentioned, leaving a body holding a regex or a Windows path exposed the same way with nobody having hit it yet.

The candidate remedy, equally unsettled: state valid JSON construction with standard escaping once, in a partial both prompts include, since the pre-flight validation on the same capture path, the graph-facing check the guide was split from, carries the same avoidance rule for the body excerpts its own findings quote, and both checks already share one response parser. Any such partial must render static text, because both including blocks are the byte-stable cacheable prefix the pre-flight restructure established (20260604-164527-d-tac-fah), and interpolated content would break prompt-cache reuse on both paths at once.

Nothing observed ties the deviation to a language. The ASCII `"` is the plain keyboard character rather than correct typography in either German or English, and roughly a quarter of this graph's own entry bodies carry it, with no failure seen here since the guide shipped (20260811-154427-s-tac-yzg). Why it stayed latent here and fired three times in one session elsewhere is unexplained: the guide's own choice of which passage to quote sits between the character's presence in a body and the failure, and that choice was never measured.
