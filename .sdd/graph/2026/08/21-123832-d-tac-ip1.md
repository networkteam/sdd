The legacy `/sdd` skill family is gone in v0.18.0, completing the transition decision (20260820-162456-d-tac-o2v): the bundled renders are removed, the thin `/sdd-engine` skill becomes `/sdd`, and `sdd init` cleans up the installed copies it once wrote, so an upgraded user ends with exactly one `/sdd` and it runs the engine.

The cleanup is the part upgrades cannot do without. `sdd init` today leaves installed skill files in place when their bundled source is gone (20260507-174656-s-tac-zaz), so removal without cleanup would leave every existing user a stale skill-driven `/sdd` next to the renamed engine one, recreating the two-flow confusion the retirement exists to end. The gap already sketches the safe rule: delete an installed file only when its content still matches the stamp from its last install, keep user-modified files with a warning naming them. The rule covers every installed file of the old family, the skill texts and the reference files they load alike.

Removal waits on evidence, not on the calendar. It ships only after the bootstrap parity evaluation (20260726-195300-d-tac-fim) records a positive verdict, an evaluation done signal, or an insight drawing several evaluation runs together, stating parity was reached; a negative verdict keeps the skills installed and this plan waiting. As an early confidence check, the work starts by verifying that the integration test harness covers capturing every entry kind with its declared fields, naming any kind it misses, since kind capture is what the engine-only world rests on.

Out of scope: the deprecation notices and README changes, which belong to v0.17.0 under the transition decision, and the getting-started documentation, which is its own decision.

## Acceptance criteria

- [ ] An upgraded project, after `sdd init`, has exactly one `/sdd` skill and it starts the engine flow; the binary carries no legacy skill render.
- [ ] No orphaned skill file and no reference file loaded by a removed skill remains when its content matches its last install stamp; user-modified files stay in place and the init run names each one in a warning.
- [ ] No installed or bundled surface still points at the skill-driven flow.
- [ ] The parity verdict exists in the graph as an evaluation done signal, or an insight over several evaluation runs, stating parity was reached, and the done signal recording the v0.18.0 release references it.
- [ ] Integration tests cover capturing every entry kind with its declared fields.
- [ ] The v0.18.0 release notes tell existing users what was removed, what replaces it, and what `sdd init` changes in their working copies.
