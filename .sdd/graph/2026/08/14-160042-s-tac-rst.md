Search shows its match evidence on the CLI and hides it over MCP, so the agent-facing surface returns hits with no indication of why any of them matched. The CLI substitutes `DefaultMaxCitationsPerEntry` (3) when the flag is unset, deliberately distinguishing an unset flag from an explicit `--max-citations 0`; the MCP surface passes an omitted `max_citations` straight through as the Go zero value, which the query treats as headers-only. Same query, same index, two surfaces, and the one an engine-mode agent uses is the blind one.

For an existence or provenance question the two are not merely different in verbosity — they invert the answer. When the searched term appears in an entry's body or in an attachment chunk but not in its summary, a header-only result renders a true positive indistinguishable from a semantic near-miss: the matched term appears nowhere in what comes back. The tool text states the intent as `depth comes from show, not snippets`, which holds for a browsing query and fails for this one, because `show` presupposes already knowing which entry to open — the snippet *is* the answer being sought.

The attachment half compounds it. The presenter already renders the source attachment path when a citation comes from an attachment chunk, and the index records `is_attachment` alongside it — machinery that shipped with search itself (20260505-181352-s-tac-96a). But that marker lives inside citations, so suppressing citations suppresses provenance too: an attachment-sourced hit cannot be recognized as one, and the surface gives no hint that attachment coverage exists at all.

Observed end to end while closing the lifecycle-field gap earlier in the same session (20260813-092611-s-tac-75b). A text search for one proper noun returned exactly one hit — correctly, the entry holding an external bug report — and the header-only view made that hit unreadable as a match. The agent read past it, fell back to a file-level `grep` over the graph directory, and then asserted that attachments are not indexed: a false claim about coverage, offered without checking, which the user corrected. That is the mentions-as-facts shape already recorded (20260528-170354-s-prc-uq8), reached from a new direction — absence of visible evidence read as absence of a match, and a hypothesis about the tool stated as fact. So the cost is not only a wasted search; it is a plausible-but-wrong conclusion about the system's own capabilities, drawn from a view that omitted the evidence.

This is the same shape as the framework-versus-project marking gap (20260716-144113-s-cpt-7ch): the index holds the distinction, retrieval is correct, and what goes missing goes missing in presentation. Nothing is absent from the index or the presenter here either — only the default differs by surface.

**The asymmetry that should drive the repair.** A suppressed body citation is recoverable and a suppressed attachment citation is not. An entry's body sits one `show` away and its header already names the entry, so headers-only merely costs a round-trip. An attachment has no such fallback: neither a header nor `show` reveals that an attachment holds the match, so dropping that citation removes the only signal that the record worth reading exists — which is precisely the failure recorded above.

**An auto-mode follows from it, recorded here as an idea rather than a finding.** Choose the citation count from what matched rather than from which surface asked: a body-only match returns headers as it does now, since `show` recovers it, while a match carrying attachment chunks returns up to N attachment citations — enough for the agent to learn the record exists and open it. The decision has everything it needs where citations are already selected on the finder side, since attachment provenance is per-citation.

The path from such a citation to the attachment reaches the file but stops short of the passage. A citation holds the matched snippet, the source attachment path, and the heading breadcrumb of the chunk it came from, and the MCP read surface takes an entry ID, an attachment name and a byte offset — so identifying and opening the right attachment works. Locating the passage inside it does not: no citation carries a position, the chunk row and its index metadata record none, and there is no search within an attachment, so surrounding context means paging from the start and hunting for the heading. Paging itself was decided deliberately, so that large files never come back whole (20260606-004059-d-tac-d21) — but passage location was never weighed there, and treating that decision as though it had settled this would be a false floor rather than an argument.

**Direct browsing of the passage belongs in the same repair.** Because the read surface is already byte-addressed, a citation that carried its chunk's byte offset within the source attachment would let the existing paged read open directly at the passage — no new read capability and no search-within-attachment tool. The cost sits on the index side: the chunk row carries no position today and there is no metadata key for one, so the offset must be recorded at index time and passed through to the citation, and rows written before that change lack it until re-indexed, which any consumer has to tolerate rather than assume.

What stays unsettled is the shape of the default around all this. The narrow alternative is for the MCP surface to apply the CLI's default wholesale, distinguishing an omitted field from an explicit zero; what that trades against is serve size, which is plausibly why the surface was built this way. Auto-mode is attractive because it answers that trade instead of paying it — the expensive citations are the ones nothing else can recover — but N, whether a suppressed-count marker should accompany it, whether body citations deserve a cheaper middle setting, and whether the offset lands together with auto-mode or after it are all open. A layout-level answer would land in the search-output unification gap (20260705-010842-s-tac-6va), which already argues that retrieval results should be shaped through the view pipeline's vocabulary rather than search-specific flags.
