An MCP tool result carries its payload twice — once as `structuredContent`, once as a `content` text block holding the identical JSON — but that wire duplication is not model-token duplication: which copy reaches the model is decided by each client, and clients diverge without documenting it. Measured on a `sdd serve` door serve: 27,003 bytes of `structuredContent` plus 26,568 bytes of `content` text, semantically identical, 53,478 bytes on the wire.

**The duplication is the spec's own recommendation, not a defect.** The current revision (2026-07-28) says a tool returning structured content SHOULD also return the serialized JSON in a TextContent block, for backwards compatibility — a SHOULD, unchanged in strength since 2025-06-18. `go-sdk@v1.6.1` implements exactly that: for a typed handler it sets `StructuredContent` from the marshalled output and then, only when `Content` is nil, synthesizes a text block with the same bytes. Every serve handler passes nil, so the block is always added.

**What the spec does not define is which representation reaches the model.** It governs the wire result; projection into model context is client behaviour. Claude Code's documentation says it prefers `structuredContent` and does not forward duplicated text blocks; VS Code reportedly prefers structured too; Cursor's reported behaviour is contradictory across sources, and its recorded failure mode is that structured-only results are dropped before the model; for Claude Desktop, ChatGPT, Codex CLI, Zed and Continue no reliable primary evidence exists at all. No client examined is established to feed both copies to the model. This matters under the standing multi-harness commitment (20260628-130414-d-cpt-kvb): the same response behaves differently per host, and most hosts publish nothing about it.

**Hence the distinction worth carrying: doubling on the wire is certain and measurable, doubling in context is unproven for every client examined and explicitly absent on Claude Code.** The client table above is recorded with its evidence strength attached rather than as flat fact, because the reports it rests on are mostly agents and issue threads describing harness internals — a class of claim that proved unreliable in both directions while this entry was being researched.

**What the protocol permits, as distinct from what we do.** Byte-identity between the two fields is not required; the spec asks only that they be semantically equivalent, so a compact rendering in `content` beside the full object in `structuredContent` conforms. That shape is what SEP-1624 — an open proposal in the MCP specification repository, which would define `content` as model-oriented and token-efficient and `structuredContent` as machine-oriented — sets out, and what the MCP Apps extension guidance already uses. Omitting `content` altogether is protocol-valid but not deployment-safe, since a content-preferring client receives nothing. On the implementation side the synthesized duplicate is conditional on `Content` being nil, so a non-nil result with `Content` set changes the emitted shape without an SDK fork or a handler-signature change. Which of these to adopt is undecided and belongs in its own decision; recorded here only as the reachable option space.

**Budgets this lands against.** Claude Code documents a warning above 10,000 tokens, a 25,000-token default maximum, `MAX_MCP_OUTPUT_TOKENS`, and a per-tool `_meta["anthropic/maxResultSizeChars"]` capped at 500,000 characters; Codex CLI's ~10K-token budget is recorded separately (20260719-122547-s-tac-40d). No MCP-wide budget or protocol limit exists, which leaves that fact's conclusion standing unchanged — serve-side size discipline is the only host-independent guarantee, and it is what the serve-size gap (20260719-122103-s-tac-jom) is about.
