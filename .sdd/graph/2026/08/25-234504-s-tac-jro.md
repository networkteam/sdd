Capturing thirteen entries in one dialogue took about two thirds of everything a six-hour session placed in its context window, leaving a 1M-token window past four fifths full, while the engine's own latency accounted for about a twentieth of the wall clock — so the cost is what each serve carries multiplied by how often the loop runs, not a slow server. This outer evaluation measured that from a live client session which mined a long source document and then captured those thirteen entries, reading the engine's session event log alongside the host agent's transcript; the full analysis is attached, and the client project, its domain and its vocabulary are deliberately absent from both.

The run gives the three duplication classes recorded in (20260811-164958-s-tac-9l8) field evidence at a scale well past the estimate that entry carries, and establishes in code why each escapes the served-once memory — which the attachment sets out rather than this body. It also finds a repetition that entry does not name: play-back re-serves the whole draft on every revision round, about half of it text the agent had sent moments earlier, and deduplication cannot reach it because those bytes legitimately change.

Two of the session's three abandons were instances of (20260811-232108-s-tac-kus) — a wrong entry kind and a needed attachment, neither correctable once the first assemble report has landed — beyond the two that entry records. The doing added one thing it could not have known: an abandon does not free the context it consumed, so on the axis that decides how long a session can run at all, a discarded draft is permanently additive.

What the measurement implies for the repairs is not recorded here; those are separate entries pointing back at this one.
