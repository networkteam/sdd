In an engine-driven session the user has no read surface beside the conversation: what the engine is doing stays invisible unless the agent narrates it, and an entry the agent names by ID can only be read in full by leaving the dialogue for a terminal.

Observed by Christopher from working engine-driven sessions in this repo, where the engine drives the process over its MCP server. Which procedure instances are open, which step each one stands at, which transition was taken, and which queries and graph writes the engine served are all internal to the engine; they reach the user only through whatever the agent chooses to say about them. The second half is equally concrete: the dialogue cites entries by short ID, as it is designed to, and reading one of those entries in full means running `sdd show` in a separate terminal, outside the conversation the reference appeared in.

The expectation behind both is not recorded anywhere and does not need to be. Someone following a process a machine drives on their behalf should be able to see what it is doing, both to build intuition for how it works and to tell a misbehaving run from a working one, and should be able to look into anything the dialogue names without stepping out of the dialogue. The expectation sharpens for anyone extending the framework with procedures of their own: following a run is how intuition for a custom procedure is built and how a broken one is diagnosed, which makes this end-user developer experience as much as participant experience. It also cuts the other way. Most people following along are not reading a runtime, so what they expect is to follow the process in plain terms, not to be handed engine internals; the two expectations differ in depth, not in kind.

Nothing in the graph commits to serving either. The engine was deliberately shipped MCP-first into Claude Code (d-cpt-3yw), where the host renders the conversation and nothing of the runtime behind it, and the hosted webapp direction (d-stg-6za) covers a sandbox in which the dialogue itself lives rather than a companion beside a host that already carries the dialogue.

The deviation is that the dialogue is the only channel: everything the engine does, and everything the graph holds that it touches, is visible to the user only insofar as the agent restates it.

What the dialogue raised as a candidate answer, unsettled here: a companion UI running beside the host, showing the live procedure instances with their current step and the transitions taken, the query and write operations the engine performs, and an inspector for reading in full any entry that was loaded or mentioned. The shape the dialogue leaned toward is layered, following the two depths of the expectation: a primary view clean and non-technical enough for any participant to follow the run, with the technical depth — the internals of the objects behind it, the full operation detail — reachable on demand rather than filling the foreground. Whether such a surface reads a live engine, a session log, or both is open, and its operation-trace half depends on the engine recording its outbound responses and errors at all, which it does not yet do (s-cpt-ev3). The engine already carries a fidelity invariant for the agent's view of durable procedure state (d-cpt-0tm); the user's view has no counterpart, and whether it deserves one is a decision this gap does not make.
