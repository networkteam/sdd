A closed MCP connection concludes a quiescent session, so a routine reconnect ends a dialogue no participant chose to end.

Observed 2026-08-28. A session sat at its shell junction with no move open while the user reconnected the sdd MCP server (`/mcp` in Claude Code) to load a rebuilt binary carrying the freshly shipped ref-kind base fact (20260828-155447-s-tac-ilv). The disconnect fired the leave rule in `mcpapp/server.go` (`handleDisconnect`, `leaveSession`): open moves park, a quiescent session auto-concludes. Moments later the same conversation presented the handle with the user's words and was refused: the session was concluded, and a finished session is never re-served. Continuing meant a fresh session under a new handle.

Expected: only a participant act ends a session. A session tracks a conversation, and a connection identifies a client process, never a conversation; the two come apart in routine use (a client restart, a reconnect, several agents sharing one connection). A connection close therefore carries no information about whether the dialogue ended, and the engine must not act as if it did. The graph commits narrower forms of this already: a dropped connection may clear the live attachment stamp but writes no history (20260731-081528-d-cpt-rw7), and a session stays with the client driving it (20260718-131626-d-cpt-9of).

The deviation: a transport event writes the one act that is irreversible by design. The leave rule's rationale, that a quiescent shell leaves nothing to resume, measures the session's stored content instead of the conversation the session tracks. Reconnects are routine, and the same seam carries the served-once repetition gap in the opposite direction (20260826-173028-s-tac-1qr).
