The ability inventory — every predicate, query, and command a procedure spec can name, with each ability's contract — is to become a registry-rendered base fact, retiring the registry tool once the fact covers what it serves.

**Motive: surface economy.** A small host-facing tool surface is worth protecting (the narrow-surface commitment of the v1 engine plan). The registry is an authoring-time read, used rarely but decisively — rendered into the one pull layer it becomes semantically searchable and referenceable from other facts' teasers, which tool output never is.

**Staleness is a non-objection.** A rendered fact seems to lag while the tool always answers live — but base facts merge into every graph at load, so the fact can render at load time from whatever the registry then holds: exactly as live as the tool for any running binary, and still honest if abilities later become dynamic.

**One real prerequisite.** Part of the inventory exists only inside a live session today: the abilities that touch a session's dependencies — writing entries, reading the project's graph — are registered together with the code that wires them, so the full inventory cannot yet be enumerated for rendering outside a session. Separating what an ability declares from how it is wired is durable work either way, and may fold into the ability-model redesign if ordering favors it — that redesign changes what abilities are and therefore the fact's content, but rendered content regenerates for free, so the direction stands independent of it.

**Deliberately open:** one fact or per-class facts; indexed or reached by teaser; the exact render moment.
