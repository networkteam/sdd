# Editorial review of the procedure spec reference

A fresh Fable agent with no SDD priming read exactly three rendered entries through the CLI, in the natural preparation order — type-system overview (20260812-180000-s-prc-typ), procedure kind fact (20260813-170000-s-prc-prd), spec reference (20260814-100000-s-prc-psr) — and judged the third as the third step of that path: definitional order, concreteness, build-up coherence, internal logic. Nothing else was in its context. Its report follows verbatim.

---

# 1. READING PATH NOTES

**Doc 1 — typ (type-system overview).** Establishes the two entry types ("a **signal** records something noticed; a **decision** records something committed to"), the full kind lists including `procedure` — "How does a playbook move run?" — the five layers, immutability ("retiring one means adding a closing or superseding entry, never editing"), and the discriminator tests. It hands off explicitly and well: "each kind has its own authoring fact carrying its meaning, make-up, and craft — pull it before drafting that kind." The reader arrives at doc 2 knowing what a procedure kind *is for* but nothing about its anatomy.

**Doc 2 — prd (procedure kind's authoring fact).** Establishes the run/read distinction ("Every other entry is read; a procedure is also run"), the engine, the canonical, the class set (`move`/`shell`/`task`), the three-field anatomy ("`params` declare what a start may pass in; `state` declares the working fields steps collect and read; `steps` is the walk itself"), the gate/agent-chooser/user-chooser triad, abilities and "the engine's live registry", the body's `## unit: <step>` sections, supersession, and load-time validation. Its handoff is explicit and correctly scoped: "How to write the spec — the fields, the variable types, the step shapes, a skeleton, and pulling the live ability registry — is the spec reference fact `20260814-100000-s-prc-psr`." One vocabulary item it introduces — "a question declared for the user" — never reappears in doc 3 under that name (it becomes "user chooser"), a small seam in the handoff.

**Doc 3 — psr (the spec reference, under review).** Delivers field-by-field syntax, a closed presence-check vocabulary, closed type set, guard grammar, chooser/option shape, the dispatch model, and a worked example. Mostly it builds cleanly on docs 1–2. Its weak points: it under-delivers on the registry-pulling promise, leaves several late-list terms undefined, and muddles the channels through which a run receives its initial values.

# 2. DEFINITIONAL-ORDER FINDINGS

1. **"the store"** — first sentence of `params`: "Params seed the store once, at start." Never defined in any of the three documents. Doc 2 says only that state fields are "collected and read." The reader must infer a run-scoped variable store from usage ("the store's fields", "this run's store"). Inferable, but used as a known term at first appearance.
2. **"ability names" in the guard grammar** — Gate steps: "The guard is a boolean combination of ability names written infix." Doc 2 established that abilities exist, but the classification that makes this sentence precise ("Guards name checks…") arrives three sections later, under Abilities. At the moment of reading, the reader cannot know a guard names specifically *predicates*, not queries or commands.
3. **`op: <command name>`** — "A gate may also run one effect first (`op: <command name>`)." "Command" as an ability class is defined only later in Abilities. Same forward reference for **`call`** ("an optional command it calls") in Chooser steps and **"query name"** in `inject`.
4. **"reportable" / "reported"** — On any step: "the state fields reportable here… required ones hold the step until reported." The reporting act — the agent submitting values against a schema — is never defined before this; it is retro-illuminated by "served as the step's report schema" in Variable types. Doc 2 said only "steps collect."
5. **"the closed ref-kind set"** — Variable types, `ref`: "relationship kind from the closed ref-kind set". That set is enumerated nowhere in the three documents, and no pointer says where to find it. Arrives from nowhere.
6. **"a confidence grade"** — `confidence` type. The grades are never enumerated in any of the three docs (the reader sees `confidence: high` only in envelopes, which are out-of-scope context). Contrast `intent` — "a directive's intent" — which doc 1 *did* enumerate (pending/guiding/settled), and `entry-kind`/`layer`, both fully enumerated in doc 1. Those three are fine; `confidence` is not.
7. **`attachment-handle` — "a staged attachment's handle"** — staging and attachments appear in none of the three documents before this line. From nowhere.
8. **"a shell's framing"** — `procedure-spec` type: "params, state, steps, and a shell's framing". Doc 2 established the shell class, but "framing" as a declarable thing is never defined, here or anywhere. An author writing a shell has no idea what this field is.
9. **`fact-index` — "a fact's retrieval-index enrollment: title and topic"** — no prior document mentions a retrieval index. From nowhere.
10. **`preflight-findings` — "write-gate findings"** and **`guide-findings` — "writing-guide findings"** — neither the write gate nor the writing guide is introduced anywhere in the path. Both are glossed only by a hyphenated restatement of their own names. ("engine-written, never collected by a step" is a useful *usage* note, but the reader still doesn't know what these findings are.)
11. **`inspectedIdsResolve` / `doneEntryResolves`** — used in the worked example's guards. The state section licenses only presence checks by name ("The commonest gate is a presence check… `hasAnchor` reads `anchor`"), implying other check families exist but never naming or exemplifying them in prose. These resolution predicates appear first inside the example, uncommented. The reader must guess they come from the registry — and cannot tell whether the `Resolve`/`Resolves` spelling difference is a grammatical-number rule (plural field → `Resolve`?) or a typo.
12. **"sub-move"** — Dispatching: "start the named procedure as a sub-move of this run." First use; "move" is established (doc 2), "sub-move" is inferable but never defined — notably whether a sub-move has its own session standing, parking, abandonment.
13. **Terms properly established earlier (fine, for the record):** gate, user/agent chooser, engine, canonical, class `move`/`shell`/`task`, `params`/`state`/`steps` as the three fields, `## unit:` sections, supersession chain and head, load-time validation, the live registry's existence — all doc 2; kinds, layers, intents, immutability — doc 1.

# 3. CONCRETENESS FINDINGS

1. **The registry pull — the biggest gap.** "The registry is askable on demand, the same way entries are read — request it by class (predicate, query, command) whenever you write steps." *How?* No command, tool, or invocation is named. "The same way entries are read" is a gesture, not an instruction — entries are read by some show mechanism the doc never names either. Doc 2's handoff explicitly promised this document covers "pulling the live ability registry", and psr's own upstream summary promises "how to pull the live registry of abilities". The body delivers only that it is pullable. Concrete replacement needed: the actual invocation (command or tool name plus the class argument).
2. **Template placeholders.** "Units may use template placeholders over the store's fields and the step's injected data." No syntax is shown — not one placeholder appears anywhere, including the example's prose description of its units. An author cannot write a placeholder from this document. Needs one literal example of the placeholder form.
3. **`op` semantics.** "A gate may also run one effect first (`op: <command name>`)." First — before what, and how often? On entry to the step, before each guard evaluation, once per run? And where does the command's output go — into the store, per its registry contract? Unanswered.
4. **Dispatch-seed arming.** "arms the mapping, and the next procedure started under this run receives each value". Is "the next procedure started" *any* next start, or only a start of the named canonical (`procedure: <canonical>`)? The block names a procedure but the sentence's mechanism is "next started". If the agent starts a different procedure first, does the seed misfire, wait, or lapse? Unanswered, and it matters for correctness.
5. **"a value passed explicitly at start wins"** — passed by whom, through what channel? `params` was defined as "what a caller passes at start", yet this sentence is about *state* fields (the seed targets state). It implies a start can carry explicit state values — a channel no section defines. Same muddle as the next finding.
6. **`default` — "state only: applied at start when the caller left the field unset"** — but the state section just said state "arrives from a dispatching parent rather than the caller". If callers cannot set state, "when the caller left the field unset" is vacuously always; if they can, the params section's definition of the caller channel is incomplete. Also "the one literal a spec carries" — a literal of what form for non-text types (`bool`, `entry-id`, `list<T>`)? Unanswered.
7. **Agent choosers get one parenthesis and nothing else.** "An agent chooser (`chooser: agent`) or user chooser (`chooser: user`) declares `options`…" — everything after this sentence (stopping, loop-back, dispatch) is illustrated for user choosers only, and the example contains no agent chooser. Doc 2 said an agent chooser "records the agent's judgment with its evidence" — where does the evidence land in spec terms? A `collect` field? Nowhere shown.
8. **`render`** — "the name of an extra `## unit:` section from the body, served with the step (typically presenting one collected field's content)". What may the name be — any string after `## unit:`? How does that unit "present" a field's content — via the (also unshown) placeholders? No render example exists in the doc.
9. **"Start small, load it, run it"** — load it *how*? Validation "when the engine loads the entry" is a passive event from the author's seat; the author needs the action that triggers a load (a command, starting the move, something). Unanswered.
10. **Option-level `collect`** — the required-hold rule ("required ones hold the step until reported") is stated for step-level collect. Whether it binds an option's `collect` the same way (e.g. a non-optional field on an option) is unstated.
11. **Genuinely concrete and creditable, for contrast:** the guard grammar's closure ("with `and`, `or`, `not`, and parentheses, and nothing else: no comparisons, no literals, no field access"); the quoting instruction ("quote the marker: `"anchor?"`"); the failure-mode warning ("a guard naming a check whose field the spec never declares loads cleanly and then never advances"); the dispatch bridge ("the child writes nothing into this run's store, so the reported field is the only bridge"); `end(completed)` / `end(abandoned)` as literal targets.

# 4. COHERENCE AND LOGIC FINDINGS

1. **"Seed" is overloaded into apparent self-contradiction.** Params: "Params seed the store once, at start." Next section: "seeding writes state only." Read in order, the second sentence flatly contradicts the first — params are not state. The resolution (the second "seeding" means dispatch-parent seeding specifically) is only available three sections later, in Dispatching. One word, three mechanisms (caller params, parent seed, `default`), no disambiguation at the collision point.
2. **The promised registry how-to is missing** (finding 3.1) — this is also a chain-coherence break: doc 2's handoff sentence and psr's own summary both name "pulling the live ability registry" as content this document carries. It doesn't.
3. **Static vocabulary vs live registry — which is the authority?** The state section presents a closed, in-document list: "a field is gateable on presence only when it carries one of these names", "nothing reads a name outside this vocabulary." The Abilities section says: "what it lists is exactly what a spec can name, for the running version." Entries are immutable (doc 1), the registry is live — the moment the running version gains or drops a `has*` predicate, the printed list is wrong, and the document never says the registry supersedes it. A reader cannot tell whether to trust the list or re-derive it.
4. **"advances in one of three ways" vs two step headings.** The steps intro promises three ways; the subsections are "Gate steps" and "Chooser steps" (with "On any step" being cross-cutting, not an advancement mode). The reader must back-derive gate / agent chooser / user chooser from doc 2's triad. The count and the structure disagree on the surface.
5. **"one `## unit:` section per step" vs render's "extra" units.** The Instruction units section states the complete-sounding rule "one `## unit: <step id>` section per step", with no mention of the extra render-named units the On-any-step section licensed. The two statements don't contradict fatally, but the section written as the definitive statement of the body's shape omits a unit class the same document introduced.
6. **Doc 2's "question" vocabulary is dropped without a bridge.** Doc 2: "a question declared for the user stops everything until the user answers." Doc 3 has no `question` construct; the stopping construct is the user chooser ("A user chooser stops the run until the user answers"). The behavior matches, so no contradiction — but a reader hunting for how to "declare a question" finds nothing under that name.
7. **The example under-delivers on its own "width" claim.** "written for width rather than realism" — yet it exercises no agent chooser, no `render`, no `op`, no `call`, no `otherwise`, and no `default`. What it *does* claim, it delivers accurately: the annotations ("an optional param and an optional collect, two injects with differently shaped arguments, compound guards, a user chooser that loops back for correction, a dispatch seed on the confirming option, and a closing gate on the field the dispatched recording hands back") all check out against the YAML, and every construct in the YAML obeys the stated rules — except the two unintroduced resolution predicates (finding 2.11).
8. **No contradictions with docs 1–2 otherwise.** Doc 3's dispatch section ("A field that arrives from a dispatching parent rather than the caller is state, not a param") is consistent with its own state section; validation-at-load matches doc 2 ("a broken workflow fails loudly there, not silently at capture"); `layer: process` in the example matches doc 2's "pinned to the process layer"; the `capture` canonical in the example was pre-seeded by doc 2 ("capturing an entry… `capture`, `release`, `cupping`"). The ref pointers between the three documents are accurate in both directions.

# 5. WHAT WORKS

The macro-architecture of the chain is genuinely good: doc 1 ends by telling you authoring facts exist and to pull them; doc 2 ends by naming psr's ID and drawing the exact boundary ("reach for it the moment you move from choosing the kind to writing the workflow"); psr opens precisely where doc 2 stopped, on the three fields doc 2 named. Within psr, the closed sets are stated *as* closed (guard grammar, type set, presence vocabulary), failure modes are named concretely (the never-advancing guard), the semantic-type/report-schema split is a real burden-remover stated as one ("Nothing about shape needs restating in the spec"), the dispatch model is crisp ("the reported field is the only bridge"), and the worked example is annotated, rule-conformant, and carries a trust warrant ("It ships from the same source the engine's own tests load, so it is valid by construction"). The prose discipline of defining most terms at first use (guard, presence check, canonical binding) mostly holds — the failures are concentrated in the type list's back half and the run-seeding channels.

# 6. VERDICT

**Mostly yes, with three real breaks.** A careful reader arriving through this path can write a structurally valid *simple* workflow — presence-gated steps, a user chooser, collects, a dispatch — by patterning off the example, because the example is honest and the core grammar is closed and explicit. The chain actually breaks down at:

1. **The registry pull** — the one promised, load-bearing "how" the document never delivers. Without it the author cannot write any guard beyond the printed presence list, nor any `inject`, `op`, or `call`, except by copying the example's four function names on faith.
2. **Template placeholders** — declared usable, never shown; the author cannot write one.
3. **The run-seeding channels** — "seed" overloaded into a local contradiction, `default`'s "caller" clashing with the params/state split, and "a value passed explicitly at start wins" implying an undefined channel. An author wiring a parent-child handoff will guess here.

Secondary guessing points: agent-chooser mechanics, `render` mechanics, the unintroduced back half of the type list (`attachment-handle`, `fact-index`, the two findings types, "a shell's framing"), and the resolution predicates that appear only inside the example. None of these blocks a first simple procedure; all of them block confident use of the full declared surface.
