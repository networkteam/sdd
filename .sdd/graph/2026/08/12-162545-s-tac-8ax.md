A two-lens evaluation of the framing-lane split finds the work sound and deployed, but leaves the behaviour it was built for unvalidated in use: three live observations on the restarted engine confirm the split loads, serves, and converges, and none of them distinguishes the split from the joined declaration it replaced.

**Inner — sound.** Verification was re-run against the merged mainline rather than the branch: `go vet ./...`, the full `go test ./...`, and `golangci-lint run ./...` all clean. The merged base-procedure entry carries six framing lanes in the intended order, with each of the four overview sections keeping exactly the filter, rank, name, and render clauses it had inside the former joined pipeline. A regression test drives a fixture graph carrying one entry per section, converges a reorientation to empty, perturbs a single section, and asserts the other three stay stubbed; it was run against the pre-fix declaration during implementation and failed there on all three, so it discriminates rather than merely passing. The 25KB door-serve payload budget that shipped alongside shell-declared framing (20260719-015148-s-tac-khq) still holds — the split adds only the extra block separators between lanes. One judgment recorded rather than hidden: the base-procedure entry was edited in place, while the README in the base-procedure entries directory prescribes that revisions ship as successor entries superseding the prior head. The departure is deliberate, named in the shipped record, and consistent with every prior revision of that file.

**Outer — deployed and harmless; the payoff unobserved.** Three observations, in order. The restarted server loaded the six-lane declaration from the embedded procedure and served every lane in full on a fresh connection, with content and order matching what the pre-split framing carried and no fail-loud guard tripping. An immediate no-argument reorientation on the same connection returned no framing at all — every lane stubbed. Then another session merged four entries and a further reorientation returned the recent-movement lane alone, every other lane still stubbed.

**Why that third observation proves less than it appears.** Each of the four overview sections was checked against the merged entries and found genuinely unchanged: the new tactical directive carries `intent: pending` and so never enters the guiding-directives lane, that lane rendered byte-identical to the earlier serve so no heat re-ranking occurred, the new done signal closes an entry no focus lists as a child, and aspirations and participants were untouched. With all four unchanged, the pre-fix joined lane would have been stubbed too — the observation is consistent with the fix but does not evidence it. The same holds for the first two observations, which the pre-fix code would have produced identically. Manufacturing the discriminating case — a throwaway actor entry, or a contrived reference to perturb a directive's heat ordering — was rejected: putting a fabricated entry in the graph to satisfy a test is worse than an honestly partial pass, and the regression test described above already covers that case.

**What stays open.** The claim that a change in one overview section leaves the others stubbed rests on that regression test alone. How often a single overview section changes in real use is unmeasured — four entries across one session is an observation, not a sample — so the frequency of the condition this repair improves remains an open question rather than a finding. The completion path is opportunistic rather than another dedicated run: the next session in which one overview section does change gets the observation for free.
