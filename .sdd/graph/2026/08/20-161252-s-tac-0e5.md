The MCP `show` surface cannot express zero traversal depth: a live request with `up: 0` and `down: 0` returned the default-depth `# upstream` and `# downstream` summary chains, so callers asking for primary entries only can receive avoidable context-heavy responses. The reported four-primary call crossed the host's approximately 10K-token tool-output budget, the failure mode documented in 20260719-122547-s-tac-40d, and a separate one-primary reproduction still emitted an upstream chain at explicit zero.

Zero is expected to suppress traversal in that direction. That behavior is part of the depth-limited `show` capability delivered by 20260414-201640-s-tac-4z6 and is explicit in `internal/query/show.go`, `internal/model/show_tree.go`, its model regression coverage, and the CLI flags in `cmd/sdd/main.go`. Source inspection localizes the mismatch to SDD's MCP adapter rather than the MCP SDK: the SDK has already decoded the supplied values into `ShowArgs`, whose non-pointer integer fields in `mcpapp/tools.go` cannot preserve omitted versus explicit zero, and `Server.show` then rewrites every zero to `DefaultShowUpDepth` or `DefaultShowDownDepth` before calling the application. This is the same omitted-versus-explicit-zero boundary shape already observed on the MCP search surface in 20260814-160042-s-tac-rst.

Christopher's intake requirement for resolving this specific deviation is test-first: add an MCP regression test and observe it fail against the current behavior before changing production code, then retain it to prove both sides of the boundary — omitted depth values still select the documented defaults, while explicit zero produces primary-only output.
