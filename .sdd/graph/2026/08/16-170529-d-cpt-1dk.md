The kind default — an entry captured without declaring a kind becoming a gap or a directive — is ruled a legacy convenience of the CLI capture surface, not type-system semantics: in the type system a kind is always an explicit choice, picked for what the entry is, and shipped type-system knowledge presents it that way.

The question arose while authoring the kind facts under the kind-knowledge plan (20260812-134549-d-tac-9be): drafted resist-the-default warnings treated the default as a semantic trap both the gap and directive facts had to guard against, and the facts' generated mechanics initially rendered the default as a type-system rule. Ruled out on both counts — the warnings and the rendered default clauses were cut, because a default is a property of one capture surface, not of the kinds themselves. The ruling also instructs reconciliation: the frozen legacy `/sdd` skill's concept reference, bundled with the CLI's installed skill render, marks directive as the default kind — that marking describes surface behavior and must not migrate into any shipped fact.

The CLI keeps its convenience until that surface evolves on its own line — nothing here commits to changing it — and the engine capture path already requires an explicit kind, so no follow-up is owed anywhere.
