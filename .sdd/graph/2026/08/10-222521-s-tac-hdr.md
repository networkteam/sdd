Commit `d3393ae1` makes sdd's config files version-tolerant on read and patch-only on write, retiring the strict-parsing coexistence gap (20260810-144515-s-tac-8ae): both halves that gap named are in place, and the failure it described can no longer arise on any file this binary touches.

Reads no longer reject a key they do not know. `StrictUnmarshalYAML` is deleted rather than narrowed — the whole-document rejection was the defect, and leaving it exported would let it drift back. `UnknownYAMLKeys` reports what a read passed over and `KnownYAMLKey` gates a write, both derived from the struct walk `EffectiveConfigValues` already used, so what counts as a config key is defined once and cannot drift from the schema. One finder, `UnknownConfigKeys`, computes the unknown set for every surface that reports it: the `sdd config` provenance view, and a warning on each CLI run which through slogutils covers styled TTY and `sdd serve`'s stderr in a single call. The one-time door-serve notice the gap proposed is deliberately not built — the warning already reaches the serve process without touching a base-procedure spec, and a per-session notice needs a mechanism the framing model does not have.

Typo protection moved to the write as the gap specified, but not as first implemented. Validating the whole patched document against the layer's schema — the obvious reading — made `sdd config set` refuse every write as soon as the file held one foreign key, leaving an older binary able to start but not to write. The probe now judges only the key being set. That defect passed the entire test suite and failed on the first run against a real file, another instance of the run-it-once discipline (20260726-204112-s-prc-ogp).

The write path was the other half, and tolerance alone would have made it worse: every config write already patched the document except `repos.SaveConfigTo`, which marshalled `GlobalConfig` back over the file and dropped comments and unmodelled keys with it, so a loud startup failure would have become silent data loss the next time an older binary ran `sdd repo add`. `RepoAdd` used both mechanisms in one method. `SaveConfigTo`, `Manager.Save`, and the unused `GlobalConfig.RemoveRepo` are deleted; `connectRepo` patches the `repos` list through `SetYAMLValue`, a general form under which `SetYAMLField` and `SetYAMLSequence` become constrained cases over one splice; and the five read-patch-write sites share one `configFile` helper carrying the permission rule. The whole-document writer survives only as a test fixture in `repostest`, structurally beyond production's reach.

This keeps the comment-preserving upsert that shipped with the config overlay and reverses the strict decoding that shipped beside it (20260708-213621-s-tac-cjr), and repeats at the config layer the strictness-as-defect judgement already reached at the session-store layer (20260726-203237-s-tac-jit). The permanent read-compatibility contract (20260602-203349-d-cpt-i2x) binds graph entries rather than config, but its conversion-path principle — a format change must never leave older material unreadable — is the same reasoning applied one surface over, completing the drop-in version coexistence the session-subsystem rebuild established at the session-log layer (20260730-093011-d-tac-k4q).

Commit `b1881f30` clears the other blocker on the same head, and is recorded here for want of a gap of its own: `examples/extendingsdd` had stopped compiling on `main` because the rebuild gave `SessionStore` a `Delete`, gave `StagedBlobStore` `StagedSessions` and `DeleteStaged`, and moved the filesystem constructors to variadic `StoreLocation`. That module is the CI guard for the published port surface and runs as its own CI step, since the root module's `./...` does not enter nested modules (20260713-001910-s-tac-ill) — so a full local suite stayed green while `main` was red. The four-line repair is trivial; what it registers is not, because those port changes are a breaking change for anyone embedding the module and belong in the release notes as one.

Tolerance protects no already-released binary: v0.16.2 will still exit on a key it does not know. The value is entirely forward, which is why this lands before the next tag rather than after it.
