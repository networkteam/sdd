Failures on the engine's non-mutating path are separated by who must act before another attempt can succeed, and the engine hands the choice back to the dialogue instead of absorbing it. Four cases. Nobody, because time alone is enough: a rate limit, a 5xx, a dropped connection, a malformed model response. The agent, whose input was wrong: an undeclared field, a patch that does not match, a reference that does not resolve. The user, acting outside the tool, after which a retry does work: an expired API key, exhausted credit, an unconfigured provider, a full disk, a refused commit. Or nobody reachable from here, because the fault is in SDD itself: a spec that will not load, a corrupt entry, a bad transition. Only the first changes what the engine itself does, but every one must reach the agent carrying what happened, who must act, and whether trying again helps once they have, because the agent's job is to tell the user something true. This responds to the missing separation recorded in (20260829-111247-s-cpt-xp3) without closing it, since committing to a behaviour does not produce it.

From outside, what this commits to is plain. A call into the engine never leaves the agent waiting long enough to look frozen, and never leaves it retrying in front of the user until it gives up. Whatever goes wrong inside comes back named and with what to do about it, so the agent and the user can react together in the conversation while it is happening, knowing whether to wait, to fix something, or to stop. When the obstacle clears, saying so is enough to carry on, and nothing said or drafted beforehand has to be produced again.

What the engine does with a transient failure: try again briefly, sized to the failure, then stop and hand back. It never sits in a long wait. A wait-only failure outliving that attempt is handed back as the same case, still a matter of waiting, with whether to keep waiting now the user's call. What comes back is a position the agent can advance from, carrying what a retry needs and enough for the agent to tell the user plainly what happened, so trying again becomes a choice made in the dialogue. Advancing from that position costs no re-transmission, because what the agent already reported stays in the engine's hands and is never sent twice. A failure the user must act on carries the original error text, at least the excerpt that matters, verbatim rather than paraphrased away, alongside whatever explanation of what might help can honestly be offered; the retry stays available for afterwards. The underlying error is never swallowed, because in the complicated cases the exact phrase is what the user searches for. A fault in SDD itself is reported rather than retried.

Absorbing the wait was weighed and rejected. A long backoff inside the call is indistinguishable from a hang, the host's own timeout ends the call regardless and leaves the state ambiguous, and while the call is blocked the agent cannot say a word to the person waiting. The aspiration's test for any automation is whether it enables better dialogue (20260422-122136-d-stg-beb), and a stalled tool call fails it. Returning a bare error carrying a note about what survived was rejected too: an error invites the agent to look for something to fix, and that is the misreading behind the loss the gap records, where an agent answered a failed check by resending its entire draft three times. A position the agent advances from also keeps the retry reachable as an engine capability rather than a host-local instruction (20260707-134311-d-cpt-476).

The placements that keep this true without every procedure re-deciding it: classification belongs where the failure is produced rather than where it is reported, because the difference is invisible higher up: one provider call returns 401, where no wait ever helps, and 429, where waiting always does, and only the code making that call can tell them apart. Handling belongs in the one place every step's operation already runs, so no procedure declares any of it and operations not yet written inherit the behaviour. A retried failure must leave a trace: a permanent defect can present as transient by sometimes succeeding on a retry, and silent retries would turn a reportable bug into an unexplained slowdown.

This extends to the operations and served queries running before the write what the delivery directive settled for confirmed mutations (20260730-171311-d-cpt-0cv), whose own path is unchanged. Left open deliberately: how long the engine tries in each case, whether a minimum interval must separate retries, and whether the three non-waiting cases ever need naming in code rather than only in the message.
