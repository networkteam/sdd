Kind knowledge becomes graph-resident — one overview fact plus one authoring fact per kind, composed through a real construction model and generated wherever the mechanics are already declared in code — so that an agent with no SDD priming drafts an entry of any kind and corrects both itself and the user toward the framework rather than merely satisfying validation.

That outcome is the target, and it is stated here because the line it sits on had never stated one. The focus this realizes commits an order — facts, then the consumers, then calibration (20260811-231119-d-tac-uea). The directive above it commits a structure. The plan this replaces committed deliverables. None of the three said what is true about the world when the work is finished, so completion resolved to whether the fact entries exist: mechanism mistaken for result. The distinction matters for content, not just bookkeeping. An agent that only complies cannot push back in dialogue, so each fact must carry the reasoning behind its kind — a required-field checklist would pass every mechanical check and miss the target entirely. Two baselines for judging it are already recorded: the live writing guide returning unstable findings across repeated runs on identical input (20260811-183929-s-tac-fu8), and drafting agents recovering through supersedes, restarts and cascading overrides across live bootstrap runs (20260722-141659-s-cpt-rza). Those two are one absence seen from both sides.

This plan supersedes the full-type-capture plan (20260726-193730-d-tac-zrh) rather than layering on it. That plan has no landed slices since late July, and its first acceptance criterion — one detail fact per kind — was already contradicted by the directive refining it, which commits two facts per kind (20260811-184407-d-cpt-x7a). Because the construction model below absorbs its shared draft boundary, its per-kind requirements, its diagnostics and its lane guidance, leaving it active would leave three overlapping commitments over one body of work. Superseding removes the duplicate and gives the directive's pending intent a home; its per-kind checking facts stay a clean follow-on. Carried forward unchanged in substance: annotation capture (20260722-141909-s-tac-6rd), kind-relevant-only diagnostics (20260722-141852-s-tac-dhn), the multi-target supersede whose home that plan already named (20260731-083311-s-tac-4vx), the per-kind lane pointer, carried instruction units, the live-head `show` contract, presentation coverage, and the freeze on legacy skill prose — each restated in this plan's acceptance criteria, which become their home once the retired plan stops carrying them.

**The knowledge is consolidated, not composed.** It already exists, distributed across captured graph entries, the bundled skill references, the engine's own embedded procedure bodies and served instruction units, and the kind-specific pre-flight templates — the last holding it in reverse, as rejections. Each kind is therefore built positive-side first, and the pre-flight rubric is run afterwards only as a completeness audit: a check used as a source silently becomes the definition, while a check used as an audit can only reveal gaps. Every kind is reviewed by the user before it lands. Because these facts ship to projects doing no software work at all, each kind's wording is instantiated in a named non-software act — a roastery, timber construction, child care — and kept only if it still discriminates there (20260730-101601-d-cpt-r99); that step is also what answers the mechanism by which specimen-grounded guidance manufactures its own narrowing on evidence nobody has reason to doubt (20260811-172858-s-prc-6b0).

The overview fact carries how the types and kinds play together and how to discriminate the right one. That knowledge must be reachable *before* a kind is chosen — inside a lane the choice is already made — so it enrolls in the derived index (20260719-133529-d-cpt-qhn) and the capture procedure's first step points at it with a teaser conveying why and when reaching for it helps without reading as complete (20260730-110228-d-cpt-rh6), while each kind's assembly lane carries the same kind of teaser for its own fact, where the drafter is actually composing. Whether the overview goes further and is served in full at every session open stays an open call this plan makes deliberately: the mechanism already ships — a shell-declared topic selector rendering selected fact bodies before the process core — but its guard is that a priming fact is paid for at every open and must therefore be written tersest of all (20260810-134906-d-cpt-a2a), so always-on has to be earned rather than assumed. The discrimination text is hand-carried in the capture procedure's body today, which makes discrimination and de-duplication one piece of work rather than two.

**One entry-construction model owns kind structure.** Common frontmatter fields sit alongside a set of nil-able per-kind blocks, of which at most one may be set and must agree with the declared type and kind, with shared sub-structs where kinds genuinely share a group. Construction is free and validation is a separate call returning findings, because total-by-construction and represents-all-history cannot both hold for one type: history contains shapes current validation rejects, and a kindless signal has no block to convert into. So the model is permissive in structure and validity is a checked property. The read side keeps its raw parsed form as the storage representation and loads every parseable entry, reporting structural drift as health data; the domain model is a projection translated to where domain logic runs, and that translation may be lossy because nothing durable depends on it round-tripping. One rule set produces both consequences — blocking on the write path, warning on the read path — so the read side stops owning per-kind rules. `show` is the one read consumer wanting the structured shape. The requirements the model must express are those the active contract enumerates (20260702-222259-d-cpt-7iy). They exist today as imperative control flow spread across the model, the CLI command and the application draft mirror — and not merely duplicated: the engine write path never runs the intent-on-directive and class-on-procedure rules at all, so the two write surfaces enforce different rules and unification closes a live divergence rather than tidying code.

**Base entries are composed, not concatenated.** Frontmatter marshals from the construction model instead of being spelled as a YAML string constant; per-kind prose lives in embedded template files; generated blocks arrive at named placeholders so regeneration can never disturb prose. Whole entries are authored as templates — the reviewable shape, where a diff reads like an entry — and every rendered entry is validated through the construction model, with a table test rendering and validating all of them so a mistake fails the build rather than surfacing at a reader's graph load. This extends the pattern already shipping: reference content derivable from code renders at load, so the fact tracks the code with no manual sync (20260707-140544-d-cpt-dtv), and hand-written prose is reserved for judgment code cannot express. Mechanics are *carried* rather than pointed at, because a base fact reaches a project holding none of this repository's source — pointing there strands the reader, the one unrepairable failure (20260810-121912-d-cpt-7zr). Generation sources from the declaration that enforces the rule, never a parallel table, and a kind or field shipping without a description fails the build and renders a loud error rather than blank.

**Type-system facts are override-closed.** They are coupled to declarations and validation a project cannot override anyway, so allowing a superseding copy buys nothing and risks a project freezing a stale generated block that silently wins. Which facts those are is a declared property resolved through ordinary graph resolution rather than a list of IDs the gates carry, following the same discipline that made fact indexing derived (20260719-133529-d-cpt-qhn). Projects narrow through the `rule` kind when it ships, which was conceived precisely as the extension point that makes constraints narrower and never opens base ones up (20260622-084244-d-tac-eho). This narrows the base-facts directive's per-project-overridable clause for code-coupled facts (20260707-140544-d-cpt-dtv); procedure versioning with supersede chains for override conflict detection is a real and separate need, out of scope here.

**Removing the copies is reconciliation, not deletion.** Kind knowledge is hand-copied across the write path, the served procedure and shell bodies the agent reads, and the engine's schema surface — the site-by-site inventory lives in the attachment. Each copy is inventoried and each unique claim it carries either lands in a fact or is raised as a contradiction for the user's ruling; nothing is removed before its content is accounted for.

Delivery runs the construction model and composition layer with the overview fact and the `done` fact end to end first — `done` because its material is already banked and argued through — then `procedure`, the mechanical extreme that forces the generated-block seam before the form hardens across the remaining kinds, which follow one at a time, then reconciliation. One consumer comes in with the facts rather than after them: the writing guide's prompt renders the overview fact as the framework floor beneath every judgment, the first of the two prompt elements the directive above commits (20260811-184407-d-cpt-x7a). Without it the completion check could not move — the harness exercises that guide, and nothing else in scope changes what it reads. Out of scope: the per-kind checking facts, whose calibration nuance is worth less than a stated semantics; the specimen sweeps already re-sequenced behind these facts (20260811-141038-d-tac-rvu); the `rule` kind; and bootstrap parity, whose first criterion is this line completing (20260726-195300-d-tac-fim). Completion is checked by re-running the specimen harness already banked in the repository (20260811-190704-s-tac-r7h) against the baselines above — a smoke test that the form serves the target, not a calibration pass. The capture procedure receives the structural assembly changes (20260703-094500-d-prc-cap).

## Acceptance criteria

- [ ] One entry-construction model exists in the domain layer: common frontmatter fields plus nil-able per-kind blocks, at most one set and agreeing with the declared type and kind, with shared sub-structs where kinds share a field group. Construction never fails; validation is a separate call returning findings.
- [ ] Every per-kind structural requirement the active 7+8 contract enumerates is expressed exactly once in that model, cited to the contract rather than restated anywhere else.
- [ ] No per-kind required-field list remains in procedure expressions, CLI command validation, or the application draft mirror; each delegates to the one boundary, and the rules the engine write path does not run today — intent on directive, class on procedure — are enforced identically on every write surface.
- [ ] CLI writes, engine capture, and base-entry assembly all construct and validate through that boundary.
- [ ] The read path still loads every parseable historical entry and reports structural drift as health data with no new load blocker; translation from the raw parsed form to the domain model yields an absent block plus a finding for a missing or mismatched kind block, never an error.
- [ ] Per-kind read-side structural warnings are produced by running the write model's rules, not by an independent validator.
- [ ] Per-kind round-trip coverage proves a constructed entry serializes and re-parses to an equal raw form.
- [ ] Base entries are composed through a template layer: frontmatter marshalled from the construction model with no hand-written YAML string constants, prose in embedded template files, generated content injected at named placeholders. A table test renders and validates every base entry and fails the build on any invalid one.
- [ ] One indexed overview fact states how the types and kinds play together and how to discriminate the correct one, enrolls under the derived index contract, and references every authoring fact.
- [ ] The call on the overview's reach is made and recorded: enrolled in the shell's opening serve in full if it earns always-on by staying terse under the priming guard, otherwise index-and-teaser stands.
- [ ] Every current kind has one unindexed authoring fact carrying its semantics, what makes it up, how to craft it, and the reasoning a drafter can argue from — not a field checklist alone.
- [ ] Each authoring fact was built positive-side first from named existing sources, audited against the pre-flight rubric for completeness afterwards, and landed only after explicit user review.
- [ ] Each kind's wording is instantiated in at least one named non-software act and retained only where it still discriminates there.
- [ ] Mechanical content renders from the declaration that enforces it: kind-to-type mapping and per-kind field requirements from the construction model, procedure mechanics from the engine spec declarations. A kind or field with no description fails a completeness test, and a missing description renders a loud error rather than blank output.
- [ ] Superseding a type-system fact is refused with a named finding on both the capture and CLI write paths, with those facts recognised by a declared property resolved from the graph rather than a hard-coded ID list.
- [ ] The capture procedure's first step points at the overview fact with a teaser conveying why and when to reach for it, each kind's assembly lane points at that kind's authoring fact under the same teaser discipline, the shell index line does the same, and the hand-carried kind text is gone from that procedure body.
- [ ] The writing guide's prompt renders the overview fact from the graph as the framework floor beneath every judgment.
- [ ] Every existing hand-written copy of kind knowledge is inventoried with its unique claims either mapped into a fact or raised for user ruling before removal; no copy is deleted with claims unaccounted for.
- [ ] Capture constructs, validates and renders every current kind, including annotation with its label-to-member assignments, and a multi-target supersede is expressible through the engine.
- [ ] Assemble diagnostics name only the conditions relevant to the drafted kind, and a genuinely root entry is not forced to invent a reference.
- [ ] Carried instruction units preserve ordered guidance across successful cascades, deduplicated by content hash, without duplicating the current stalled unit; a table test proves start-capture, report kind plus complete draft, arrive at playback in one further call.
- [ ] Default `show` resolves the primary and every relationship node to live supersession heads with an origin-to-head breadcrumb, while exact mode preserves the requested historical primary; `show` renders all structured kinds, and `view` plus catch-up regressions cover counts, filters, topics, participants, and annotation staying out of narrative lanes.
- [ ] No bundled or installed legacy `/sdd` skill prose changes as part of this plan.
- [ ] The banked specimen harness is re-run after the facts and the framework floor land, compared against the recorded baselines, with the result captured.
