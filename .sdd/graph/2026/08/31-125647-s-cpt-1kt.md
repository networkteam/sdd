Where should SDD's UI components live and render: in a surface we host, driven by an agent-owned UI protocol, or inside whatever MCP host the participant already uses, served as MCP Apps?

The demand arises from the SDD assistant UI prototype. Its component vocabulary (entry cards, catch-up views, capture drafts, procedure position) must be built against one of these paths, and its long-term value depends on not being welded to the wrong one.

The two paths:

- **Agent-owned UI protocol** — the researched default: AG-UI was confirmed as the runtime-to-UI protocol (s-tac-zsr), with the UI living in a page we host.
- **MCP Apps** — inverts the ownership: the sdd MCP server serves UI components itself, and they render inside the participant's agent of choice, web or desktop. This extends the delivery insight that SDD should reach participants through the generalist agent they already use (s-cpt-r57) and the aspiration against interface monoculture (d-stg-x0l); we do not expect people to work in the assistant UI exclusively.

The two paths are not necessarily exclusive. A component vocabulary designed host-neutrally might serve both, which would turn the choice into sequencing rather than either/or; that is a candidate answer, unsettled.

What could settle it: the prototype's hands-on probes, including an MCP Apps probe alongside the agentic-UI integrations, plus observing how MCP Apps client support matures.
