The served-once memory treats every new connection as a fresh consumer, so an agent whose context survived a reconnect is re-served the entire orientation it still holds — the memory is process-local, keyed to the live connection, and not reconstructable from the session log.

The everyday shape of the case: exit the agent session and resume it (Claude Code's --continue), which stops the stdio-served MCP server process and starts a fresh one on resume — the agent's conversation context survives in full while the server's memory begins empty. Observed in exactly that shape in this session, in the source and in the field. Source: the served-block memory is an in-memory map on the MCP server keyed by the live connection object, dropped whenever a connection closes; the session log records that a step was served, never the rendered bytes or their hashes, so no replay can rebuild what a consumer received. Field: the session was exited and resumed mid-dialogue (to swap the server binary), and the reattach re-served the full orientation the agent demonstrably still held — minutes after slice one of the capture-efficiency plan (20260826-120330-d-tac-8f8) had eliminated exactly this class of repetition within a connection.

Expected: the plan's own principle — the engine never serves what a connection already holds — is about the consumer's context, for which the connection merely stands in. The connection-keying decision states its assumption directly: keyed to the connection so a same-connection resume never re-pays orientation while a fresh consumer always gets full text (20260705-010751-d-tac-dbk). A reconnecting consumer that kept its context is neither of those cases.

The deviation is the reconnect direction: a same-context reconnect is treated as fresh and re-pays the whole orientation. The opposite direction of the same proxy — context lost inside one live connection — is already resolved: the shipped reorientation escape (fullReplay) covers it. The reconnect direction has no counterpart to that escape.

Recorded as reasoning rather than findings, two candidates from the dialogue that compose: persist the served-record — the lane hashes — in the session log so it survives the process and the connection; and take a declaration at the attach seam, because only the agent knows whether its context survived — continuity keeps the stubs, freshness (or today's fullReplay) forces the full re-serve. Session-durable memory alone would strand a handover — a different agent, told the session handle, attaching with none of the prior conversation's context — by stubbing content that agent never saw, silently.
