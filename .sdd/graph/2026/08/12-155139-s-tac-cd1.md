The capture procedure's `supersedes` param is now declared `list<entry-id>`, so a confirmed supersede edge lands on the written entry instead of being silently discarded — delivered in commit `45b7d117` with an end-to-end regression test that fails before the change and passes after, per the standing contract for code-path fixes (20260416-141340-d-prc-8vh).

**Why this closes the gap.** The defect was a disagreement between two independent statements of one shape: the procedure declared the param as a single entry ID while the engine's write path read it through a list-only store helper that returned nothing for a bare string and reported no error. Declaring the param as a list makes the two agree. The regression test drives the real procedure end to end — start with the param, report, playback confirm, pre-flight, write, summary verify — and asserts both that playback renders each target and that the persisted entry carries the edge. Playback is asserted alongside persistence because that was the gap's whole character: the display was correct and the write was not, so a test checking only the written entry would leave the more dangerous half uncovered.

**The change lands in the procedure entry itself** (20260703-094500-d-prc-cap): the param declaration, plus the two templates that rendered the scalar and now range over the list exactly as `closes` already did.

**A second consumer was repaired by the same change.** The writing guide reads `supersedes` through that same helper, so it was shown no closure edge and reported the supersession as unanchored. It now sees param-supplied supersede targets, completing on the param path what was already delivered for closure edges reported at assemble (20260811-190704-s-tac-r7h).

**What this delivers early, and what it deliberately does not.** A list-typed param also makes a multi-target supersede expressible through the engine, which is an acceptance criterion of the active construction-model plan (20260812-134549-d-tac-9be); that criterion is now satisfied and test-covered rather than waiting on the plan. The arity gap behind it (20260731-083311-s-tac-4vx) is therefore only half answered and stays open: what it left unsettled is whether retiring two lineages with one entry deserves a deliberate playback shape that names each predecessor and what it contributes, rather than a longer list the user must read carefully — and the playback shipped here renders precisely that longer list. The lifecycle-field family's request that arity and declaration be repaired together rather than patched twice is met (20260810-140618-s-cpt-g7u).

**A scalar now fails loudly.** The param rejects a bare string with a named error rather than accepting it and discarding the value. Nothing seeds it programmatically: no procedure spec and no engine code passes `supersedes` at start, and the remaining mentions across the shipped procedures and the legacy skill are descriptive text or the CLI flag, which has always taken a comma-separated list. Any caller that did pass a scalar would now meet a rejection instead of silence, which is the intended trade.
