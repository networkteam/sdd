A dialogue's identity is its handle, a handle is a capability that is issued and never published, and the transport connection carries bytes and nothing else. That is the shape; everything below follows from it.

The transport holds no state about a dialogue. The connection-to-session map is deleted. Every stateful call carries its session handle, nothing is derived from which connection a call arrived on, and no connection event acts on a session: the leave rule goes with the map, so the disconnect that auto-concluded a quiescent session (20260828-164140-s-tac-mss) has no trigger left, and ending a session becomes a participant act only.

Handles are issued, never published. A handle reaches a caller in exactly three ways: `start_session` mints one for the caller that asked, `start_procedure` returns instance handles and the forked child session handle of a dispatched task, or a person hands one over. `list_sessions` is removed from the MCP surface, and the session shell stops naming other open dialogues, including the count it serves today.

A handle authorizes continuing one dialogue, and that is all it authorizes; it composes with authentication rather than replacing it. Hosted, the transport authenticates the principal, sessions are scoped to that principal, and a work call presents its handle within that scope; the handle alone never suffices. Locally the OS user is that scope already, so possession is the whole remaining check: the `userWords` and `takeover` arguments go, and `resume_session` shrinks to one ungated job, re-serving the current position of the session whose handle the caller presents. Either way unguessability is a premise: a handle must carry enough randomness that possession implies issuance.

Listing lives where a principal exists. The MCP surface has no notion of who is asking, which is why its listing degenerated into publishing every handle to everything on the connection. The `sdd` CLI and the authenticated UI do know who is asking, so listing sessions and tearing down stale ones belong there. Neither surface exists yet; this directive commits to the CLI listing as part of the work, since without it a lost handle has no recovery at all, and leaves its concrete plan to a follow-up.

The reasoning that produced this shape matters as much as the shape. Three earlier proposals in the same dialogue tried to defend the boundary by checking the action: widening the binding rule by one case, requiring an explicit handle, then requiring the user's words on every attach. Each failed for one reason. Checking an action requires knowing which caller is acting, and the MCP surface has nothing to know them by: a tool call is a method and params with no indication of its sender, and a dispatched sub-agent's calls arrive on the parent's connection. Gating issuance requires nothing of the sort. A capability that was never handed out cannot be misused by a caller you cannot identify.

Consent in particular cannot serve here, and the third proposal proved it by breaking the delegation model: requiring the user's words on every attach would have made a forked child session unusable by the delegate it exists for, because a delegate has no user to speak for it. Consent is a user-facing act and delegation happens where no user is present.

The map had to go whole rather than lose one use. It knows one fact, which client process a call came from, and was answering four questions: which dialogue this is, whether this caller may be here, whether this consumer has already been served a block, and when a dialogue ends. A connection identifies a client process and never a conversation, and the two have come apart three ways: sub-agents share one connection, `--continue` gives one conversation a new connection, and remote transports re-mint connections on their own.

That a person copies a handle out of an authenticated listing is a stronger gate than `userWords` ever was, and the difference is what it rests on. `userWords` is the agent's claim about what the user said. A copied handle is the user's own act in a surface that authenticated them, so the design no longer depends on agents acting in good faith. The flow that pays this extra step is rare by observation: continuing a dialogue in a second agent when the first is unavailable. Everyday recovery keeps working, because the conversation itself carries the handle.

For delegation this closes every engine-side route the delegate-session directive could only mitigate (20260827-232430-d-cpt-voa). A delegate holds the child handle it was dispatched with, and no call on the surface publishes another, which removes the remaining recorded route in the isolation gap (20260826-225922-s-cpt-pxq). What the engine cannot close is the host: a delegation mechanism that copies the parent conversation copies the parent handle with it. That seam sits above the guest-surface enforcement ceiling (20260629-204630-s-cpt-1dz), and keeping the parent handle out of a delegate's context stays with the dispatch side. The rest of that directive stands entire and its follow-up work is unchanged: the fork on task-class dispatch, the non-interactive child session, the result returning as a transition into the dispatching instance, and the read set staying with the agent that read. Only the exposure it accepted is removed here.

Served-once deduplication is re-keyed rather than lost. It keys on the session handle and derives what a consumer has seen from the session ledger, with the reorientation call as the consumer boundary: an agent presenting a handle and asking for its position is declaring it needs re-serving, so the derived set resets there and accumulates after. This requires the ledger to record what was served, which it does not today, and is the candidate the served-once reconnect gap already named (20260826-173028-s-tac-1qr); it also answers that gap's stranding concern from the other side, since an agent handed a handle with no prior context reorients and receives full text rather than silent stubs.

Two consequences are accepted rather than solved. An agent that loses its handle cannot rediscover it and must ask the user, which is not a stdio-only cost: a Streamable HTTP deployment re-mints connections and a stateless one treats each request independently, so connection-derived recovery is unavailable there in any case. And cleanup loses its event trigger; staleness is instead derived from what the store already records for each session, which client last attached and when, together with elapsed time.

This supersedes the predecessor that removed only the no-argument branch of `resume_session` (20260827-235350-d-tac-d15). That entry deleted one use of the map and left the map, the consent exemption and the listing standing, so the same substitution stayed available elsewhere; the dialogue that followed established the construct as the defect rather than any one of its uses. It builds on the session-model contract, whose first invariant already held that a dialogue's identity is its durable handle and never a transport connection (20260718-131626-d-cpt-9of), and retires two of that contract's invariants for the MCP surface: structural consent (I5), whose machinery guarded a boundary that unpublished handles remove, and free discovery (I4), re-scoped to surfaces that know a principal.
