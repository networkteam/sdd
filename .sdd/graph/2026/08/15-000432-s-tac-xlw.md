Triaging the full open-gap set against the engine-primacy commitment shows that "recommend the engine" and "retire the skills" are two releases with different blocker sets, and that separating them turns an unshippable list into a short one.

**Why the question was asked.** The engine-primacy directive (20260715-175731-d-cpt-p3k) committed two things in one breath — the engine as SDD's main working mode, and the /sdd flow to deprecation — while explicitly leaving the mechanics unsettled: what retires when, what remains as a pointer skill, how installed renders and `sdd init` behave, and what existing users are told. The next release after the first prerelease (20260811-101227-s-prc-2hj) is the one that would carry the message "work in the engine now", and nothing recorded answered what stands in its way. The graph holds roughly a hundred open gaps in no severity order; the assessment had to be made rather than looked up.

**The split is the finding.** Recommending the engine while the skills stay installed, and actually retiring the skills, are gated by disjoint work. The second waits on the bootstrap parity verdict (20260726-195300-d-tac-fim), which waits in turn on the kind-knowledge work still in flight, and on the standing bootstrap-deprecation blocker (20260716-144333-s-prc-7ku). Read as one release the list is long enough to look indefinite. Read as two, the first is short — four repairs and one decision, none of them opening a dependency or a surface the project does not already own — and the second keeps its real gate instead of borrowing the first's.

**What severity means once the engine is primary.** The governing question stops being how bad a gap looks and becomes whether a fallback exists. Several gaps read as minor today only because every graph is local and the CLI is one shell away: an engine capability the procedure cannot express is a detour here and an absolute stop for a hosted user. The same reframing promotes an ordinary annoyance into the release's largest cluster — values confirmed by the user and then dropped on the way into the entry, with no error raised anywhere. That is survivable while capture is one write path among several, and unavoidable once it is the only way anything reaches the graph. The class already has a directive committed against it (20260812-160448-d-tac-ymk), which ends it from the entry side by making every field arrive through a declared binding; what the release needs is narrower than that design — make the drops loud, and every member becomes a visible error instead of a lost value.

**The smallest blocker is the most consequential.** Search returns matching entries with no indication of what matched in them: the CLI substitutes a default of three cited snippets per entry when the flag is unset, while the agent-facing surface passes the omission straight through as a zero and suppresses snippets entirely (20260814-160042-s-tac-rst), confirmed in the code during this pass. An agent therefore sees which entries came back but never why, which reads as a near-miss when it is a true hit. Engine-first makes that the surface every agent grounds through, so a correction confined to one default value at the query boundary lands directly on the discipline the rest of the framework assumes.

**The retirement release carries a blocker invisible from the engine side.** `sdd init` does not prune installed skill files whose bundle source was removed (20260507-174656-s-tac-zaz) — filed in May, tagged as init ergonomics, nothing about it reading as engine work. Dropping the skill renders would leave every existing user with stale installed copies and reproduce precisely the dual-flow ambiguity that motivated the deprecation call. A triage scoped to engine gaps would not have surfaced it; the two-release framing is what put it in view.
