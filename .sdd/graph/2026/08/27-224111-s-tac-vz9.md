A multi-step procedure's report schema re-serves in full at every gate step because the per-step required list changes the canonical bytes the schema stub keys on, so the largest static payload of such procedures escapes the shipped dedup entirely. Observed in this session's implementation run: the anchor, contract, baseTarget, workTarget, and record steps each arrived with the complete schema — the same invariant properties block — while the stub fired only where a serve repeated byte-identically (the work junction re-serving itself). Verified in the source: the stub is keyed on the canonical JSON of the whole served schema, and the per-step schema varies only in its required list while the properties block stays invariant across steps.

Expected per the capture-efficiency plan's governing principle — the engine never serves what this connection already holds (20260826-120330-d-tac-8f8) — and its schema criterion as delivered in slice one: a schema this connection already received arrives as a stub (20260826-172134-s-tac-3yc). The delivered criterion holds to the letter, since the bytes genuinely differ per step; the deviation is that the intent misses for every multi-step gate procedure, where the invariant bulk re-pays its cost at each step for the sake of a one-line difference.

Recorded as reasoning, not a commitment — one candidate from the observation: split the serve — dedup the invariant properties block on its own bytes, and always serve the small varying part (required, and the chooser answer envelope where a step has one) inline.
