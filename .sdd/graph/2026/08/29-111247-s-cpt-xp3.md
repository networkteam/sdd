The engine's non-mutating path does not distinguish a transient failure from a wrong input, so an agent that cannot tell which it hit regenerates work the engine still holds. Observed when the writing guide's response failed to parse as JSON (20260827-224853-s-tac-giv): the agent resent its complete drafted report after each of three failures, although the engine had stored those fields before the guide ran and one small field would have re-run it. The error named the failed command and its step. Nothing in it said whether the input was at fault, whether anything survived, or whether trying again unchanged would help. A second mode turns the same absence from wasteful into blocking: on a connection lost in a tunnel, retrying inside the call leaves the agent unable to say anything to the user for as long as the outage lasts, while returning a bare error invites the same regeneration as before.

The same question already has an answer on the path that writes an entry. The delivery directive (20260730-171311-d-cpt-0cv) settles it there: a transient failure is a diagnostic attached to a pending state rather than a state of its own, retry never replays dialogue or LLM work, and where automatic retry is unsafe the failure returns carrying what a retry needs, so the caller's next move is informed rather than blind. None of that reaches the operations and served queries that run before the write, which is where the observed loss happened. The capture-efficiency plan carries the agent's half of the same principle, that nothing whole is re-transmitted which changed only in part (20260826-120330-d-tac-8f8), and delivered it for the succeeding path only.

The cost is not recoverable afterwards: context a resend consumes stays consumed for the session (20260825-234504-s-tac-jro), so every unnecessary regeneration shortens the dialogue it belongs to.

Candidate direction, unsettled: classify where the failure is produced rather than where it is reported, handle it once at the point every step's operation already runs, and return a transient failure as a position the agent can advance from rather than an error it must interpret. One risk belongs with it. A permanent defect can present as transient, as the guide's prompt did by sometimes succeeding on a resend, so a retried failure that leaves no trace converts a reportable bug into an unexplained slowdown.
