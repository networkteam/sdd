The SDD assistant UI ships as a first prototype: a web surface where the SDD dialogue itself lives, the third surface beside the CLI and engine-driven coding agents, connected to a locally served sdd over the engine's MCP HTTP transport. The experience it demonstrates is a personal project assistant for a less technical person: formatted dialogue, agent-composed views, every entry reference hoverable, a non-technical but graph-grounded picture of the project, and a conversation that takes in new information and works out how the graph must change to reflect it. This realizes the web UI direction (d-stg-6za) for the non-developer audience (d-stg-x0l), and retires that direction's "sandbox" wording in favor of "the SDD assistant UI"; the dialogue-first aspiration (d-stg-beb) is what the surface makes visible.

Shape and stance: the prototype lives in this repository as another surface, without commitment to keep it. Rough edges are accepted while iterating, and the framework itself may change with what the build teaches. The premise that a thin TypeScript agent over engine MCP no longer contradicts the Go runtime verdict is recorded separately (s-cpt-2an).

Stack: the agent layer starts on Vercel's AI SDK as the thin-relay backbone. Mastra is deliberately demoted to a fallback if the agent layer grows real needs (memory, orchestration): it sits on AI SDK's model layer, and its June edge was agent scaffolding around an agent that carried SDD's semantics itself (s-tac-i6m), which the engine now serves. The UI layer is not chosen from docs: the first phase builds feel-spikes of the documented agentic-UI integrations (AI SDK UI, assistant-ui, CopilotKit, OpenUI) against one shared simple case, plus an MCP Apps probe whose findings feed the open rendering-path question (s-cpt-1kt).

Demo scenarios, the experience bar:

- a flexible catch-up where the agent picks the components and views that serve the asked question;
- formatted dialogue with hoverable entry references (entry cards);
- a non-technical view of which procedure and step the session stands in;
- capture with a rendered overview of the intended entry constellation before per-entry detail, the render side of the committed distill/slicing route (d-prc-j3h).

A debug mode is the natural extension, not the foreground: inspection depth for participants willing to dive, and visual observability for developing sdd itself. Inside this surface it partially answers the companion read-surface gap (s-cpt-53q).

Held as find-out questions, deliberately not pre-decided: how agent-composed reusable components work in practice (a fixed vocabulary the agent composes per conversation, short of fully generated UI); and where the line runs between agent-mediated personalized representation and direct interactive data access, where the agent pre-configures a view and the user filters and searches without an agent round-trip. The mechanical path risks rebuilding a raw-data project-management tool against dialogue-first (d-stg-beb).

Deliberately not committed here: the final UX and UI direction (the prototype exists to inform it); the hosted SDD surface (a separate story, the prototype connects locally); capturing the component model up front (it is recorded as findings once built).

## Acceptance criteria

- [ ] A person can drive a real SDD session end to end in the assistant UI against a locally served sdd over MCP HTTP, with the engine's full MCP surface reachable through the agent.
- [ ] Feel-spikes of the four agentic-UI integrations exist against one shared simple case, and the picked direction is recorded with the comparison that decided it.
- [ ] An MCP Apps probe ran, with findings recorded toward the rendering-path question (s-cpt-1kt).
- [ ] The four demo scenarios work end to end in the prototype.
- [ ] Findings on the two find-out questions (component composition; representation vs direct data access) are recorded in the graph.
