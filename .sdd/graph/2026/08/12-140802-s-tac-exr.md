A supersede edge the user confirmed at playback was never written to the entry: the capture procedure declares `supersedes` as a scalar param while the engine's write path reads it with a list-only helper, so the field is silently discarded and both entries stay active.

**Target.** The capture procedure makes playback the verification contract — the user checks the exact entry against its labelled fields, and confirm writes that entry — and supersede captures are not a separate move but that same spine entered through the `supersedes` param (20260703-094500-d-prc-cap). A confirmed supersede therefore lands on the written entry.

**Actual.** Capturing 20260812-134549-d-tac-9be, the capture was started with `supersedes` naming the plan it replaces, the playback rendered that line among the fields, the user confirmed, and the written entry carried no `supersedes` key at all. Both plans derived as active — the exact duplication that entry says it prevents — until the edge was restored by hand.

**Mechanism, in outline.** The capture spec declares `supersedes` as a single entry-id while `closes` is a list. Both the write draft and the writing-guide draft read the value through the workflow registry's string-list helper, which returns nothing for a value that is not a list. So the edge reaches neither: the write omits it, and the guide, shown no closure edges, correctly reported the supersession as unanchored — a finding the drafting agent dismissed as an artifact of what the guide had been shown. That is the same plumbing already repaired for fields reported at assemble (20260811-190704-s-tac-r7h), leaving the param path as the half still failing. The playback template reads the scalar directly and displayed it, which is why nothing looked wrong.

**Why it matters beyond this instance.** In a graph with more than one participant this is severe. A confirmed supersede that never lands leaves the derived state wrong for everyone else — the retired entry still reads active, still ranks, still presents as live work — and nothing prompts anyone to notice, because the only surface that would have shown the absence is the playback that displayed it correctly. A participant who does not own the entry files cannot repair one by hand either.

**What was done, and why it is not precedent.** The edge was restored by editing the written entry's frontmatter directly and committing it as a mechanical fix. That was a workaround to skip a re-capture, affordable only because this graph currently has effectively a single participant, and it should not be read as a sanctioned way to materialize an approved write — the repair path in any shared setting is a captured entry, not an edited file.

**Left for a dedicated session.** Whether earlier engine-path supersede captures lost their edges the same way, and which repair to take — widening the reader, moving the declaration, or refusing a confirm whose fields cannot round-trip to the write. `closes` is list-typed and unaffected. The repair's home is already committed rather than open: the construction-model boundary of the plan whose capture surfaced this (20260812-134549-d-tac-9be), which carries expressing a multi-target supersede through the engine as an acceptance criterion and therefore rewrites this exact declaration and reader.

**Where it sits.** This is a third shape in the lifecycle-field family, alongside the two that entry splits (20260810-140618-s-cpt-g7u): beyond the reach of authoring discipline — the author declared the edge through the procedure's own param and the user confirmed it — but not beyond mechanical reach. Dropping the field left the retired entry's full ID in the body with no edge behind it, which is that family's catchable shape, and the edge-presence enforcement it records as never built runs over the assembled entry at the write gate, after the param was already lost. This instance is therefore fresh evidence for building that check rather than a case against it. The declaration is the same under-powered one as the single-valued param gap, which already named that construction boundary as its fix's home (20260731-083311-s-tac-4vx), and the family asks for arity and declaration to be treated together rather than patched twice; the silence is the report boundary's, one boundary further on (20260811-233331-s-tac-bjn).
