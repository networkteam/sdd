The attachment-link check now reads past code, and the one historical entry it warned on was reformatted so its warnings clear. Commit `52c6783` moves the check into `internal/model/attachmentlinks.go` and runs it over a masked copy of the body, with fenced blocks, indented code blocks and inline code spans blanked and newlines kept so offsets still line up. Both prefix forms pass through the same mask. Tests came first: `internal/model/attachmentlinks_test.go` exercises the read side through `ValidateEntry` and the write side through `ValidateForWrite` in both directions, and ten of its cases failed before the change.

Masking is deliberately generous, because the two surfaces fail differently. A missed warning on the read side is recoverable. A wrong finding at the write gate blocks unconditionally, since the user override reaches pre-flight judgment only and nothing but deterministic validation survives confirmation (20260810-141555-d-cpt-20r). So an ambiguous region is skipped rather than reported. The mask is written by hand rather than built on the `golang-commonmark` parser already in the tree, because the check needs byte offsets into the original body that the tokenizer does not expose for inline spans, and because `internal/model` carries no dependencies.

The fix alone did not clear the standing warnings. The brief for this run held that both matches in 20260409-113337-d-tac-04t sat in inline code. Reading the bytes showed one in bare prose and the other indented two spaces where CommonMark requires four, so neither was code by any rule a parser would apply. Christopher judged permanent warnings on that entry unacceptable and authorized editing it, on the ground that adding markdown syntax does not change meaning. Commit `934bb15` wraps the syntax tokens in backticks and fences the two literal listings, leaving every word intact. The authorization was given for this entry after inspecting its exact text, and reaches no further.

`sdd lint` reports no issues against the live graph after a rebuild. The running `sdd serve` process still reports the two warnings because it predates that build, and clears on restart.

Noticed while working and left open: nothing on the engine path documents the authorable placeholder form, and the one place it is written down goes away at v0.18.0 (20260821-123832-d-tac-ip1). It needs its own gap signal, which carries the evidence.
