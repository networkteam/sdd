Strict config parsing makes any newly introduced config key fatal to every older sdd binary that shares the file: all config locations are decoded with unknown-key rejection (`StrictUnmarshalYAML`, deliberately shared "so every config location shares one definition of strictness"), so the first time a newer binary writes a key an older binary does not know, the older binary stops working entirely. Observed live while proving the session-subsystem rebuild's binary-swap coexistence criterion (20260730-093011-d-tac-k4q): after the rebuilt binary wrote `sessions.retention` to the user-global config, the previous release's `sdd serve` exited at startup with `field sessions not found in type repos.GlobalConfig`. One legitimate new key bricked the older binary — drop-in version coexistence, which the rebuild just established for the session-log layer, is violated at the config layer, and the current binary carries the identical failure forward to the next key any future version adds.

The trade-off is two standing principles colliding. Strictness protects hand-edited configs against typos by failing loud; tolerance is what lets two binary versions share one machine. The store already resolved this collision once: the outer validation of the relocation slice (20260726-203237-s-tac-jit) found strict `DisallowUnknownFields` session decoding aborting on old logs and judged the strictness itself the defect — defensive machinery generated by review and then verified as sound. The config surface is the same failure class one layer over, with the direction of skew reversed: there a newer binary rejected older data; here an older binary rejects newer data, which no retirement table can ever fix retroactively — only tolerance shipped in advance can.

Agreed direction (Christopher, in dialogue): tolerate unknown config keys at parse, with the loaded config carrying the ignored keys so real surfaces can render them — a slog line is not one, since `sdd serve` runs as an agent's stdio subprocess whose stderr nobody inspects. Concretely: the engine's session-start serve carries a one-time notice naming the keys so the agent can tell the user — deliberately door-only, not the threaded standing-notice pattern the rebuild deleted; interactive TTY commands warn through the existing styled warning surface; and the `sdd config` provenance view names ignored keys per location. `sdd config set` remains the validated entry path, so typo protection lives at the write side where the current binary knows the schema, rather than at every read where it cannot distinguish a typo from the future. The door-serve forwarding must be a decoupled, generic mechanism — a diagnostics channel any subsystem can feed and the door serve renders once — not config-specific plumbing threaded into the door.
