Every automatic serve stays within its budget as the graph grows: content that scales with the graph or session state is cut at per-part caps that name what they dropped and how to pull it, and authored instruction text is never truncated. This supersedes the bounded-serves plan (20260820-165139-d-tac-wlq), keeping its goal and replacing its mechanics, after three findings from the design dialogue changed the shape.

First, named-lane serve composition shipped (20260826-172134-s-tac-3yc), so every step serve already decomposes into the parts a bound attaches to. The short pushed lead the superseded plan wanted is what a serve with capped lanes already is; no separate push+pull restructure remains to build. Second, a code audit of every push surface found the problem wider than three serves: twenty scaling surfaces, seventeen without a working bound. The framing macros (focus, participants, wip) emit no count limit, only one inject query accepts a byte cap, MCP responses carry unbounded line lists (session rejections, open threads, discarded threads, produced values), and store values interpolate into instruction text uncapped. The audit also found the cut mechanics in prototype: the view tool's size guard and the resume projection's per-value caps cut honestly, while the lane byte cap cuts silently. The full inventory with file:line evidence is in [the audit record](./29-173342-d-tac-rzi/serve-size-audit.md). The repair is therefore mechanism-level, not per-spot: macros carry bounds, every inject accepts a cap, one shared honest cut replaces the three existing styles. Third, the whole-serve hard limit is dropped as a runtime mechanism. It could only hold by cutting something, everything legitimately cuttable is already cut at its own cap, and a cut instruction is not a smaller instruction but a broken one. The door gap (20260818-133703-s-tac-ayj) named the principles lane as the case where a cut destroys the content's purpose.

Individually capped parts can still sum past a host budget, which is how catch-up died (20260719-122103-s-tac-jom). That check moves to authoring surfaces as advisory arithmetic: worst-case bytes (template skeleton plus declared caps plus typed slot allowances) against the engine's default serve budget, raised as a pre-flight finding when a procedure entry is captured and as an `sdd lint` finding for specs already in a graph, which also catches hand-edited specs and default changes on engine upgrades. Overshoot is a risk, not a defect: the spec still runs, so spec load never fails on it, and declaring a larger total on the spec silences the finding and records the trade.

Size is the engine's job, not the author's. An unannotated spec is bounded by engine defaults on every scaling part; explicit caps (the existing maxBytes shape) are overrides. Authors declare fields, types, and steps; the engine owns size, the same split the type system uses for value shapes. The default budget is grounded in the verified host floor of roughly 10K tokens per tool output (20260719-122547-s-tac-40d), and default caps are calibrated from measurement, not invented: the first slice measures every automatic serve of the shipped procedures against this repository's own graph, the fix order and defaults fall out of that data, and the measurement stays as the regression test that replaces the fixture-blind door test.

Cut pointers get one grammar addition: a skip modifier composing with the existing limit, so a truncated list's pointer is its own expression plus skip and limit. The pointers lean on the view tool being usable without prior grammar knowledge, so the open view-UX gap (20260717-095714-s-tac-lwi) gates how well they work in practice.

The v0.17.0 target and its reasoning carry over from the superseded plan: the fallback skills still exist in that release (20260820-162456-d-tac-o2v), so the bounded serving model proves itself while a way out remains. This plan commits the bounded-push half of the catch-up restructure insight (20260719-124754-s-cpt-s37); its per-perspective briefing dimension stays open there. Out of scope: explicit pulls (show, view, search, read_attachment), which arrive complete under their own tool-side guards, and serve repetition (dedup, read-ledger joins), a separate axis.

## Acceptance criteria

- [ ] Every serve component that scales with the graph or session state (inject results, framing lanes, interpolated store values, line lists in MCP responses) carries a bound, from engine defaults where the spec declares nothing.
- [ ] The engine never truncates authored instruction text.
- [ ] A bounded entry list cuts only at whole-entry boundaries, and every cut names the dropped count and a ready-to-run pull for the remainder.
- [ ] The view grammar composes a skip modifier with the existing limit, so a cut's pointer can page through what it dropped.
- [ ] Explicit pulls (show, view, search, read_attachment) are not cut by serve bounds.
- [ ] Capturing a procedure whose worst-case size arithmetic exceeds the serve budget raises a pre-flight finding; a larger total declared on the spec silences it.
- [ ] `sdd lint` raises the same budget finding for procedure specs already in the graph.
- [ ] A test measures every automatic serve of the shipped procedures against a realistically populated graph and fails when one exceeds its budget.
- [ ] A live session on a host with a ~10K-token response budget runs opening, catch-up, and engage without a truncated serve.
