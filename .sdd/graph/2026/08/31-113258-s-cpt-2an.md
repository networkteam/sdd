The engine's MCP surface now sits between SDD's semantics and any agent or surface, which narrows the premises of two runtime decisions made before it existed. When the Go runtime verdict (d-cpt-8k5) was captured, an out-of-process agent had to re-implement SDD's process, prompts, tools, and discipline, so eliminating CLI/agent drift argued for in-process Go. The engine dissolved that premise for external agents: procedures, instructions, queries, and graph writes are served over MCP, and `sdd serve` ships the spec-compliant streamable HTTP transport with mandatory bearer-token auth. An external agent can therefore be a thin relay that forwards serves, renders state, and carries the user's words back, holding no SDD semantics of its own. This holds locally for exploration today; the full team experience needs the hosted SDD surface, which fronts the same MCP with real authentication and low setup friction. The verdict keeps holding where its premise binds, an agent that embeds SDD's semantics in its own process. It does not bind a thin relay's stack, where UI-ecosystem reach can dominate the choice. The same shift bounds the engine directive's surface picture (d-cpt-3yw), which planned the hosted webapp as a later in-process adapter over the identical engine; the MCP HTTP transport fills that role out of process, with no adapter to build. It also meets the deferred CLI-parity MCP server's trigger (d-tac-3vz), a non-Go external agent needing structured access, through the engine server that already ships rather than the preserved CLI-parity spec, so nothing new needs building there. None of the three decisions is overturned; each holds inside the boundary this reading draws. Recorded now because the SDD assistant UI prototype reasons from it: a TypeScript thin agent behind a custom UI no longer contradicts the Go verdict.
