Refines Plan 1's topics frontmatter shape away from the polymorphic two-shapes-one-key design (`topics: [{label, members}]` on annotation, `topics: [string]` everywhere else) toward a unified shape where the YAML key carries one concept consistently and the `kind: annotation` entry type is forward-extensible to other annotation forms beyond topics.

## Unified shape

**Inline `topics:` on any non-annotation entry — always a list of strings:**

```yaml
topics: [catch-up-scaling, infrastructure/cli]
```

Meaning: "this entry belongs to these topics."

**Annotation entries — `refs:` carries the entries the annotation is about (existing universal edge field, no new concept), `topics:` carries topic assignments:**

```yaml
type: signal
kind: annotation
refs: [a, b, c, d]
topics:
  - catch-up-scaling                         # string form: applies to all refs
  - label: type-system/kinds                 # object form: applies to a sub-selection
    members: [a, b]                          #              members ⊆ refs
```

Items in the annotation's `topics:` list support two forms:
- Plain string → topic label, applied to *all* of the annotation's `refs:`
- `{label, members?}` object → topic label with explicit member sub-selection. `members` must be a subset of `refs:`.

The default and most common case (one topic across all members) is the one-line string form.

## Annotation kind generalization

The `kind: annotation` decision is reframed as **structural metadata layered onto referenced entries**, with `topics:` as one annotation form. The kind itself is not topics-exclusive. Future annotation forms (e.g. severity tagging, dependency-type tagging) can add their own frontmatter fields alongside `topics:` without requiring a new kind. The narrative-exclusion-from-catch-up rule remains: annotation entries are structural, not observational.

## Why this resolves the original friction

The polymorphic shape (`topics:` carrying string list on most kinds vs. object list on annotation) created two YAML shapes for one key. The unified design:

- **One YAML concept per use site.** Annotation has `topics:` + `refs:` (no new edge field); other kinds have inline `topics:` strings. The `members:` field disappears as a kind-specific edge — `refs:` already carries the annotation-to-member relationship.
- **Polymorphism is contained.** Within the `topics:` list on annotation entries only, items can be string-or-object — a compact way to express "this topic gets all refs" or "this topic gets a sub-selection." No node-shape dispatch outside that list.
- **Annotation membership flows through the existing refs index.** An entry's effective topics = its inline `topics:` ∪ topics declared by annotations whose refs (or members sub-selection) include this entry. Reuses `g.RefsTo` directly.
- **Forward-extensibility.** Adding a new annotation form later is "add a frontmatter field on annotation kind" — no kind proliferation, no schema migration.

## Acceptance-criteria refinements applied to d-tac-gvn

- The AC reading "frontmatter validates `topics: [{label, members}]` shape" is reinterpreted as: annotation `topics:` items validate as either (a) string topic-label or (b) object with `label:` (required) and `members:` (optional, subset of `refs:`).
- The AC reading "Inline `topics: [<label>, ...]` valid on any entry kind's frontmatter" stands unchanged but with the explicit clarification that inline form is strings-only (no objects).
- Annotation refs gain semantic interpretation: in addition to general "builds on" edge meaning, on `kind: annotation` entries, refs are the canonical member set for any topic in the entry's `topics:` list that does not specify its own `members:`.
