Adds per-ref kind qualifiers to refs: entries with a backwards-compatible YAML schema for reading, closing the ref-metadata gap (s-cpt-k7z) and laying the structural foundation for label-aware consumers like the heat-algorithm fix (s-cpt-zsd). Reads accept both bare-string IDs (legacy entries; parsed as kind: unknown) and object form ({id, kind, desc?}); writes always produce object form with an explicit kind. closes and supersedes stay as plain strings — they carry uniform mechanical meaning already.

The kind field picks from a closed vocabulary of seven values:

- **grounds** — anchors to standing structure (contract, aspiration, standing directive)
- **builds-on** — extends prior lineage
- **addresses** — responds to a gap, question, or signal
- **surfaces** — created or discovered the referenced gap during this work
- **evidence** — empirical observation supporting the claim
- **depends-on** — functional prerequisite
- **related** — parallel sibling, no other axis fits

`unknown` is a parse-time fallback for legacy bare-string refs, not a valid new-capture choice. The set was derived empirically against a 33-ref sample drawn from 11 mixed source entries (strategic and tactical, decisions and signals across kinds). See attached design for the sample, label distribution, edge cases, and the kind-vs-label vocabulary decision (kind matches the existing closed-set-discriminator pattern; label stays reserved for topic paths).

**Pre-flight has two layers.** Mechanical check (high severity, blocking): every refs item on a new entry must have a kind from the closed set — bare-string capture rejected, missing kind rejected, invalid kind rejected, `unknown` rejected at capture. LLM check (medium severity, advisory): when a ref carries `desc`, the desc must be consistent with how the entry description characterizes the relationship — contradictions flagged for revision with the ref ID and relevant body excerpt.

**Backwards / forward compatibility.** Reads remain compatible with all existing entries: legacy bare-string refs continue to parse, mapped to kind: unknown for traversal purposes. Writes are not forward-compatible — older SDD binaries cannot parse object-form refs in new entries. Mitigation given small user base: ship binary and skill upgrades together; document the upgrade requirement in cli-reference.md. No auto-backfill of historical entries — old refs stay as kind: unknown forever unless their parent entries are superseded.

**CLI surface.** Single repeatable `--refs` flag, JSON per call: `--refs '{"id":"...","kind":"builds-on","desc":"..."}'`. The old CSV form (`--refs id1,id2`) is dropped — it would always fail mechanical pre-flight under the new rule. Symmetric with the existing `--topic` and `--involvement` patterns.

**Out of scope** (deferred to follow-ups). Label-aware heat weighting (the s-cpt-zsd resolution — needs comparative findings like d-tac-uww produced). Filter primitives keyed on kind. Search-ranking changes. Retroactive labeling tooling. Compact-form CLI sugar for ergonomics (could be added if JSON-per-ref becomes friction).

**CQRS decomposition per d-cpt-ah1**: schema and parser in `internal/model`, frontmatter writer in `internal/model`, mechanical pre-flight check at the validation seam, LLM consistency check in the pre-flight prompt within `internal/llm`, render updates in `internal/presenters` and the skill docs, thin CLI shell in `cmd/sdd`.

See [design discussion](./17-175045-d-tac-cs0/design.md) for the full dialogue arc, 33-ref labeled sample, edge cases (parallel siblings, forward-discovery), the kind-vs-label decision, and consumer-deferral rationale.

## Acceptance criteria

- [ ] Model: `Ref` type with `ID`, `Kind`, `Desc` fields; refs frontmatter unmarshals both bare-string and object forms (bare string → kind: unknown)
- [ ] Model: object form requires `kind` field; missing or empty kind rejected at parse time
- [ ] Model: `Kind` validated against closed set {grounds, builds-on, addresses, surfaces, evidence, depends-on, related, unknown}; values outside the set rejected
- [ ] Model: `closes` and `supersedes` remain `[]string`; object form on these fields rejected with a clear error
- [ ] Frontmatter writer: always writes object form with explicit kind for new entries; never emits bare-string output on capture
- [ ] CLI: `--refs` is repeatable; each value is JSON `{"id":"...","kind":"...","desc":"..."}`; `desc` is optional
- [ ] CLI: bare-string `--refs id1,id2` rejected with a clear error message directing to the new JSON form
- [ ] Mechanical pre-flight (high severity, blocking): new entries with refs whose kind is missing, empty, `unknown`, or outside the closed set are rejected
- [ ] LLM pre-flight (medium severity, advisory): when a ref carries `desc`, the description body must be consistent with the ref's characterization — contradiction flagged with ref ID and relevant body excerpt; skipped when `desc` is absent
- [ ] `sdd show` renders `kind` per ref line in metadata block and upstream/downstream summaries; `desc` (when present) renders inline beneath the ref line
- [ ] `sdd lint` validates `kind` values against the closed set; reports invalid values as findings
- [ ] `cli-reference.md` updated with refs object-form schema, kind vocabulary table, `--refs` JSON form, dropped-CSV-form note, and the binary+skill-upgrade-together rule
- [ ] `/sdd` SKILL.md updated with kind-selection guidance during capture playback (which kind for which relationship intent) and the new `--refs` JSON pattern
- [ ] Unit tests cover: bare-string parse (legacy), object-form parse, missing-kind rejection, invalid-kind rejection, closes/supersedes object-form rejection, mechanical pre-flight rejection, LLM-check fixture (matched + mismatched cases)
- [ ] Smoke test: capture an entry with object-form refs (mix of kinds, at least one with `desc`); verify pre-flight passes; verify `sdd show` renders kind and desc correctly
