Requests Christopher's confirmation to adopt the following as a binding contract: that the decision graph must stay conflict-free, and that conflict-prone tooling must be kept separate from it. The principle was established by Christopher in an in-person discussion and is recorded and proposed here by Jonathan; this open question is a directed request for his confirmation or refinement before it becomes a contract.

**Proposed contract.** Because the decision graph is append-only and entries are immutable — one new file per entry, never edited in place (d-cpt-e1i) — well-formed graph changes can never produce a git merge conflict. This would be binding, with two consequences. First, a git-level (mechanical) conflict on a graph file must never arise from well-formed use; if one does, it is always a signal that the tooling is broken (a race, a bad merge, corruption), and it must be captured as a signal and tracked, never silently resolved. (Semantic conflicts between entries — two incompatible decisions — are a distinct concern and out of scope here.) Second, mutable conflict-prone tooling — installed skills, the CLI binary version, generated artifacts — must be kept separate from the graph (a separate branch or repository) so it cannot contaminate the graph's conflict-free space. This reframes the sync conflict-prediction machinery (d-tac-hsu) as guarding the tooling boundary, not the graph itself. The version-clobber gap (s-tac-ddi) is the concrete graph-recorded evidence motivating the tooling-separation rule.

**Requested of Christopher:** confirm and capture it as a contract (closing this question), refine the wording or confidence, or decline.
