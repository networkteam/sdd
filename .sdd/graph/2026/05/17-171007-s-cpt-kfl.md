`sdd view` carries refs as inline text in summary lines without surfacing their derived status, so list consumers (catch-up, ranked roll-ups, any view) see point-in-time summary text but not whether referenced entries are still active, closed, or superseded. This caused a temporal blur in `/sdd-catchup` evaluation where the agent rendered "engage refactor pending" against `d-prc-iqw` whose ref `d-prc-kyz` had since closed via `s-prc-st0` — the agent had no signal of the state change. `sdd show --downstream` already has the mechanism (walks refs, emits `{status: ...}` on each), but it's chain-shaped (one anchor, depth-limited), not list-shaped.

Proposes a new `sdd view` transform — `refs(...)` or similar — that per entry in a list emits outgoing refs as indented sub-lines with derived status, defaulting to interesting state changes (closed-by, superseded-by) to keep catch-up output lean. This is a sibling failure mode to summary-body drift (`s-cpt-tdp`): there, the stored summary diverges from the body's truth at generation time; here, the stored summary diverges from referenced entries' current state as the graph moves. A refs transform doesn't fix stored-summary drift, but lets ref-state drift be surfaced by rendering rather than waiting for re-summarization.

Design dimensions (default filter, depth, direction, line shape, grammar) need dialogue before plan capture — see [design idea](./17-171007-s-cpt-kfl/design.md). Complementary to but distinct from per-ref "why" annotations (`s-cpt-k7z`, stored at capture time) and the heat-algorithm refinement (`s-cpt-zsd`) those would enable.
