`sdd init` doesn't auto-prune installed skill files when their bundle source has been removed, leaving installed orphans that drift from the bundle until cleaned manually. Surfaced during the engage refactor implementation: after deleting `internal/bundledskills/claude/sdd/references/playbook-explore.md` from the bundle, `sdd init` reinstalled and re-stamped the unaffected files but left `.claude/skills/sdd/references/playbook-explore.md` in place — the orphan had to be removed by hand before the working tree was clean. This pattern will recur for any future skill-file removal (renames, splits, retirements).

**Resolution idea**: `sdd init` could delete an installed file when (a) it has no matching bundle source AND (b) its current content hash matches the last `sdd-content-hash` stamp in the file's frontmatter — i.e., the user/operator hasn't modified the installed copy since the last stamp. Modified orphans should stay in place with a warning so user edits aren't silently discarded. The hash check provides the safety property: only auto-installed files that nobody touched get auto-removed; anything edited (deliberately or accidentally) is preserved until the user resolves it.

Refs the engage refactor's closing done signal (s-prc-st0), which noted this as deviation #3.
