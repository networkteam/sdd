Examine how popular Claude Code skill bundles structure modular content and — most importantly — how they handle **routing**: getting the agent to invoke the right module / sub-skill / playbook move at the right time. Goal: ground the SDD skill modularization concern (s-prc-nxy) in observed industry practice, with specific focus on patterns that resemble SDD's playbook-move dispatch.

Scope: three Claude Code skill bundles, examined via local clone:

- **GSD ("Getting Shit Done")** — https://github.com/gsd-build/get-shit-done.git — popular community-maintained productivity bundle.
- **gstack** — https://github.com/garrytan/gstack — popular community-maintained bundle (Garry Tan).
- **beads** — https://github.com/gastownhall/beads — bundles a Claude plugin with skills *and* is closer in shape to SDD itself (persistent memory backed by an embedded database). Carries a secondary angle worth examining: how the skills interface with the persistent layer, and how that mechanism compares to SDD's graph-as-record approach.

For each, characterize:

- **Routing / triggering patterns** — how the parent skill detects context and invokes the right sub-module: descriptive metadata, conditional cues, naming conventions, illustrative examples that prime the agent's decisions, explicit hand-off mechanics between sub-skills, fallback behavior when the trigger is ambiguous.
- **Per-move documentation shape** — how a single named move (analogous to our playbook moves) is documented: entry conditions, steps, exit conditions, transitions to other moves. What does the agent actually read to decide when and how to apply a move?
- **Modularization mechanics** — how content is split across SKILL.md, reference files, sub-skills, scripts, examples; what gets always-loaded vs on-demand.
- **Observed pitfalls** — tensions or regrets named in the bundles' READMEs, release notes, or commit history around routing reliability, trigger ambiguity, or modularization choices.

Beads-specific additions:

- **Skill-vs-storage interface** — how the skills interact with the embedded-database persistent layer (read-only? mutating? what abstraction does the skill present to the agent?).
- **Persistent-memory mechanics** — schema, immutability characteristics, comparison axes against SDD's markdown+frontmatter graph. If anything substantive surfaces for SDD's design, that drops out as a separate insight signal alongside the closing done.

Token counts and file sizes are secondary data points — useful for context-cost comparison but not the focus.

Output: a closing done signal carrying the comparison and findings (attached), feeding directly into the modularization design choice.
