New participants join with whatever local sdd version they happen to have, and the main branch pins no stable tooling version — so skew between a participant's binary and the project's expected tooling causes friction and can silently damage the project (for example, an older binary overwriting committed skills with its own outdated bundle). Proposed working agreement: pin the tooling on the main branch to a known stable sdd version, and confine dev-versions of the tool to dev branches. New participants then join against a predictable, stable baseline on main, while in-flight tool development stays on branches until it stabilizes and is promoted.

This is a workflow response to the version-skew root — distinct from the tooling fix of adding a version check (s-tac-ddi) and from the deeper data-format-conformance question — and it puts the tooling-from-graph separation principle (s-cpt-t2n) into practice on the branch axis. It serves the standing adoption-friction concern of low-friction entry for new participants (s-stg-qg0). Adopting it as a binding working agreement is a follow-on decision. Raised by Jonathan.
