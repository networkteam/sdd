Proceed with the workflow-agent direction (s-cpt-r57) as two sequenced experiments rather than committing to the full architecture up front. **Level 1 first:** build the CLI-parity MCP server (d-tac-0v4) as foundation and standalone value — structured graph access over MCP for any agent runtime, useful on its own and a prerequisite for Level 2; its risk is mainly engineering. **Level 2 as the experiment on top:** the stateful workflow agent (guide + gate) delivering skill content and dynamic instructions just-in-time, started on plain request/response rails — each tool response carries the next step and the executing agent calls back — with MCP sampling/elicitation deferred as a graceful upgrade where a client supports them. Level 2's outcome is genuinely uncertain (will executing agents honor the rails, is pulled context enough to steer, do dynamic instructions stay coherent); this commits to *trying it this way*, not to it working. **Discipline-by-surface constraint:** a generic executing agent is given graph reads plus the gated write flow only — raw write operations are never exposed to it, so the disciplined path is the sole way to create entries, operationalizing the validation-separation contract (d-cpt-vt1) at the tool surface. The full Level 1 write surface is for developers, experiments, and our own runtime, not naive consumers. Closes when Level 1 ships and the Level 2 experiment returns a verdict — works, doesn't, or needs reshaping.
