Capture-time ref-kind selection misfires and produces non-blocking noise: the agent tends to pick `related` as a low-information default and then write a more committal body, while pre-flight's medium band flags whenever a sharper kind merely exists — so defensible choices still cost the user a read-and-respond cycle. Two mechanisms combine. First, an authoring-order inversion: the kind is chosen from live dialogue intent (often the semantically-thin `related`), then the body frames the relationship more committally ("fulfills an AC", "the gap this builds on"), so the chosen kind undersells what the body asserts. Second, pre-flight's medium band is a finding-by-construction — it flags `related`/`grounds` whenever a sharper kind exists, not only when the body contradicts the kind; since almost any ref has a sharper reading, the medium fires often and each one reads as "worth dialoguing".

Measured on this repo's own graph (full record in the [attached evidence note](./29-210808-s-prc-web/ref-kind-evidence.md)): of 12 `related` refs, ~5 are clearly correct siblings, ~7 are "defensible but a sharper kind fits" (the band the medium fires on), and 0 contradict their body. 7 of the 12 carry no `desc` at all. `surfaces` has never been used. So the volume is not "every capture" in a carefully-tended graph, but the medium band's signal-to-noise is poor: it fires on defensible choices and catches no genuine error here.

This is the selection-and-calibration half; the shared-reference half — skill and pre-flight reading separate, hand-synced copies of the kind definitions — is already open as s-tac-uer. The two interlock: durably tightening the selection rule wants a single canonical home, which is s-tac-uer's domain.
