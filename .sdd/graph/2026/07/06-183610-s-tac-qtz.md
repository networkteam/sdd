`TestE2E_HybridFusion` in `internal/finders/search_e2e_test.go` flakes because the fixture searches a corpus far larger than the three fruit entries it writes. `LoadGraph` unconditionally injects the ten embedded base procedures into every graph, and `IndexHandler.Build` indexes whatever the graph returns — so the in-memory index the test queries actually holds `d-prc-cap`, `d-prc-cat`, `d-prc-eng`, and the rest, alongside `s-tac-aaa/bbb/ccc`. The failure surfaces in CI as `top hybrid hit: got 20260703-094500-d-prc-cap, want the orange entry`.

The defect only bites because of the fake embedder. The e2e embedder maps any text without an apple/orange/banana token to a pure dim-3 fallback vector `[0,0,0,h]`. The hybrid query phrase `"citrus harvest"` carries no fruit token, so it is also `[0,0,0,h_q]` — and two pure-dim-3 vectors are collinear, giving cosine exactly 1.0. Every base-procedure chunk therefore scores a perfect 1.0 in the vector arm, while the intended orange entry (`[0,1,0,h]`) has its fruit component *lower* its alignment with the fallback query, ranking it below them. In RRF fusion the orange entry wins the text arm outright but can tie a base procedure on fused score; the tie then resolves by nondeterministic map/sort order, so the top hit flips run to run.

This is a test-fixture isolation gap, not a product bug: with a real embedder the base procedures get distinct directions and cannot collide at 1.0. It builds on the search feature shipped in 20260505-181352-s-tac-96a, whose e2e suite this defect lives in. Reproduced locally under `go test ./internal/finders/ -run TestE2E_HybridFusion -count=30`. The fix must scope the fixture's effective corpus and/or give the fake embedder non-collinear fallback directions, so unrelated entries can never tie the intended hit.
