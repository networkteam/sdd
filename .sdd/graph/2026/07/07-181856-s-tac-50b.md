The graph-access lifetime drift is resolved: a finder-owned GraphSource now owns "what the current graph is," replacing the engine's mutable Graph field and the scattered, hand-maintained refreshGraph protocol (commit e735e79). This retires s-tac-jg8 by removing the fragility it named at the root — post-write freshness is no longer a manual refresh call that each write command must remember, but is driven structurally: engine.Command carries a MutatesGraph flag, and the engine's runCommand invalidates the source after any command that declares it (newEntry, replaceSummary), so the fidelity-review read reloads and sees the just-written entry with no forgot-to-refresh bug class left. All four refreshGraph call sites and the function itself are deleted; advance-entry freshness (startProcedure/next) becomes a plain memo-drop that can only stale orientation, never gate a write on a stale snapshot. Following the attached review's severity ranking, every read now routes through the one seam: MCP free reads and the CLI via Finder.CurrentGraph (one-shot, no retained cache, per-call/per-command lifetime unchanged), handlers via a Reader.CurrentGraph interface method kept decoupled from the finders package, and the engine through a small Graphs provider interface (StaticGraphs backs the engine unit tests). The review's fine-as-is items — the CLI/handler load pattern and the orientation-only staleness at re-knock/park/abandon — are left unchanged. No behavior change was intended or introduced: go vet, go test ./..., golangci-lint, and gofmt are all clean, and the real capture path (TestCaptureProcedureLoop, driving the MCP server through the verifySummary fidelity step that reads the graph by the new entry's ID) confirms the just-written entry is still served. The payoff beyond the fix: model.MultiGraph gains the single insertion point behind GraphSource.Current that the cross-repo references plan (d-tac-i6f) explicitly depends on, with cache clone/pull staying handler-side.
