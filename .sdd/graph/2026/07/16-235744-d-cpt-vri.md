In-place store-format evolution is the committed path for the machine-global vector index: a format change loads old state without migration and starts writing the new shape into the same store directory, relying on per-store monotonically increasing binary versions rather than on-disk isolation. The assumption was checked against this machine's real usage: stores are per-repo, and per-repo binary assignment is disjoint (dev binary for sdd, release binary elsewhere) — except for connected repos, the one path where another project's binary writes into a repo's store, which is the deliberate sharing of the machine-global placement (d-cpt-6cq). A live check confirmed sdd is connected from a release-binary project today, so mixed-generation writes are real but bounded: the window lasts only until the format change ships in a release and the installed binary is updated. Within a window, symptoms are silent re-embed churn and possibly stale citations served by the older binary — self-healing, no corruption: an old binary parses a multi-version manifest entry as zero-value, so its delete list is empty and it removes nothing.

The operational rule that keeps the assumption true: a format-affecting change to the store (manifest shape, chunk-ID scheme, row metadata semantics) must ship in a release promptly after merging, with the machine's installed binary updated. If a future format change cannot promise a short window, the known escape hatch is format-versioned store directories with copy-seeding — a format component in StoreDir isolating binary generations, seeded by converting a copy of the prior store so nothing re-embeds. The full analysis, including why bidirectional on-disk compatibility was rejected, is in the attached [note](./16-235744-d-cpt-vri/format-compat-analysis.md).

This scopes the slice-2 multi-version format (d-tac-js8) as safe to land without directory isolation.
