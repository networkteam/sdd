The engine's session list gives a user no way to tell what an open session was about: its self-derived descriptors — participant, anchor, and open instances — identify a session mechanically but not by subject, so a user offered several parked sessions cannot choose which to resume. This surfaced on one of the first live `sdd-engine` runs — three near-identical parked capture sessions were listed with only their timestamps, participant, and current step, indistinguishable to the user without opening each. The v1 workflow engine plan (20260702-220449-d-tac-ry0) committed to exactly these self-derived descriptors, and the shipped MCP shell (20260703-002223-s-tac-kd2) derives them from the session log alone — neither carries a human-meaningful label. The proposed direction, for dialogue: the agent supplies a short, identifiable session name or summary through its calls, and can update it on subsequent turns as the session's subject sharpens. Open question — whether that descriptor is agent-supplied (relayed like a chooser's userWords), auto-derived from the first captured draft or anchor entry, or both.
