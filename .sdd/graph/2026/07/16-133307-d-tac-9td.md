Restore fast MCP phrase and hybrid search by reconnecting `sdd serve` to the existing machine-global persistent index and indexing immutable entries monotonically instead of treating graph revision or request filters as vector freshness.

The release regression in `s-tac-ex4` is concrete in `cmd/sdd/serve.go`: `buildLocalApplication` injects `localadapter.NewMemorySearchIndexStore()` into every project-aware runtime, while `cmd/sdd/search.go:resolveIndexStore` already resolves the established persistent `index.RepoKey` / `index.StoreDir`. It is compounded in `application/vector_search.go`, which derives desired chunks after request filtering, compares graph-wide `Revision`, deletes chunks outside that request-shaped set, and rejects hits from another revision.

The repair is grounded in immutable graph entries (`d-cpt-e1i`) and in the narrower role of revisions as mutation-concurrency tokens (`d-cpt-65i`). The index therefore remains the monotonic union of immutable entry chunks for a repository and embedding fingerprint; status, supersession, and query filters are applied only when reading hits. It uses the machine-global content-addressed topology from `d-cpt-6cq`, preserves the separate embedding and storage ports from `d-tac-wjq`, and builds on the persistent chromem behavior and locking already delivered by `s-tac-96a` and `s-tac-cjr`.

Implementation will add a persistent local `SearchIndexStore` adapter over `internal/index`, wire base and connected-repository MCP runtimes to the same store directories as CLI search, and reopen the store inside a lock for each read/write operation so long-running servers see concurrent index updates without stale snapshots. The existing v1 index must be usable immediately: no migration and no cold rebuild. Public patch-release compatibility is preserved through additive hit/chunk metadata and an optional indexed-entry manifest capability; existing `Revision` fields remain source-compatible but are deprecated and ignored for freshness.

CLI and application indexing will share one deterministic entry-derivation path for summary, body, and Markdown-attachment chunks, including the existing entry-state hash and citation metadata. The application indexes only graph entries absent from the persistent manifest, embeds the query once, ignores stored hits whose entries are absent from the current graph, and then applies filters/status at read time. Explicit CLI force/rebuild remains the destructive repair path.

Rejected alternatives are retaining a per-process memory index, copying disk state into memory, invalidating on graph revision, deleting vectors due to request filters, or accepting one cold rebuild after upgrade. The cross-repository embedder-selection gap and the verification retrospective remain separate work so this plan stays release-focused.

## Acceptance criteria

- [ ] Production `sdd serve` no longer constructs `MemorySearchIndexStore`; base and dependency runtimes resolve the same machine-global repository/fingerprint `StoreDir` as CLI search.
- [ ] An existing v1 CLI-built index is readable by a fresh MCP server immediately, without migration, graph-document embedding, or rebuilding.
- [ ] Two consecutive fresh MCP server processes return the expected phrase-search result from that index with exactly one query embedding per search and zero graph-document embeddings.
- [ ] Graph revision changes, status changes, supersession visibility, and narrower request filters neither invalidate nor delete persisted vectors.
- [ ] Adding one immutable graph entry embeds only that entry's summary/body/Markdown-attachment chunks once; the following restart embeds zero graph documents.
- [ ] CLI and MCP use shared deterministic chunk derivation and entry hashing, and attachment hits preserve body, breadcrumb, depth, attachment path, and citation behavior.
- [ ] Stored hits whose entries are absent from the current graph are ignored at read time; destructive cleanup occurs only through the explicit CLI repair/rebuild path.
- [ ] The persistent adapter acquires locks before loading fresh store snapshots, persists through the existing v1 manifest/chromem format, validates fingerprint/metric/dimensions, and passes reusable store conformance tests.
- [ ] Exported v0.16.x storage APIs remain source-compatible through additive fields and optional capabilities; revision fields are retained but ignored for vector freshness.
- [ ] A production-path subprocess test with a fake Ollama-compatible server and real temporary cache proves CLI-to-MCP reuse, two cold-process zero-document searches, one-entry incremental indexing, and a subsequent zero-document restart using counters rather than timing thresholds.
- [ ] Application tests cover pre-indexed search, unrelated revision changes, one-entry addition, restart, filter/status changes, Markdown attachment citations, and missing-current-entry hits.
- [ ] `go vet ./...`, `go test ./...`, nested `examples/extendingsdd` tests, and `golangci-lint run ./...` pass.
- [ ] Before release, phrase search succeeds twice from fresh real agent/MCP sessions against the real repository without any graph-document embedding batch.
- [ ] The attached implementation specification is the detailed design contract; the retrospective and unrelated embedder-selection work remain out of scope for this patch.
