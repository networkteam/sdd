`sdd repo remove <repo-id>` is redefined to be project-scoped and reference-safety-guarded: it removes the committed `dependencies` entry from the current repo's `.sdd/config.yaml` and auto-commits that change, and it refuses when any entry in this graph references that repo-id — "safe" meaning zero cross-repo refs into the target. It no longer touches the per-user global connection or cache. This resolves the incoherence recorded in the dependency-lifecycle gap (20260709-161133-s-cpt-3wt): because entries are immutable, a referenced dependency is permanent, so the only sound removal is the declared-but-never-referenced case; the guard is a cheap local scan of this graph's cross-repo ref prefixes, refusing — or requiring an explicit `--force` that loudly names the refs it would strand — otherwise. Grounded in resolve-or-block (20260628-130400-d-cpt-uh0), which the guard keeps intact by refusing to create the dangling-reference state dropping a referenced dependency would produce. Alternatives rejected: keeping remove machine-global (the surprising status quo that orphans the committed declaration), and a machine-wide dependents scan to decide safety (expensive — connections are global, so dependents span every repo on the machine; the local scan suffices because refs are one-way forward, so a graph only ever strands its own refs). Machine-level connection/cache/index management is deliberately out of scope here — it moves to a separate command surface, the open part of the lifecycle gap. Auto-committing the config write also folds in the config-write consistency finding (20260709-161317-s-tac-ol7).
