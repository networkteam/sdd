`ExitWorktree action:remove` refuses to tear down a worktree whose branch still carries a commit, even when that commit is already an ancestor of main — forcing a re-invocation with `discard_changes: true` on every worktree run. `ExitWorktree` is a Claude Code harness tool, so both this friction and its remedy are Claude-Code-specific. In the sdd worktree recipe the branch is merged into main before teardown (the landing read and merge are the safety gate), so by cleanup time the work is provably on main and the tool's "this will discard work permanently" warning is a false positive: the branch is redundant, not unmerged. This confirmation step interrupts every worktree implementation run today, where it previously completed in one call. Because worktree session exit belongs to the harness and the sdd CLI owns no part of the worktree lifecycle (20260628-130403-d-cpt-h4l), the check is not ours to change — the lever is the Claude-Code-specific recipe layer that same directive assigns (CLAUDE.md's worktree notes and the Claude render of the /sdd recipe), not the agent-neutral guidance. Proposed remedy: instruct that layer to merge into main first and then pass `discard_changes: true` by default once the branch's commits are confirmed ancestors of main, so a provably-redundant branch tears down in one call. This is the same shape as the `sdd wip done` merged-check friction (20260601-164639-s-tac-qun), where an ancestry check tripped up teardown; that gap's lesson — tool-level guards beat agent-followed guidance — applies but is unavailable here, since the harness tool isn't ours to guard, leaving merge-first guidance as the safe default.
