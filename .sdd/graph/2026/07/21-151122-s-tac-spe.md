The entry write path exists twice: the CLI constructs command.NewEntryCmd and dispatches handlers.Handler.NewEntry, while the engine/MCP surface re-implements the same orchestration — build entry, validate, pre-flight, summarize, write, commit — as application.CreateEntry over its own EntryDraft in application/write_api.go, violating the CQRS write contract (20260413-142300-d-cpt-l3s) that the active planning contract (20260413-142536-d-cpt-ah1) enforces. The general contract for all writes, restated by Christopher in the dialogue that surfaced this gap: every write enters through an adapter — CLI, MCP, HTTP, whichever — which constructs a command, optionally sets callbacks to receive information back, and calls a handler that returns only an error. Ideally the command already carries the information the client needs, or generates it at construction (an ID readable off the command); callbacks are the last resort. No adapter orchestrates the write pipeline itself.

The duplication entered with the public project-aware application runtime (20260712-104530-d-tac-1mb): that plan grounded itself in the CQRS contract and stated the root package owns NewEntry, but delivery realized NewEntry as a parallel pipeline beside the handler rather than a dispatch into it, and its slice 6 deleted the legacy handler-backed MCP stack — leaving the CLI on handlers and the engine on the runtime. The two paths stay behaviorally consistent only because they share the lower layers (model validation, mechanical pre-flight, summary generation); every new write field must be mirrored onto both — the bootstrap procedure port mirrored canonical/aliases/actor and the focus involvement fields onto NewEntryCmd and EntryDraft alike — and checks can drift silently: the focus-actor coverage hole stayed benign only because it was absent from both paths at once.

Resolution needs its own plan, not a patch: the runtime carries mutation-target, session-binding, durable intent/apply, and staged-blob machinery the CLI handler has no notion of, so making both surfaces true adapters over one command-and-handler write path is a design exercise — deciding where the durable-write machinery lives inside the handler layer and what of EntryDraft survives as the command. The unification must also keep the exported public API of the sdd module offering an entrypoint into that command/handler path — quasi another adapter alongside CLI and MCP — so external Go compositions reach writes through the same single contract rather than a separate surface.
