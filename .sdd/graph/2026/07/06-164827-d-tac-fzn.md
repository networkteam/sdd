The engine's implementation procedure wraps long-running host work in a working loop with structural escapes: mode-and-marker setup, per-slice check-ins with accumulated progress notes, a dialogue-first blocked path, and a gated closeout that records the closing done before the engine removes the marker and offers evaluation. Settled through a structured design interview (record attached); five decisions:

**Working loop, not linear.** After anchor resolution and the served contract — the entry's chains with acceptance criteria and augmenting directives — the run sits at an agent-chooser working junction the agent returns to between slices: continue with a progress note, blocked, or conclude. Progress notes accumulate in state as the pickup material a log-only resume otherwise lacks (s-cpt-m6m). Rejected: a linear single work step (cross-session pickup would rely on git history alone) and a pause-only handoff note.

**Mode is the user's call; markers are engine work.** A setup user-chooser offers in place, branch, worktree, or quick; picking a tracked mode collects the marker description and runs wipStart in the same answer, so markers cannot be forgotten. Branch and worktree moves themselves stay host work with agent-neutral instructions. Quick stays inside the procedure and skips only the marker — contract, loop, and record gates still apply. Rejected: quick exiting to a plain capture (reintroduces the cold-capture friction the seeding contract removed, and leaves no home when a small fix grows) and dropping quick (marker churn for ten-minute fixes).

**Scope check as structural escape.** The setup junction carries a hold option — a needed decision is missing — that dispatches a seeded capture for the missing decision or plan and loops back to setup. Readiness is instructed prose; proceeding is never blocked. Rejected: a dedicated readiness-confirmation step (one extra turn on every run) and prose-only (the satisficing failure mode the engine exists to remove).

**Blocked is dialogue-first.** Taken when work hits a choice no decision covers, the blocked answer only marks the stop and stashes the run's grounding; the served unit instructs presenting the roadblock to the user with proposed ways forward and settling it in dialogue. The dialogue's outcome becomes zero or more captures — augmenting directive, directive, gap, question — each through normal confirmation, arriving pre-grounded via the stash (the seed grammar of s-tac-xeq). Then continue, or pause with the notes carrying the pickup. Rejected: auto-dispatching a capture on blocked (skips the dialogue that should shape it) and a forced progress-done-plus-signal pair (ceremony when the answer is one dialogue turn away).

**Closeout: commit, done, marker, evaluation offer.** Conclude instructs committing code first, then dispatches the closing-done capture — citing commit hashes, closing the acceptance criteria and augmenting commitments, carrying `implementation/<...>` work-shape topics per d-cpt-yum. The engine then removes the marker itself (quick runs skip it), and a final user junction offers starting the evaluate procedure seeded from the run, or finishing. The landing read before any merge stays instructed dialogue, per the evaluation model's split between the landing gate and the learning loop (d-cpt-eib). Rejected: a prose-only evaluation prompt and always-evaluate (couples two moves the model keeps separate).

Authoring realizes this design as the embedded implementation procedure in Slice B of the engine completion directive (d-tac-dbk).
