The engine's `next` MCP tool makes two chooser-answer mistakes easy, both hit while recording this session's findings and each costing an avoidable rejected round-trip. First, a chooser answer must name the chooser by its step identifier (`playback`, `verifySummary`), but the serve's `pending_chooser` block exposes only the chooser's `kind` (`user`, `agent`) and its options — never the identifier — so the caller supplies the kind and is rejected ('chooser "user" is not pending — the pending chooser is "playback"'); this misfired twice, once per kind, because the value the tool demands appears nowhere in the payload it just sent. Second, collected fields (e.g. `fidelityNote`) must be nested under a `fields` object inside the chooser-answer report, but the served `report_schema` lists those fields at its top level, so the caller places them top-level and is rejected ('option "faithful" requires field "fidelityNote"') despite having supplied the value. Both are discoverability gaps in the serve rather than caller misunderstanding: naming the pending chooser in `pending_chooser`, and either accepting top-level collected fields or marking the `fields` nesting in the served schema, would remove the round-trips. Observed dogfooding the engine's MCP surface while capturing evaluation findings.
