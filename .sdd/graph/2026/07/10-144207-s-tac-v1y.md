`sdd config get` and `sdd config set` fall short of the three-layer overlay they operate over: `get` on a parent key errors instead of returning its subtree, and `set` can target only two of the three config locations. Both were observed while documenting the config model, and both are measured against the placement directive (20260708-184318-d-cpt-6cq) whose overlay and `sdd config` surface the plan (20260708-185833-d-tac-nhx) shipped. First, `sdd config get llm` fails with `no value for "llm"`: get resolves only a leaf scalar, so a parent/branch key errors rather than returning the block beneath it. It should render the subtree — the whole `llm` mapping — the way the effective view already holds the full nested config. Second, `sdd config set` exposes only two write targets, user-global (default) and machine-local (`--local`), while the settled model has three locations: user-global, the committed per-repo `.sdd/config.yaml`, and the machine-local `.sdd/config.local.yaml`. There is no way — and no mention in `--help` — to set a committed project property through the CLI; that layer is written only by `sdd init` or by hand. The plan scoped `set` to global+local deliberately (a committed change is a reviewed commit), but the surface neither offers a committed target nor names the third location, leaving someone who knows there are three layers unsure how to set a project-level key. Open: whether to add a committed-project write target (e.g. a `--project` flag) or to document the init/hand-edit path and surface the third location in help. Both are small CLI-surface fixes that make `sdd config` honor the overlay it exposes.
