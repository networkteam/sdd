The thirty-four stranded pending-write notices are cleared by a read-side projection fix alone: `recoveryItem` must derive actionability from the recorded apply outcome instead of from terminal absence, and the legacy-version branch must stop short-circuiting ahead of that read. No session-store write, no sweep, no migration, no new recovery verb, and no session deletion.

The store is already correct. Verified against the live machine-global store, every stranded intent is a complete triple: a `mutation_intent` carrying `Version: 1`, `Document: null` and canonical bytes; a `mutation_outcome` recording `apply.State: "applied"`; and a `finalizer_outcome` recording the git finalizer as succeeded — with no terminal event. The three sessions holding them are s_20260714-095955-885b3c45, s_20260715-165703-e25be2e2 and s_20260716-121551-d740f1c6. So the writes are delivered and the notice is simply wrong, exactly as the gap reported (20260727-102820-s-tac-9op): wrong about its state and wrong about its need. Writing terminal events to satisfy a misreading projection would be fixing the wrong end; teaching the projection to read what the store already records fixes the class rather than today's thirty-four instances.

The defect is an ordering one in `recoveryItem`. Actionability is set unconditionally for any mutation lacking a terminal, then the legacy-version branch returns `LegacyUnroutable` with state `unknown` — both before the recorded `apply.State` is ever consulted. Inverting that order is the whole fix, and it is the read-side expression of the two-durable-conditions rule in 20260727-230506-d-cpt-msg: definitive applied with all recorded finalizers succeeded means delivered and not actionable; definitive not-applied is the genuine awaiting-decision case; unknown is pending delivery. A recorded finalizer failure must keep the item actionable, since a failed git commit is an independently retryable finalizer under that same contract and not a notice to clear — this is the boundary the fix must not cross.

The surplus recovery surface — `bindLegacyTarget` and the specialized verbs — is left in place. Removing it is the larger complexity cut, but it is write-side and costs nothing to defer once nothing routes to it. This plan is likewise independent of the write-path unification (20260721-151122-s-tac-spe): being read-side only, it does not wait on that design exercise.

Fixtures are extracted verbatim from those three real session logs rather than hand-written, each trimmed to its metadata envelope plus one mutation triple. This is the specific discipline demanded by 20260726-204112-s-prc-ogp: the proofs that certified `bindLegacyTarget` used constructed v1 intents carrying documents the v1 writer never produced, so a hand-authored fixture here would reproduce precisely the failure it is meant to prevent. The run against a copy of the live store is a separate criterion for the same reason — not a redundant check, but the only one that confronts the accumulated corpus — and Christopher drives that run himself before merge, so neither the implementation nor any inner evaluation may report it as met.

## Acceptance criteria

- [ ] `recoveryItem` derives actionability from the recorded apply outcome before any version-based branching, so a legacy-version intent with a definitive outcome is never rendered `unknown · target binding required`. Checked by a unit test whose input is a v1 triple extracted verbatim from a real session log; it fails on the current code.
- [ ] An applied mutation whose recorded `finalizer_outcome` reports failure stays actionable. Checked by a unit test pinning that boundary, so the fix cannot over-suppress genuine finalizer failures.
- [ ] `listRecoveriesRuntime` over a session-store fixture built from the three real logs returns zero actionable items. Checked by an integration test exercising list, replay and projection together; it fails on the current code.
- [ ] Test fixtures are extracted from the real session logs rather than authored by hand, with the extraction reproducible. Checked by review of the fixture provenance against the source logs.
- [ ] A run against a copy of the live session store reports zero pending-write notices where it currently reports thirty-four. Christopher drives this run himself after implementation and before merge; it is not a committed test, and neither the implementation nor the inner evaluation may claim it — closure stays open until that run has happened.
- [ ] No session-store write, migration, sweep, or new recovery verb is introduced, and no session log is deleted. Checked by review of the diff.
- [ ] `go vet ./...`, `go test ./...` and `golangci-lint run ./...` are clean, including the nested module tests.
