The MCP search tool's `type` filter silently returns zero results for the documented shorthand form: the schema promises "s/signal or d/decision", but `publicGraphFilter` casts the type raw while only layers get abbreviation expansion — `type: "s"` matches no entry and empties every AND-filtered result set, in vector and text modes alike. Confirmed live from two independent sessions: `{"query":"broken vector search","type":"s"}` returns "(no matches)" while `type: "signal"` returns six gap signals, and the CLI with `--type s` works because it normalizes on its own path.

The defect predates the persistent-index repair (d-tac-9td) and was masked behind the spec-gate and cold re-embed regressions — live validation of that plan's first slice exposed it. Beyond normalization, the failure mode violates the fail-loud rule: an unrecognized type, layer, or kind builds a filter that silently matches nothing instead of erroring, indistinguishable from a genuinely empty result. Fix direction, already committed to on the repair branch: normalize type like layer, and return loud typed errors for unrecognized filter values.
