A confirmed graph mutation is a durable declaration of desired state — target, operation ID, exact canonical bytes, digest — and delivery is retryable until precisely that state exists, replacing the recovery state machine with convergence. Uniqueness at the write path is the invariant that makes retry safe, only two conditions are durable (pending delivery and delivered), and the same observable guarantees must hold for a local Git graph and a hosted store alike.

**The declaration.** It persists once, before any delivery attempt. Retry never regenerates content, never changes destination, and never replays dialogue or LLM work: ID absent means write the exact bytes, ID present with a matching digest means this was a retry and it succeeded, a timeout or crash means retry the same declaration. Pre-generating the ID alone would be insufficient, because recomputing timestamps, summaries, or rendered content could produce different bytes — but the confirmed document is already in hand at that point, so persisting the exact payload closes the gap. This relocates crash-safety to a strictly better place: a declaration that fails to persist means the capture was never confirmed durable, and the user is still in the conversation to redo it — benign rather than ambiguous.

**Uniqueness at the write path, not the read.** Reading the target to decide whether the write landed is authoritative on a filesystem but not for a hosted store, where a read can lag its own write and absence is therefore not proof of absence. The guarantee is enforced by unique-ID-or-conflict at the write path; the read is an optimization. This yields the portability requirement: a store that cannot offer unique-ID-or-conflict on write cannot host these guarantees.

**Two durable conditions.** Pending delivery and delivered. Transient failures — target unavailable, request lost — are diagnostics attached to pending delivery, never new states and never new verbs. The same ID under a different digest, and storage corruption, fail loud instead of becoming states one can sit in, and a declaration that no longer validates against the graph stays pending with a diagnostic until dialogue resolves it. The reason is the failure shape recorded in 20260727-102820-s-tac-9op: entry IDs are timestamp plus suffix and the bytes are frozen at confirm, so a digest conflict is reachable only through corruption or an ID collision — a durable state for it would be a branch nothing but a constructed test can ever produce, which is exactly how `bindLegacyTarget` came to be unreachable while its proofs passed.

**Ordering replaces atomicity.** Atomic multi-document apply is dropped as a public invariant, re-scoping the storage-neutral batch commitment in 20260712-194427-d-tac-wjq. It costs nothing today: the batch has exactly two construction sites and each carries exactly one document, so multi-document atomicity has never been exercised. The declaration nonetheless stays whole — one ID, one digest, one commit covering the entry and all its attachments; what is dropped is only the store's obligation to apply the parts indivisibly. Ordering suffices because the intermediate states it leaves are garbage but not lies — an orphan attachment, a WIP marker outliving its closing entry, both groomable — while the two states that would be lies are precisely what the order forbids: an entry published before its attachments exist, and a marker removed before its closing evidence exists. What is given up is rollback, and that is the gain: the rollback path and the pending-transaction sweep delivered in 20260713-005437-s-tac-paq exist only to make multi-part apply all-or-nothing, whereas convergence retries through the same code path as the first attempt rather than a second inverse one. The accepted cost is that orphan attachments accumulate and want a sweeper, and that grooming must skip whatever an in-flight declaration still claims.

**The whole-graph revision compare-and-set is dropped; revalidation against the fresh snapshot stays.** These are different things, and only the second has semantic content. Revalidation proves the refs still resolve and the graph still validates; because entries are append-only, nothing another writer does afterwards can invalidate a proof that just passed — another session adding an entry cannot break yours. Once it passes, revision equality contributes only a chance to lose the race. Today the loss is real rather than theoretical: bounded retries are followed by discarding the intent and asking the user to re-try the write, which throws away a confirmed capture and re-bills pre-flight and summarization — the exact loss forbidden by 20260727-224047-d-cpt-u8o, which fixes the confirmed entry as the one thing that must survive.

**Summary replacement is the single carve-out.** It rewrites an existing entry file in place — the only such write in the system — so same-ID-different-digest is genuinely reachable when two participants re-summarize the same entry. It therefore takes a per-document precondition on the entry's current digest rather than a graph-wide revision, and it is excluded from automatic retry: the replacement text is author-supplied rather than regenerated, so a retry is mechanically sound, but auto-retrying makes the loser overwrite the winner and ping-pongs if both sides do it. A conflict fails loud carrying the current digest and the current summary text, which per 20260707-134311-d-cpt-476 keeps retry reachable without a host-local command and makes ignoring the conflict an informed choice rather than a blind one. Ignoring is legitimate here, unlike for an entry — a summary is a derived pointer and someone else's is as valid as mine — but it is always the caller's decision and never a silent last-write-wins inside the store, and a human-verified correction must not be silently replaced by a machine regeneration.

**Intents predating this rule are not convergeable and are discarded.** The rule requires the persisted exact content, which the v1 intent shape never stored, so those declarations cannot converge under it either. They are discarded with a visible note and no recovery verb — sound because 20260727-224047-d-cpt-u8o establishes that incomplete session bookkeeping is not a record worth recovering, while the graph writes those intents describe are already present and committed.

**Where these preconditions live.** They belong to the unified command-and-handler write path called for in 20260721-151122-s-tac-spe, not to today's split surfaces — encoding them into the current shape would target code already slated to be folded. Summaries are a second instance of that same drift and in the opposite direction from the new-entry case that gap describes: the CLI summarize path writes frontmatter straight to disk with no intent, no precondition and no compare-and-set, and does so across many entries concurrently under `--all --force`, making it a likelier real-world source of a lost summary than two engine sessions racing. Whether that path is folded in or explicitly declared out of scope is left open here.

**Acceptance.** Per 20260726-204112-s-prc-ogp, convergence counts as demonstrated only when a process killed mid-write against a real accumulated store converges on the next attempt — not when a constructed declaration does. Every pending declaration must additionally be swept at a defined trigger, and that sweep must be exercised by the real path: a pending delivery nobody ever retries is how the stranded-notice pile formed in the first place. Who owns the sweep locally, and at what trigger, is named here as a requirement and settled separately.

**Re-kinded, not re-decided.** This replaces 20260727-230506-d-cpt-msg with its content intact — the same commitments, the same reasoning, the same edges. Only the kind changes, from `contract` to a `directive` carrying `intent: guiding`. The reason is recorded in 20260728-084122-s-cpt-eff: `contract` was deprecated on 22 June, that deprecation reached no capture surface, and a standing constraint captured under guidance still naming `contract` therefore fell outside the standing-context lane every session opens with — the lane filters on directive plus guiding intent, and contracts carry no intent at all, so no per-entry fix existed. Under the discriminator in 20260629-001157-s-cpt-c7f this is a stance rather than a rule: it carries no activation, no "when" that fires and can be checked, only a persistent position on how delivery behaves. And it governs SDD's own code and tooling, which is what 20260628-154618-d-cpt-dym reserves `intent: guiding` for. Three phrases naming the predecessor's own kind were reworded — the portability requirement, the heading on where the preconditions live, and the heading for intents predating this rule — because they described a kind this entry no longer carries; nothing else changed. The design record attached to the predecessor is not duplicated here and remains reachable through the supersede chain. It answers only the concrete half of that gap: whether the capture-side steer is decoupled from rule-system delivery, or held until it lands, stays open there.
