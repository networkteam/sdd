MCP cross-repo vector search can use a different embedder than CLI cross-repo search, so the two co-equal surfaces can fill and read different connected-index stores for the same query. Surfaced by the inner code evaluation 20260709-152356-s-tac-6n3 while reviewing the slice-4 wiring in 20260709-141700-s-tac-jbs. The CLI path deliberately treats cross-repo search as a shared-vector-space operation: `sdd search --repo` / `--all-repos` and `sdd index --repo` / `--all-repos` select the global cross-repo embedder first, falling back to local resolution only when no global embedding provider is configured. The MCP server path does not mirror that rule: `sdd serve` builds one searcher with the local effective embedder at startup and passes that same embedder to the cross-repo prepare step. If a repo-local embedding override exists while a user-global embedding provider is configured for cross-repo work, the CLI and MCP surfaces can build under different fingerprints and query different `(repo-id, fingerprint)` stores, producing inconsistent cross-repo vector results. This is a reliability gap against the original cross-repo implementation 20260708-010505-s-tac-94a and the prior architecture review's CLI/MCP parity yardstick in 20260708-090449-s-tac-vyq: the handler/finder split mostly holds, but the composition-root embedder choice diverges across hosts.
