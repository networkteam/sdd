SDD's user-global config is a cross-repo-only schema, so participant, llm, and local embedding placed there are silently dropped — all config should instead be a unified global-first overlay where any user/machine setting is globally settable with per-repo override. Surfaced during the outer validation of cross-repo references (20260708-151819-s-tac-cr0): a user reasonably copied their shared settings (participant, llm, embedding) into ~/.config/sdd/config.yaml, but only the connected-repos list and the cross-repo embedder are honored there — participant and llm are silently discarded, proven by `sdd lint` reporting 'no local participant configured' once the project-local config was moved aside. Root cause: the user-global file parses into a narrow schema (repos + embedding) loaded only by the connected-repos registry and the cross-repo search embedder, while the general config resolution reads only the project's .sdd/config.yaml + .sdd/config.local.yaml and never consults the global file. The silent discard of unknown keys violates the fail-loud discipline, and the split forces per-repo duplication of exactly the settings a user shares everywhere. Proposed direction (not yet a committed decision): factor the overlayable user/machine settings into a shared BaseConfig embedded by both a per-repo LocalConfig and a user-global GlobalConfig, combined by overlay — global as the base, the per-repo config overriding it (the committed .sdd/config.yaml refined by the per-machine .sdd/config.local.yaml), CLI flags last — so participant, llm, and embedding are set once globally and overridden only where a repo differs; add a `sdd config` surface to create the file, get/set keys, and print the effective merged config; and make unknown or wrong-file keys fail loud. The overlay covers only the shared BaseConfig settings; layer-specific fields sit outside it. The GlobalConfig additionally holds `repos` — the per-user registry of connected repos' clone URLs and homedir caches (how this machine fetches each connection), which is global-only. The per-repo config additionally holds the repository's own fields, none of them global: repo_id above all — the repository's identity, never user-chosen and never inherited from a global default (a global fallback would silently mis-stamp any repo lacking one) — plus graph_dir, supported_agents, skill_scope, likely language (the graph's authored language, shared by all contributors), and the repository's declared cross-repo dependencies (a committed, per-repo, directed list — a distinct concept from the global `repos` resolution, carried in depth by the connections finding). The homes of language, skill_scope, and sync.cooldown (project-pinned-with-global-default vs global) remain open for the eventual decision. This finding bears on the cross-repo global-config design (20260606-003344-d-cpt-s6q), which introduced the narrow global file and its single global embedding config.
