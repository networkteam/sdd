The public mcpapp handler runtime lacks a host-controlled lifecycle for cancelling and draining asynchronous connection cleanup before the composing application tears down its stores. The inner evaluation (20260713-165141-s-tac-78g) exposed this in the implementation governed by (20260712-234500-d-tac-x1m): ten repetitions of the real stateful HTTP identity tests failed four times because disconnect watchers continued leave-session work while TempDir-backed session storage was being removed, producing missing lock files, session-not-found errors, and non-empty-directory cleanup failures. The race detector passed, so the defect is lifecycle ordering rather than an unsynchronized-memory race. External applications should construct the MCP application and register its Handler on an HTTP server they own; local sdd serve should likewise own its HTTP server, address binding, static bearer middleware, and graceful HTTP shutdown, so listener-owning RunHTTP behavior does not belong in the public mcpapp package. A bounded Shutdown(ctx) on the handler runtime should mark it closing, reject new MCP sessions, and close every tracked MCP ServerSession concurrently. Once each session's in-flight requests finish, the SDK Close completes and unblocks its Wait watcher; that watcher then performs leave-session cleanup, and a wait-group barrier lets Shutdown return only after all such cleanup has drained. If the shutdown context expires because a session cannot close gracefully, Shutdown returns the timeout and the host can force-close its own HTTP connections. Session-close, watcher, and leave-session errors must be surfaced rather than only logged.
