The workflow engine delivers process knowledge only by push — three served tiers with no pull layer — so knowledge an agent needs to look up mid-work has no home except the Go source. The engine's session architecture (d-cpt-h99) fixed three knowledge tiers, all served proactively: connection-time server instructions (tier zero, the irreducible minimum), the session-start serve (tier one — process core, conduct and register rules, the live procedure enumeration, routing), and per-step instruction units (tier two, just-in-time for the running move). It declared "everything the agent needs arrives served" and set the sdd-engine skill on a path to retire into a pointer at the door. But "everything served" is only everything the engine chooses to push; there is no counterpart to the middle tier the /sdd skill shipped in its modularization (s-prc-lyg) — on-demand playbook references the agent pulls when a topic comes up. Reference knowledge — how to author or customize a procedure, the ref-kind taxonomy, the view filter grammar, the layer definitions — is neither small enough to live in the always-served minimum nor bound to a single procedure step, so under the engine's push-only model it has no home and survives only in source. This surfaced live: determining whether a custom project procedure was even authorable required reading the Go source (the base-procedure embedding and graph merge, the closed registry of predicates/queries/commands, the spec's state-machine format), because no served or pullable surface explains "how to tweak the process." The regression bites hardest exactly where SDD wants reach — a non-framework user customizing SDD for their own project.
