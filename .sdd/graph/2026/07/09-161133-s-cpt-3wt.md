The cross-repo `dependencies` set a graph declares is bounded-below by the references that already exist in it — so a dependency that has been referenced cannot be soundly undeclared, and today's `sdd repo remove` ignores this entirely. Surfaced by the outer validation 20260709-160634-s-tac-tt8. Because entries are immutable, the moment an entry cites a cross-repo ref into repo B that ref is permanent — even superseding or closing the entry leaves it on disk — so B is a permanent dependency of this graph's history. Dropping `dependencies: [B]` cannot undo the refs; it only removes the declaration resolve-or-block (20260628-130400-d-cpt-uh0) requires, retroactively re-creating the dangling-reference state that invariant exists to prevent. This makes the current surface incoherent two ways. First, `sdd repo add` and `sdd repo remove` are asymmetric: add dual-writes the committed dependency plus the per-user global connection, while remove drops only the global connection — machine-wide, surprising from inside a project — and orphans the committed declaration. Second, there is no clean teardown of a connected repo's three footprints (global registry entry, cache clone, machine-global index store); remove touches only the first. The cross-repo design (20260606-003344-d-cpt-s6q) introduced these as two concepts — a committed directed `dependencies` list and a per-user `repos` resolution — but never defined how a dependency retires. Direction settled in dialogue: `repo remove` becomes project-scoped and ref-safety-guarded (its own directive), and machine-level connection/cache/index management moves to a separate command surface — undesigned, and the open part of this gap.
