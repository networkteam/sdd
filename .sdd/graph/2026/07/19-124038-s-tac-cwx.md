Dialogue sessions carry no branch context, so ordinary captures from a worktree-bound working context default to the repository's configured default branch and fail on refs to worktree-resident entries — with per-capture `captureBranch` seeding the only lever, discoverable only through a rejected write. The default is by design: the explicit-mutation-authority directive (20260713-214050-d-cpt-65i) bars launch directory and ambient cwd from selecting any mutation destination — motivated by the launch-context drift analysis (20260713-121507-s-prc-akz) — and makes `defaultBranch` the fallback for an ordinary capture whose branch was not explicitly selected. Live use immediately found the seam that clause leaves open: during the session-model outer evaluation, two concurrent sessions (Claude Code and Codex) each captured findings that referenced done signals living only on the worktree branch; both writes were correctly blocked by resolve-or-block as dangling on the default branch (the first was the truncation-evaluation capture, 20260719-122103-s-tac-jom, and the same rejection also exposed the binding-wipe defect, 20260719-123145-s-tac-tq7), and both agents recovered only by seeding `captureBranch` per capture — the Codex agent only after the user intervened with "You must target the current branch of the worktree". Nothing at session open tells the agent which branch the dialogue's context lives on, and nothing carries that answer across the session's captures. The goal, stated by Christopher from live use, is a seamless UX across the whole working arc: a user starts in the repo root, implementation begins, the agent enters a worktree — at that point the session's current-branch binding must be set to the worktree branch, and every future capture targets that branch, including ordinary captures made after the implementation procedure has finished, until the worktree is left and the binding reverts. The binding is therefore session-level state driven by explicit host-transition declarations (enter/leave worktree), deliberately not a contained per-procedure state scoped by procedure nesting — the implementation lifecycle's explicit `baseBranch`/`workBranch` roles would consume it as their default rather than replace it. A transition-declared, session-logged binding is not ambient cwd resolution — each change is an explicit auditable event — so it arguably stays within the directive's explicitness rule while revisiting its ordinary-capture default clause. Open design questions: the declaration seam (worktree lifecycle is host-owned, so the agent or host must report transitions — the engine cannot observe them), drift protection when a declared leave is forgotten or the server outlives a host branch switch (the exact risk the launch-context analysis warned about, arguing for fail-loud validation of the declared binding against the store at write time), and the precise interplay with the implementation lifecycle's branch roles.
