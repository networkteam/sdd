Legacy-session migration copies each per-session staging directory into staged-blob storage but never removes the source, so migrated `<id>-staging` directories linger indefinitely in the sessions directory. During conversion, the migrator opens each file in the legacy `<id>-staging` directory, stages it into the current staged-blob store under a fresh blob ID, and then atomically replaces the session log — but the original staging directory is never deleted. Because a rerun short-circuits at the current-format classification check (an already-migrated session is a no-op), the leftover directory is never revisited or cleaned on any later `sdd init`. No data is lost: the attachment bytes are preserved in their new location and a resumed capture recovers its staged evidence. The issue is that the plan committed to *moving* legacy staged files into current storage, and the implementation copies — leaving cosmetic cruft. A fix would remove the staging directory after the successful atomic replacement (the last mutating step, so rollback-on-failure behavior is unchanged), or before returning on the idempotent current-format path so existing residue also gets swept. Surfaced by the inner code evaluation (20260714-142231-s-tac-zdt) while verifying the converter shipped by the migration work (20260714-140424-s-tac-fco).
