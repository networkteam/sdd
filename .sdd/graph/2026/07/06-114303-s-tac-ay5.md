The engine's `start_procedure` MCP tool doesn't surface a procedure's accepted start inputs before the call, so callers discover them only through rejected round-trips — the same discoverability family as the now-fixed `next` chooser-answer gaps (s-tac-keb), on a surface that fix did not touch. Dogfooding capture in a Codex session hit two misfires: an unaccepted param (`goal`) was rejected with `unknown start input "goal"`, and `supersedes` in the wrong shape was rejected with `expected entry ID (string)`. Confirmed still present on current code — the tool's `params` field carries only a generic description ("typed start inputs per the procedure's declaration") rather than the specific procedure's declared param names and types; the accepted set appears only in the rejection. Surfacing each procedure's accepted params and shapes in the served schema — as the `next` fix did for the chooser step id — removes the round-trips. Softer than the `next` gaps (the rejection does list the valid params), but still an avoidable failed call.
