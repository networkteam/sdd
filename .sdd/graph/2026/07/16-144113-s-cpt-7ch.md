Embedded framework entries surface in search results indistinguishable from project entries, and agents have no served guidance to treat them differently when presenting results to users. Evidence from the docs example-world pilot (20260715-183740-d-cpt-jrt): in the freshly fabricated roastery graph, `sdd search --term story` ranked two embedded base procedure entries above the project's own entries, carrying July-2026 timestamps alien to the graph's story timeline — and the same will happen to any real project consumer, whose searches interleave framework entries with their own without any marking. The indexing itself is correct and affirmed: the base-facts directive (20260707-140544-d-cpt-dtv) explicitly commits the finders to treat embedded and on-disk entries identically so framework knowledge stays pullable — that design holds. What is missing sits above it, in two candidate directions. First, served guidance: base instructions or procedure text should make agents aware that search results can contain embedded framework entries, so they recognize them (the entries carry framework markers — no participants, the engine/base-procedures topic) and do not present them to users as if they were project entries — in dialogue, framework knowledge answers the agent's own questions; it is not the user's project material. Second, ranking calibration worth considering: an overall relevancy down-weight for static embedded entries, tuning them below same-relevance project entries without hiding them. For the docs program this bites immediately — every fabricated scenario graph inherits the embedded corpus, so docs search examples must either be curated around collisions or the presentation treatment must land first.
