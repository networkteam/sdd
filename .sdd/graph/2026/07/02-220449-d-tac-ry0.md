Build the v1 workflow engine per the reviewed surface spec ([surface-spec](./02-220449-d-tac-ry0/surface-spec.md)): playbook moves become `procedure` entries — canonical-named, process-pinned graph entries whose frontmatter carries a state machine over a typed variable store and whose body carries per-step instruction units — executed in-process with a closed Go registry (predicates, queries, commands) composed by name in YAML, sessions persisted as append-only JSONL event logs, and a narrow MCP surface where graph writes exist only as procedure transitions. This supplies the implementation plan the engine directive demands (20260702-174833-d-cpt-3yw) and executes step 3 of the planning activity (20260702-180130-d-tac-tdh), folding its step-4 transition mechanics into the slices; it builds directly from the inventory and interview record (20260702-204302-s-tac-4yf). The alignment directives ship inside it — the shell's alignment junctions (20260628-154629-d-prc-1ob) and the interview procedure spec (20260628-154633-d-prc-e2y) — and session-scoped attachment staging plus the paged read tool realize the two commitments orphaned by the MCP-server supersession (20260527-212055-d-tac-6zt, 20260606-004059-d-tac-d21). The rule kind is designed alongside the procedure kind as one type-system revision but ships fast-follow on the rule plan's line (20260622-084244-d-tac-eho).

The overarching goal is parity in use: a usable SDD flow comparable to today's skill experience, with the parity inventory defining "comparable" and side-by-side dogfooding measuring it — a thin engine-bootstrap skill ships next to the untouched /sdd, the user chooses per session, and once a procedure ships its spec is authoritative and the corresponding skill prose freezes.

Slices, dogfooding starting inside the spine: (1) type-system revision — procedure + rule kinds designed together, procedure ships now, embedded base loading, canonical resolution, fork lint; (2) engine core, pure Go — store, registry, guards, cascade, session log, table-test harness; (3) MCP shell — loop/session/staging tools, free reads including read_attachment, framing injection, served-instruction memory, thin bootstrap skill; (4) capture procedure — full spine dialogue, dogfooding begins; (5) engage plus explore; (6) catch-up; (7) groom, evaluate, implementation; (8) interview and the close gate; (9) Claude Desktop as second client.

## Acceptance criteria

- [ ] The type-system revision is captured: procedure and rule kinds designed together in one revision, procedure shipped (process-pinned, write-once canonical), rule deferred with its design recorded.
- [ ] The engine core passes per-procedure table tests; guards are boolean combinations of named Go predicates only — no assignment or expression syntax anywhere in YAML.
- [ ] Sessions survive restart by log replay; list_sessions and resume_session work across agent sessions; abandon surfaces held WIP markers without implicit cleanup.
- [ ] The MCP surface matches the spec exactly; no graph-write path exists outside procedure transitions; the pre-flight override is reachable only through a user chooser.
- [ ] The capture procedure reaches parity in use, including supersede/close/augment via params, staged attachments, and summary verification.
- [ ] Each remaining procedure (engage, explore, catch-up, groom, evaluate, implementation, interview) ships with its spec, table tests, and parity in use validated through side-by-side dogfooding.
- [ ] The thin engine-bootstrap skill ships alongside the untouched /sdd with per-session choice; shipped procedures' specs are authoritative and their skill prose is frozen.
- [ ] Deferred items and their revisit triggers are recorded in the shipped plan artifacts: bootstrap port, sync reactions, explore compression fork, rule-kind shipping, generic evidence vocabulary.
