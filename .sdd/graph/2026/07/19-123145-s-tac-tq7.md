A failed capture write permanently poisons the MCP connection's session binding: in `runWorkflowNewEntry` the workflow's `SessionBinding` is overwritten with `result.Binding` before the error check, so when `CreateEntry` fails — as it did live on a legitimate dangling-ref rejection — the zero-value result wipes the binding to an empty session ID, and every subsequent tool on that connection fails misleadingly. All four sibling mutation commands (`replaceSummary`, `wipStart`, `wipDone`, `wipRemove`) guard this assignment on success; `newEntry` is the single unguarded site. The failure cascade was reproduced independently in two live sessions during the outer evaluation of the session-model plan (20260718-180550-d-tac-e3x) — a Claude Code session and a concurrent Codex session, both tripped by the same trigger: a capture ref that resolved only on the worktree branch while the write targeted the configured default branch. After the wipe: `next` reports "this connection is not attached" and points at `resume_session`, but `resume_session` — in every variant, including takeover — dies earlier in its still-held pre-check calling `Load("")` → `sdd: invalid session ID ""`, so the very tool the error recommends is the one the wiped binding breaks; `start_session` reopens the dialogue in memory but serves `"session": ""`; and, shown by the Codex reproduction, even the free read tools (`show`) fail identically, because an attached connection's reads append to the session read log through the same wiped binding — the entire toolset dies, reads included. The store was verified healthy throughout (latest metadata intact, all draft state and staged attachments preserved), and in both sessions a fresh server process attached to the same session normally — a scripted MCP probe in one, a hand-driven `sdd serve` over JSON-RPC in the other — proving only the live process's memory is poisoned and no tool-reachable recovery exists; only a transport reconnect heals it. Severity: the trigger is a normal event — any validation-rejected capture write, exactly what the write gate is designed to produce — which occurred here while recording the truncation evaluation (20260719-122103-s-tac-jom). Fix direction: guard the assignment like the siblings (`if err == nil`); a store version advanced before the failure is already covered by the append path's resync-and-retry, so keeping the old binding on error is safe. A regression test should pin: rejected `newEntry` → same connection's `next`, `show`, and `resume_session` still work. Full timeline, log excerpts, code citations, and probe evidence are in the attached debugging record.
