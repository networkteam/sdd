The public application has split participant authority: `Principal.Participant` represents the caller resolved from the current request, while `ProjectRuntimeOptions.Participant` independently controls initial framing and serves as a fallback for identity-bearing writes. The outer evaluation (20260713-160800-s-tac-luv) surfaced the mismatch while validating the active public API implementation (20260712-234500-d-tac-x1m): an external bearer-authenticated session resolved a non-empty principal but served blank initial participant framing because its shared project runtime carried no participant. The divergence runs deeper than presentation—new engine sessions use the runtime participant, durable session metadata stores the resolved principal, resume replays the stored participant, and entry/WIP defaults mix the two sources. This is redundant in local SDD, where the effective overlay—user-global configuration, committed repository configuration, then machine-local repository override—is already resolved into the local principal; it is invalid for a hosted server, where a shared project runtime serves many users. The single authority should be `Principal.Participant`: the hosted resolver maps request identity to the user, applies that user's per-project participant override or user-global canonical participant, and the local resolver maps its effective participant configuration through the same contract. `ProjectRuntime.Participant` and its fallbacks have no remaining role.
