Engine host-neutrality is a base-procedure discipline, not a universal one: the framework's shipped procedures must stay host-neutral, but a project may author procedures that depend on their own runtime — a release procedure that only runs on a developer's local machine is a legitimate project procedure. This scopes the host-neutral-procedures directive (d-cpt-476), which as written binds "every future procedure spec." The dividing line is the same cheap-vs-expensive-to-change axis the foundations directive draws (d-stg-dn6): neutrality is the discipline for what is expensive to change and must work everywhere — the framework's base procedures, which ship in the binary and run against any graph, including remote or hosted ones where git, gh, and the sdd CLI are not on the agent's path. A project's own procedures are the cheap-to-add, surface-specific layer: they live in the project's graph, are authored for a known execution environment, and may freely direct the agent to host-local commands, because the project owns and knows its runtime. So d-cpt-476 sharpened d-stg-dn6 toward base procedures (host-neutral served text); this sharpens the same principle the other way — project procedures are exempt from the neutrality rule and may be runtime-coupled. Anticipated follow-on, noted but not committed here: procedures may later carry an explicit declaration of the environments they depend on, so a host-coupled project procedure announces its runtime requirements rather than failing opaquely when run somewhere it cannot reach.
