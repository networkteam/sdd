One confrontation with reality outperforms an arbitrary amount of review over the artifact, and the two are not interchangeable currencies — so plan, implementation, and evaluation guidance should each treat "it met reality once" as a distinct requirement rather than one checking method among equals. The episode that makes this concrete: four independent review agents ran four lenses over the session store-relocation implementation — proportionality, architecture, acceptance criteria, and a data-safety code review — and returned merge-ready with zero blockers (20260726-195621-s-tac-0hg); the first run against a real accumulated store then failed on the primary path within seconds, and separately revealed that the committed acknowledgement prompt is invisible on an actual terminal (20260726-203237-s-tac-jit). Christopher's formulation: running it once for real beats a hundred agents doing theoretical review.

The reason is structural, not a matter of reviewer diligence, and it is not particular to code. Reviewers — human or agent, however many — reason over the same artifact the author reasoned over, and inherit the author's model of what it will meet. Adding review rounds multiplies scrutiny of that model without ever testing it. Reality disagrees with the model for free, because it holds facts the artifact cannot supply: an accumulated store contains the shapes a format actually wrote across its own history, a terminal has a width, a reader has their own context, an audience has its own reaction. None of that is derivable from the thing under review, so no amount of reading recovers it. The graph already recorded this twice — real-tool smoke testing catching what mocks could not, precisely because domain logic was well covered (20260423-145830-s-prc-lgz), and an implementer-run simulated client passing where a foreign agent session found the defect in minutes (20260716-155256-s-prc-686). Both were available and neither fired, which suggests the lesson does not survive as insight signals alone: it has to sit in the guidance for the moves where the omission happens. It is also the complement of the review regime's other failure mode (20260726-200257-s-prc-cbl): that insight says repeated adversarial rounds manufacture undecided defensive work, this one says they cannot substitute for the one run that would have caught the defect — the same rounds that produced the strict decoding also certified it.

The generic distinction the base procedures can carry — and it must be generic, since they ship knowing nothing about code or any other kind of work — is where an outcome's truth lives. Some checks re-examine the artifact: tests written from the same understanding, reviews, readings, critiques. Others confront it with something outside it that gets a vote. Which specific outside matters is entirely project- and work-dependent — real data, a real terminal, a real user, a real reader, a real deployment — and the procedures should not attempt to enumerate any of it. That per-project shape is exactly what the graph-resident rule layer is for: rules keep the base process lean while letting a project state its own constraints (20260608-190808-d-cpt-30v), attaching and firing at the relevant junctures through the activation mechanism (20260622-084244-d-tac-eho). So the split is: the base procedures carry the distinction and the demand; rules carry what counts as reality here.

Applied across the three surfaces, still generically. Plan capture: the plan-authoring gap (20260706-215247-s-prc-38f) already asks that each acceptance criterion name how it will be checked — "a test, or another verification or validation method" — and already insists the shipped procedure stay generic with per-project shape supplied by rules. What this adds is that those methods are not equivalent: for any criterion whose truth lives outside the artifact, naming an inspection is not naming a check, and a plan whose criteria are all satisfiable without meeting anything is under-specified. Implementation: closeout should not be able to claim such a criterion met by inspection alone. Evaluation: this is already the outer lens's intent (20260703-200000-d-prc-evl) — the framework fixes the posture and leaves its concrete meaning to the project — but the posture is currently weak enough that an inner-style judgment can pass for outer, which is precisely what happened here.

What exactly each surface should require, and whether this lands as procedure guidance, as rules attaching per project, or as a sharpened definition of the outer lens, is open and belongs in dialogue.
