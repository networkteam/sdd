Remote non-Git SDD deployments lack branch-and-merge semantics that keep captured graph entries coupled to the fate of work which may later be merged or abandoned. The local implementation lifecycle in 20260713-214251-d-prc-pop achieves that coupling through base and work branches: implementation captures live with the work branch and become part of the base graph only when the work lands, so abandoning the branch also abandons its entries. Reasoning from the explicit mutation-authority direction in 20260713-214050-d-cpt-65i exposes the missing remote analogue: an MCP server backed by a canonical non-Git GraphStore can accept captures during external work, but without logical branching those entries enter the canonical graph even when the associated work is later discarded.

The first branch-targeting delivery is deliberately local-Git-only and must not implement a push/write/pull synchronization protocol for a separate local checkout. It should, however, preserve a storage-neutral extension seam so a future remote GraphStore can fork a logical branch, receive branch-scoped captures, merge accepted work, and abandon rejected work without depending on Git. The open design work is to define branch identity and isolation, merge and conflict semantics, abandonment behavior, and the capability surface through which the implementation procedure offers those operations without assuming Git.
