Remote runtime instances backed by a canonical non-Git graph store still lack a logical work-lineage lifecycle that can keep branch-scoped captures, recovery state, and eventual merge or abandonment fate aligned without borrowing Git semantics. The local base/work lifecycle in 20260713-214251-d-prc-pop makes entries follow the work branch and reach base only when the work lands; a remote canonical store without an equivalent fork keeps captures even when the associated external work is rejected. This remains the missing remote analogue of the explicit mutation-authority model in 20260713-214050-d-cpt-65i.

“Remote” now needs three distinct cases. A desktop or hosted client using a non-Git canonical store needs native logical fork, merge, and abandon. A runtime instance sharing a server-side Git workspace with its coding agent may later reuse Git-backed target acquisition. A runtime instance separate from an unpushed local checkout would instead require an explicit push/write/pull synchronization protocol; logical graph branches do not by themselves synchronize code, and the first local delivery must not grow that protocol. Direct authorized capture into a connected repository under 20260713-214523-d-cpt-n8z is another sibling capability: it selects an existing external repository-and-branch authority, whereas this gap concerns creating and governing isolated lineages inside one non-Git graph authority.

The open design must define logical branch identity and generation, fork base and isolation, branch-aware reads, merge and conflict semantics for immutable entries and attachments, abandonment and audit retention, and capability discovery by procedures. Expected graph revision remains graph-state concurrency control, not proof of lineage; the same-name recreation case exposed by the local plan means a future remote branch design must explicitly decide whether targets carry stable fork identity in addition to a human branch name.

The recovery model crystallized in 20260715-170623-d-tac-2ko also belongs at this boundary. No branch-scoped intent may replay automatically. Fork deletion, repository revocation, unknown apply outcomes, unfinished finalizers, and terminal abandon-unknown must remain queryable and auditable without forcing non-actionable history into work lanes. Branch merge or abandonment must specify what happens to unresolved mutation intents, while runtime recovery events remain infrastructure state rather than automatically becoming graph entries.

Authorization is likewise capability-shaped rather than engine policy: the shared engine must present distinguishable fork, merge, abandon, target-write, recovery, and cross-principal ownership facts, while each runtime instance's wiring decides who may perform them. The future design should determine whether logical branching is an optional subsystem capability beside the unchanged storage-neutral GraphStore contract grounded in 20260712-194427-d-tac-wjq, how a runtime advertises that capability, and how base procedures offer branch modes only when supported.

This signal replaces 20260715-113417-s-cpt-vxd because the earlier wording treated remote operation too uniformly, used the obsolete term “deployment,” and predated the explicit apply/recovery, lineage-identity, authorization, audit, and capability-discovery constraints. It does not expand 20260715-170623-d-tac-2ko: the first delivery remains local-Git-only and preserves these seams without implementing remote branch lifecycle or synchronization.
