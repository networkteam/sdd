Codex CLI enforces a hard per-tool-output token budget — approximately 10K tokens by default as of version 0.144.5 — truncating any tool result that exceeds it before the model ever sees the content; recorded as harness reference knowledge for SDD's standing multi-harness commitment (20260628-130414-d-cpt-kvb). The truncation is a marked middle-cut: head and tail are retained and an explicit `…N tokens truncated…` marker is inserted in place, so a JSON envelope typically still parses while interior content is silently gone, and a warning names the loss (observed live: `Warning: truncated output (original token count: 13749)`, 3,749 tokens dropped mid-payload). Dropped content is not recoverable retroactively — re-requesting the same oversized payload truncates identically. The budget is configurable via `tool_output_token_limit` in `~/.codex/config.toml` (available since roughly 0.59); community reports cite a 10KiB/256-line variant in earlier releases. Equally relevant for engine design: this Codex harness invokes MCP tools from a JavaScript execution wrapper where tool results arrive as runtime values and the budget applies only to printed output — an agent can store a response unprinted (`store("sdd_replay", r)`), keep it fully intact inside the exec runtime, and re-emit it later in capped chunks (`load(...)` plus per-line slicing), which is exactly how the truncated catch-up serve was recovered in the live evaluation that surfaced this behavior (20260719-122103-s-tac-jom). Two design consequences follow: any single MCP response above the budget silently degrades on a default-configured Codex host, and replay-based recovery works only on harnesses that permit unprinted retention — serve-side size discipline is the only host-independent guarantee. Verified against the Codex session rollout log on 2026-07-19; the full evidence record (timeline, verbatim log quotes, per-lane measurements) is attached to the surfacing evaluation gap.
