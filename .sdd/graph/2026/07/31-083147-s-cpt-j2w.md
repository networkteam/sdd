The circling has a structural cause rather than a behavioural one: in this repository SDD is both the work being built and the instrument used to build it, and the boundary between the two is never named. There is no shortage of outward work here — the format, the code, the thing people adopt — but nothing distinguishes it from observation about how the instrument is being used in the current session.

The two behave differently under check, which is why the boundary matters. Product work has an external referent that can contradict you: code fails, a build breaks, someone cannot use the thing. Meta-observation has no such referent — the only available check is the framework's own record, so grounding a claim about the graph in the graph is circular by construction. Correctness collapses into internal consistency, and internal consistency is precisely what resemblance-matching produces. The check that ought to catch the error is made of the same material as the error.

Because the boundary is unnamed, the two mix freely, and this is the sharper half. In an ordinary project, noticing something about your tooling is a digression from the work, and that friction is what stops the noticing from becoming the work. Here both are legitimately in scope and indistinguishable in the record, so each meta-observation can be captured as though it were work on the product, and each capture raises further observations about how the capture went. Nothing marks where to stop, because nothing is off-topic — and the uncheckable side quietly borrows the credibility of the checkable one.

So the remedy is not more care, and not more outward work, since outward work is already what this project is. What is missing is that the boundary is never drawn explicitly — not in dialogue, not in the record. Other projects have it by construction, which is part of what adoption is worth beyond validating the framework (20260628-130020-d-stg-ous); here it would have to be drawn deliberately, and no mechanism for drawing it yet exists.
