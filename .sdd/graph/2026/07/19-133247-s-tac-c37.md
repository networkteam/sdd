The session store is bound to the server's launch directory (`.sdd/sessions/` inside whichever checkout the server started in), so a server launched in a worktree of the same logical project sees an empty session list — sessions that metadata explicitly binds to the project (`github.com/networkteam/sdd`) become undiscoverable from a sibling checkout. Observed live in the implementation flow: a user starts in the repository root, asks for worktree-based implementation, the agent creates the worktree — the sdd server launched at the root keeps its session files in the root's `.sdd/sessions/`. If the user then follows the harness's suggestion to resume the agent session from inside the worktree, the freshly launched server looks in the worktree's own `.sdd/` and cannot find the session. The working workaround — keep the MCP server rooted at the repository root and only then have the agent enter the worktree — is exactly the kind of implicit launch-context knowledge the placement rule was written to eliminate. This is the session-store instance of placement-by-convenience: the config-and-state placement directive (20260708-184318-d-cpt-6cq) files every kind of state by whose fact it is, and already moved the vector index — per-machine derived state — into a machine-global content-addressed store shared by a checkout, its worktrees, and the connected cache precisely to end per-checkout fragmentation. Sessions fit the same category: per-machine operational state, never committed, logically keyed by project identity rather than checkout path. The endorsed direction (Christopher, from live use) is therefore to move session storage into a machine-global per-project store — keyed by repo identity the way the index store is keyed by (repo-id, embedder-fingerprint) — so every server for the same project sees the same sessions regardless of which checkout it was launched from, and `list_sessions`/`resume_session` work identically from root and worktree. This composes with the missing session branch binding (20260719-124038-s-tac-cwx): store locality answers where sessions live and are found, the branch binding answers where a session's captures land — together they make worktree-based sessions seamless; it also extends the launch-context drift family analyzed for graph mutation authority (20260713-121507-s-prc-akz) from the write side to session discovery. Open design points: the store key for identity-less repos (the placement directive left the same question open for the index store), concurrent multi-process access from several checkouts at once (the CAS-versioned append model already assumes concurrent writers, and per-session file locks exist today), migration of existing in-tree session files, and whether session scratch/staged blobs move with the store.
