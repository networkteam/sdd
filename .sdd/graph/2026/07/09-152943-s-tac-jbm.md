Text-only `sdd search --repo` can still hide first-time connected-cache clone or pull work behind a footer labeled `indexing`, leaving a smaller opaque cross-repo read path after the slice-4 vector-index progress fix. Surfaced by the inner code evaluation 20260709-152356-s-tac-6n3 while reviewing 20260709-141700-s-tac-jbs. The slice correctly wires vector-mode connected index builds through progress callbacks, which addresses the main 35-minute silent embedding hang from 20260708-164711-s-tac-k50. But the CLI currently shows the same transient `indexing` footer for any cross-repo search, while text-only search performs only cache freshening: clone or cooldown pull, then a pure text read. That path has no progress callbacks, and the search view hides Info logs because `StreamLogs` is false, so the only clone/pull feedback appears if the operation warns or fails. The practical effect is lower severity than the original gap — no embedding progress is missing — but a first text-only cross-repo search against an uncached repo can still look mislabeled or quiet during real work. The likely fix is to separate the cache-freshening phase from index progress in the CLI surface: either use a distinct label such as `syncing`/`connecting` with streamed logs for text-only cache work, or only show the `indexing` progress footer when vector fill can actually report progress.
