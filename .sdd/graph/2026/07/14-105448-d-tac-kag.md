SDD will make legacy session compatibility non-blocking at runtime and migrate legacy sessions only through an explicit, retryable `sdd init` flow. This plan addresses the v0.16 startup and migration gap in 20260714-103304-s-tac-rcv while keeping the ordinary engine path simple: current-format sessions work normally, legacy or unreadable legacy files never prevent a fresh session or healthy-session listing, and no session is rewritten merely because a >=0.16 runtime encountered it.

The read boundary will discriminate the legacy event-line shape from the current session-store envelope on every scan. Listing omits legacy records, so a pre-0.16 server may continue creating its own sessions without re-breaking a newer server. Direct access to a legacy handle fails with a typed, host-neutral “session migration required” result; it must not tell an agent to invoke a local command. This applies the engine host-neutrality rule in 20260707-134311-d-cpt-476 while leaving migration guidance to the local CLI surface.

The migration belongs in `sdd init`, building on its established “run whenever things change” lifecycle in 20260418-151212-d-tac-r5g. When legacy sessions exist, an interactive init asks the user to confirm that no session server is actively using the repository. Declining skips only session migration: normal init refresh and migration work continues, the legacy files remain intact, and a later init asks again. Non-interactive execution never infers consent; migration requires an explicit opt-in carrying the same acknowledgement. This deliberate user gate replaces liveness heuristics: pre-0.16 processes do not honor current holder locks, so no implementation can prove their absence reliably.

After confirmation, init migrates every legacy session independently and losslessly. Legacy engine events are wrapped in the current stored-event envelope with synthesized session metadata, and any per-session staging directory and attachment handles are migrated into current staged-blob storage. Each session replacement is atomic and idempotent. A malformed session remains untouched; init logs an error naming its filesystem path, continues migrating other sessions, and exits non-zero after the sweep if any session failed. A rerun processes only records still in legacy form. If an older server later creates another legacy record, newer runtimes continue ignoring it and a future init offers migration again.

This operationalizes the migration work deliberately deferred until a second concrete format by 20260712-194427-d-tac-wjq without introducing a versioned directory, automatic takeover, or background conversion. The maintenance surface stays confined to format discrimination, one legacy-to-current converter, init orchestration, and their conformance tests.

## Acceptance criteria

- [ ] A sessions directory containing any mix of current, legacy, and malformed legacy JSONL records never prevents >=0.16 startup, creation of a fresh session, or listing of healthy current sessions.
- [ ] Runtime listing ignores legacy records on every scan; a legacy record created later by a concurrently running pre-0.16 server remains non-blocking.
- [ ] Direct runtime access to a legacy session returns a typed migration-required result whose engine-facing text contains no CLI command or host-local instruction.
- [ ] `sdd init` detects remaining legacy sessions and, in interactive use, asks for explicit confirmation that no session server is actively using the repository before changing any of them.
- [ ] Declining session migration leaves every legacy session untouched, completes all other normal init work, and causes a later init to offer migration again.
- [ ] Non-interactive init never migrates sessions without an explicit opt-in that carries the active-session acknowledgement.
- [ ] After confirmation, init converts every valid legacy event log into the current envelope without changing its engine-event payloads, session identity, participant, label, timestamps, or resumable instance state.
- [ ] Migration carries legacy per-session staged files and attachment handles into current staged-blob storage so a resumed capture retains its staged evidence.
- [ ] Each session migration is atomic and idempotent: interruption or rerun cannot produce a mixed-format session, and already-current sessions are not rewritten.
- [ ] A malformed legacy session remains untouched, emits an error containing its filesystem path, does not prevent other sessions from migrating, and makes init exit non-zero after the full sweep.
- [ ] Rerunning init after partial success retries only the legacy sessions that remain.
- [ ] Tests cover ordinary upgrade, declined migration, successful parked-session replay, staged-attachment preservation, partial failure with continued progress, non-interactive refusal without opt-in, and a new legacy record appearing after an earlier migration.
