The release workflow should be ported from a Claude-only skill to a graph-local project procedure, as the first real dogfood of authoring a custom procedure and of whether base-facts knowledge is reachable without falling back to source. The release flow lives today as a project-scoped Claude Code skill (s-prc-lep): a six-step arc — survey the changes, propose the version, draft the notes, gate on explicit confirmation, ship, verify. Porting it to a procedure authored in this graph would be the first custom (non-base) procedure, exercising the authoring path that survives only in the Go source today. It is legitimate as a host-coupled project procedure under the base-vs-project neutrality scope (d-cpt-70z): its instruction units may carry the git, gh, and sdd calls directly, and the confirm-before-ship step becomes a real user chooser the agent cannot talk its way past. The deliberate value is dogfooding graph-local procedures, and the sequencing is the point: build the base facts and procedure-authoring knowledge first (d-cpt-dtv), then author the release procedure using only what the graph serves and the facts that can be pulled — so the build doubles as the evaluation of whether that knowledge is actually accessible. If it can be authored without reading the Go source, base facts work; if not, the gap persists. Retiring the release skill once the procedure reaches parity is the endpoint. Note that some release knowledge — the version-bump convention, the recovery anti-patterns (no --draft, no re-tag) — is reference material that may itself belong in facts rather than step instructions; the fact/step split gets settled in the doing.
