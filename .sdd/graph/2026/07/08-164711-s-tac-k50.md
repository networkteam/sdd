Long-running cross-repo operations give no progress output, despite the cross-repo work's claimed conformance to the terminal-experience architecture — `sdd repo add`'s clone and the first cross-repo search's index build both run silently, the latter for ~35 minutes, reading as a hang. Surfaced during the outer validation of cross-repo references (20260708-151819-s-tac-cr0). `sdd repo add` prints through bare fmt.Printf with no styling and no clone progress; the first `--repo` search silently lazy-fills the connected cache index (embedding ~400 entries via a local Ollama model) with zero output. The closing done (20260708-010505-s-tac-94a) claimed the cross-repo work 'conforms to the terminal-experience architecture via slog and reporter callbacks' — the callbacks exist, but the transient-progress and styled-feedback surface the architecture commits to (20260628-131545-d-cpt-dgk) was never wired for these operations. This is not a new problem so much as an unpaid one: that architecture's own chain already carries a closed gap about the local index/search progress bar reading as a hang, and the cross-repo path does not even show that bar. A second, related gap sits alongside: there is no eager way to index a connected repo — `sdd index` has no `--repo` / `--all-repos`, so the only path to build a connected cache index is to trigger a search and endure the silent build. Proposed direction (not yet a committed decision): wire the clone and the connected-index build through the terminal-experience coordinator so both show honest transient progress on the human path (and clean slog on the non-TTY path), and add `--repo` / `--all-repos` to `sdd index` for visible, eager pre-indexing instead of an invisible blocking build on first search.
