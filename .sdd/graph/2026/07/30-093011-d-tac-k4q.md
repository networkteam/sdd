The engine's session subsystem is rebuilt in four slices — sessions resolve across known store locations and append to the log they were resolved from, one filesystem store implementation replaces the parallel pair behind ports that can finally enumerate and delete, a lock-free garbage collection removes ended sessions once they are past a retention window and drains pending declarations, and concluding becomes terminal with continuation carried by a fresh session rather than a revival — realizing the read-side compatibility model committed in 20260729-082254-d-cpt-4tx.

The subsystem being replaced is measured, not estimated. On `main`, `local/local_sessionrelocate.go` is 3,025 lines and `local/local_sessionmigration.go` 2,453; together with the session store, blob store, transition marker, containment machinery and lock files, the `local/` session-and-store surface is roughly 7,400 lines of production Go. Every line of the first two exists to carry session material safely to a new location. Nothing moves any more, so they go entirely rather than being consolidated.

**Slice 1 — resolve across locations, append where resolved.** A session is looked up across the locations sdd has ever written: the in-tree `.sdd/sessions/` directory, the identity-less machine-global store, and the current repository-identity store. Whatever location answers is the location subsequent events append to, which is why no home policy is needed — writing where you read leaves nothing to reconcile. Older on-disk shapes are tolerated and converted by the versioned retirement table shipped in 20260727-091833-s-tac-d9n, which becomes the whole of compatibility. Everything relocation-shaped is deleted with the two engines: the `--migrate-sessions` flag and its acknowledgement prompt, the tombstone, the three-state transition marker, the standing relocation notice threaded from `cmd/sdd/serve.go` into every door, listing and info response, and the store-routing policy engine that currently lives in `cmd/sdd/storepaths.go` operating on `local` package types from `package main`. Location resolution replaces it and lives in `local/`. Old locations drain through ordinary collection, not a migration pass — the same mechanism, no special case for the transition. A session whose only copy sits under a superseded repository identity is simply not found, which is how this plan carries the acceptance that 20260724-145631-s-tac-vxs asked to have settled: no breadcrumb, no registry, no rekey. That case is reachable only by deliberately changing an established repository identity, never by an ordinary version update, which changes no key at all.

**Version coexistence is a stated property of Slice 1, not a hope.** The relocation model required an offline window by construction — its acknowledgement prompt existed precisely to make the user stop every `sdd serve` process and restart agent sessions before anything moved. Read-side resolution needs none of that: the binary can be replaced while sessions are running, because a running process keeps appending to the log it already resolved and a session started afterwards resolves independently, so two binary versions coexist over one store with no offline step, no acknowledgement and nothing to restart. What this does require, and it is not free, is tolerance in both directions on enumeration. The retirement table gives a newer binary the ability to read older shapes; it gives an older binary nothing, since no table can describe fields that did not exist when it was built. So a session a binary cannot read must be skipped, with every other session still returned — backward conversion is a property of the table, forward tolerance is a property of enumeration, and a drop-in upgrade needs both. This is the one place where compatibility is a design obligation rather than best effort.

**Slice 2 — one store, one containment, ports that can sweep.** `application/blobstore.go` offers Stage, Stat, Open, Retain and Release, and `application/sessionstore.go` offers Create, Load, List and Append; neither can enumerate owners or delete anything, which is the structural half of 20260728-004924-s-tac-gtx — collection is not merely unwritten but unwritable. Both ports gain enumeration and deletion as part of their published surface, so a third-party composition reaches collection through the same contract the local one does. Behind them, one filesystem implementation replaces the rooted and path-based pair (production only ever constructed the rooted variant), and one crash-safe publish helper — temp write, fsync, rename-no-clobber, directory fsync — replaces the two transaction engines' per-payload state machines, quarantine-then-finalize deletion, rollback of already-verified publishes and resumable manifests.

**Slice 3 — garbage collection over the sessions that are safe to remove.** A session is removable when two plain conditions hold: it has ended, by being concluded or explicitly abandoned, and it ended longer ago than the retention period. Removal then deletes its log together with its staged blobs, and a staged-blob owner whose session is already gone is removed as an orphan. A session that has not ended is never removed — it stays listed, and disposing of it is the user's explicit act, which `abandon` already exists for. This is what 20260727-224047-d-cpt-u8o licenses: sessions are scaffolding whose life is that of a conversation, which is what justifies removing them at all and what bounds how long keeping them could be defended.

Retention is a delay, not an archive, and it revises one clause of the anchoring directive deliberately rather than by drift. 20260729-082254-d-cpt-4tx settled retention as collection at the moment of conclude with explicitly no grace window; dialogue overturned that clause. A session that has just ended is precisely the thing you want to read when something went wrong inside it, and deleting it at conclude destroys the evidence exactly when it becomes interesting — inspectability for debugging is worth a bounded window, and nothing in the scaffolding calibration argues against keeping scaffolding briefly. So concluded sessions are kept for a configurable period, expressed in days and settled through the existing configuration surface rather than a new flag, with a proposed default of 14 days as a starting value rather than a design commitment. The complexity cost is one comparison inside a pass that already enumerates, with no new state and no second mechanism, and it is still not an archive: nothing survives the window.

The pass is driven opportunistically at `sdd serve` startup, and there is deliberately no user-facing command for it. That is the moment the store is opened anyway, it involves no procedure and no served instruction, so collection is host-neutral by construction rather than by rule. The operation itself is one command dispatched to one domain handler, with two callers over it: local startup, and the exported API for a hosted composition that wants it on a recurring schedule, since a long-lived server starts once and would otherwise never collect again. Two adapters over one command and one handler, deliberately not a second parallel surface — 20260721-151122-s-tac-spe records what that costs on the entry write path, and this is the shape that avoids repeating it.

The pass is lock-free and optimistic, and this is the proportionality decision worth stating explicitly. An ended session is by construction never written to again, so two processes starting at the same moment derive the same target set and both simply delete; an already-deleted path is success rather than an error. That removes the last reason for coordination in this subsystem: no lock, no transaction, no manifest, no recovery verb, no resumable state. Nothing needs recovering because nothing is left in an intermediate condition that matters — a partially removed session is a log or a blob set that the next start re-derives and finishes, and the target set is recomputed from scratch every time rather than remembered. What the pass does protect, and the whole of it: it never removes a session that has not ended, never one inside the retention window, never one an in-flight declaration still claims, and never one the running binary cannot read — an unreadable session may belong to a newer binary, so it is skipped and left alone rather than treated as garbage. What it deliberately does not protect against: concurrent removal of the same target, which is idempotent; partial removal, which the next pass completes; and interruption at any point, which leaves nothing to reconcile. Per 20260726-200257-s-prc-cbl, anything beyond that short list has to arrive with its own stated threat model rather than as an implementation detail.

The drain of pending declarations rides the same pass, since it touches the same store and the two genuinely couple at one point: a session an in-flight declaration still claims is not removable, which is 20260729-092849-d-cpt-tm1's requirement that grooming skip whatever a declaration still claims. That directive also asks that every pending declaration be swept at a defined trigger and that the sweep be exercised by the real path; server startup is that trigger, and it fires on ordinary use rather than waiting for anyone to invoke it, which is what the stranded-notice pile shows the alternative produces. One unreadable payload must not abort the pass either: that is the clause 20260727-091833-s-tac-d9n deferred rather than dropped, deferred into the consolidation because that is where the transaction machinery lived — the machinery is gone, so the property lands here, on the only whole-store pass that exists. The blast-radius reasoning that rejected eager migration applies unchanged: a single unreadable log stops that log, not the run.

Having no age threshold on *unended* sessions, no liveness inference and no heuristic is a principled call rather than a shortcut. Deadness is not observable: liveness inference was deliberately removed from the session model, an agent conversation can legitimately stay open for weeks under one handle, and nothing distinguishes a dialogue someone parked from one they will never return to. Any threshold there would guess, on the user's behalf, at the one thing only the user knows — and a wrong guess deletes work someone intended to resume, which is the failure this whole rebuild is calibrated against. The retention window is a different thing entirely: it applies only after the user has already declared the session over, so it decides how long to keep something finished rather than whether something unfinished is alive. The honest cost is that collection reclaims only as much as the conclude rate allows, which is why Slice 4 carries a teaching half rather than treating it as polish. That sessions go unconcluded and accumulate is an observed failure mode; how often it happens is not something any single machine or project can establish, so no rate is claimed and none is needed — as 20260728-004924-s-tac-gtx already argued, a store with no collection path is a gap at any rate above zero.

**Slice 4 — concluding is terminal, continuing is a new dialogue.** 20260729-084833-s-tac-3be records that after a session concludes the door re-serves the spent session with no pending step and nothing to do, while starting a move silently revives it — a path served nowhere, which stalled a live agent until the user guessed it. Conclude keeps its current shape and gains no gate: it lists the threads still open as perspective and then ends the session, leaving them behind. That is deliberate rather than lossy by oversight — a session must be closable without first discharging everything raised in it, since a dialogue can always leave matter untackled, and which loose ends deserve carrying is the judgment of the user driving the session, not the engine's. Because ending drops those threads as resumable work, the served instructions must consistently keep that listing specific about what each thread is rather than reducing it to a count; today's serve already does this and the rebuilt path must not regress it. What is added is the way on: the conclude response states that the session is finished and that continuing means opening a new one, and a move attempted against a completed session is refused carrying the same instruction instead of silently reviving it. Opening that new one mints a new handle, distinct from the spent one, which the agent carries forward in its place — the identity of a dialogue is its handle, so a new dialogue cannot reuse the old identity, and handing back the just-concluded handle is exactly the connection-as-identity confusion the observed episode consisted of. The new session is otherwise an ordinary fresh shell that the agent seeds — a label, and the relevant move started with what it already holds — which works precisely because the conversation is continuous where the session is not, so nothing has to transfer across the boundary. The retention window does not reopen any of this: a finished session's log is kept to be read, not to be resumed, and inspecting what happened is a different act from carrying it on. It is bounded by 20260719-124405-d-cpt-0tm: door-opens-fresh governs the no-handle case only and must never widen into a rule that re-initializes — attaching to a still-running session by handle projects its pending step at its current position with the state and schema to continue it.

Ending also has to be something a user knows exists, and this is the second half of Slice 3's value rather than a nicety beside it. Someone arriving from any other agent tool closes a window or a tab; there is no reason they would suspect a dialogue has an official end, and sessions left open in a store are what that looks like at rest. Listing stale sessions back at them is possible but poses friction and reads as an accusation, so the answer is teaching plus guidance instead: the shell's served instructions make ending a normal part of the arc, and when a dialogue reaches a natural stopping point the agent offers to end it — having first checked what is still open and said so — rather than waiting for a word the user has never heard. Whoever simply stops is not punished for it, because the session stays listed and resumable, which is today's behaviour and the right floor. The default path becomes an ended session, which is what makes collection effective in practice.

**Where the seven items of 20260726-195959-s-tac-wg5 land.** They land inside the rebuild rather than ahead of it as behaviour-preserving deletion, and the accounting is worth stating because three of them dissolve rather than get done. Its items (3) merge-the-two-transaction-engines and (5) collapse-the-transition-marker dissolve — both engines and the marker are deleted outright, since a design with nothing to move has no transaction to run and no transition to mark. Item (1) becomes a single `os.OpenRoot` for containment, retiring `trusted_store.go` and the `rooted_regular_*` and directory-sync ancestor-pinning apparatus. Item (2) is the collapse to one store implementation in Slice 2. Item (4) is the deletion of the three `//go:build windows` files in `local/`, which `.goreleaser.yaml` — darwin and linux only — has never compiled. Item (6) is the routing engine leaving `cmd`. Item (7), consolidating effective-branch precedence currently split between `readTarget` and `captureMutationTarget` with an asymmetric work-branch honor, is the one item independent of relocation and survives as a genuine consolidation; the semantics it consolidates are those of 20260722-112853-d-tac-ln1, whose declared branch binding and machine-global per-project store keyed by repository identity stand intact while its relocation mechanism does not.

**What this plan is not, and does not wait for.** The convergence half is out of scope: the unified command-and-handler write path called for by 20260721-151122-s-tac-spe is not built here, and this plan does not block on it. That independence is deliberate and it is what makes the declaration drain real now rather than notional — it sweeps the pending-declaration surface that exists today, including discarding the pre-rule intents 20260729-092849-d-cpt-tm1 declares non-convergeable, so the sweep is exercised by the real path from the first day rather than waiting for a mechanism that would make it exercisable later. When the unified write path lands, the pass gains a better declaration shape to sweep, not a new job. The formal retirement of the relocation directive chain is likewise not this plan's work: 20260729-085604-d-tac-wgc already closed 20260723-192701-d-tac-g7r and 20260724-123026-d-tac-vhk together in one entry, deliberately, so that no active refinement was left stranded on a retired target. This plan deletes their code; it performs no retirement act.

**The discipline a greenfield owes.** 20260726-200257-s-prc-cbl is the reason the mass being deleted exists: individually reasonable defensive fixes, each accepted as an implementation detail requiring no decision, compounding past any proportionality check. A rewrite has no test pressure to constrain it, so every defensive addition is accepted only against a stated threat model and a size estimate. Two are stated up front, alongside the collection pass's own list above. Path containment is kept — threat: a defect in key derivation or location resolution writing outside the state root, credible because keys are derived from repository identity and a stable root hash; mechanism: one `os.OpenRoot` at the store root, not a pinning apparatus. Symlink-rebinding hardening is rejected — its threat model requires a local attacker with write access to the user's own XDG state directory, at which point containment defends nothing, and it cost ~530 lines. The size budget for the rebuilt subsystem — location resolution, one store implementation, one publish helper, the collection pass — is 1,200 to 1,500 lines of production Go against ~7,400 today, and exceeding it requires a stated reason rather than an accumulation of reasonable ones.

Per 20260728-083647-d-prc-pck the criteria below state outcomes observable from outside the work; the internal decomposition above — ports in `application/`, one implementation and location resolution in `local/`, one command dispatched to one domain handler with startup and the exported API as its two adapters — is a design constraint, not an acceptance criterion. Per 20260726-204112-s-prc-ogp the resolution and collection criteria are met only against a real accumulated store rather than a constructed one, and the coexistence criterion only by actually replacing the binary under a live session; a review that reasons over the artifact does not satisfy them. Deliberately, no criterion is stated as a count or a byte figure taken from one store: this graph's own machine is a single heavy dogfooding checkout, and a threshold read off it would encode that special case into a subsystem meant to serve many projects and roles.

## Acceptance criteria

- [ ] A session written by an earlier binary — in the in-tree `.sdd/sessions/` directory or in the identity-less machine-global store — is listed and resumable by handle from the current binary with no migration step run first, and events appended to it afterwards are readable in that same log file where it was found.
- [ ] Replacing the sdd binary while agent sessions are running needs no stop, no acknowledgement and no offline window: each running session keeps appending to the log it already resolved, a session started afterwards works alongside it, and both appear in listings from the binary that can read them.
- [ ] A session log a binary cannot read — whether written by an older or a newer version — is skipped with every other session still listed and resumable, and is never removed on the grounds of being unreadable.
- [ ] `sdd init` exposes no session-store flag and never prompts about session storage; `sdd info`, session listings and the door serve carry no relocation or pending-transition notice; no tombstone is written or consulted; and a session whose only copy lies under a superseded repository identity is absent from listings with no surface offering to move it.
- [ ] Concluding a session ends it and the response names each thread it is leaving behind, states that the session is finished, and states that continuing means opening a new one; the session's log stays readable for inspection until its retention period expires.
- [ ] The door called on a connection whose session just concluded returns a new session under a new handle, never the concluded one; no served operation revives a concluded session, and a move attempted against one is refused with a response naming the new-session path; a still-running session resumed by handle comes back at its pending step with its collected state and the schema to continue it.
- [ ] In a real dialogue that reaches a natural stopping point, the agent offers to end the session and names what is still open, without the user needing to know any term for it; and someone who instead simply stops finds the session still listed and resumable rather than lost or reported at them.
- [ ] Starting the server against a real accumulated store leaves every session that ended longer ago than the retention period gone together with its staged blobs, every session that ended more recently still listed and readable, and every session that has not ended untouched with its open threads intact; afterwards nothing is reported as actionable and no pending declaration remains outstanding.
- [ ] The retention period is configurable through the existing configuration surface and takes effect on the next start, with no rebuild and no per-invocation flag.
- [ ] A composition running the same collection on a schedule through the exported API produces the same removals against the same store as a local start does.
- [ ] Two processes starting simultaneously against one store both complete without error, neither failing on work the other already did, and nothing is left half-removed that a later start does not finish.
- [ ] Nothing is removed that has not ended, that is inside its retention window, or that an in-flight declaration still claims; a staged-blob owner whose session is already gone is removed; and an unreadable log or blob is reported with the pass continuing over the rest rather than aborting.
- [ ] An external Go composition implementing the session and staged-blob ports passes the conformance suite including collection — enumerating owners and deleting retained blobs are reachable through the published port surface, not through local-only code.
- [ ] For every combination of session branch binding, explicitly supplied capture branch and configured default, the effective target branch stated in capture playback is the branch the write lands on, with an explicitly supplied work branch honored identically on both the read and write side.
