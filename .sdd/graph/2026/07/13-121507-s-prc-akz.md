Engine-backed worktree implementations lack an explicit graph-authority binding, so lifecycle records can land in different checkouts or branches whenever a long-lived workflow server and its host agent do not share one stable working directory. The local server resolves one graph directory at startup and keeps all engine reads and writes on that handler, while worktree creation, entry, exit, and artifact commits belong to the host. The Git auto-commit adapter separately uses the server process working directory rather than being directory-bound to the repository that owns the graph path. Nothing names or validates one canonical mutation authority across those boundaries, so graph placement and commit placement can drift silently.

In Claude Code, an uninterrupted session launched on the base checkout and then moved with `EnterWorktree` leaves the already-running stdio server bound to its launch context, which makes WIP and done placement appear safely base-bound. That is not a general guarantee: a session started with `claude --worktree` or in a desktop-managed worktree launches from the isolated checkout, and `EnterWorktree` relocates the transcript so a later restart or resume can launch a fresh server there. The same implementation can therefore begin with a base-bound marker and continue with worktree-bound completion writes. In Codex, the generated project registration uses `cwd = "."`, while local and managed-worktree tasks run from different checkout roots; the server consequently binds to whichever task root launched it, and changing how the task was started changes where engine mutations land.

This extends the earlier directory-bound worktree friction recorded in 20260601-164525-s-prc-8bp, but the prior remedy addressed entering the worktree and carrying local state, not the engine's canonical mutation authority. The harness/git/recipe boundary in 20260628-130403-d-cpt-h4l leaves worktree lifecycle with the host, yet the engine still needs to bind every mutation in one implementation run to an explicit authority and fail loud if a resume or host transition would redirect it. The implementation procedure in 20260706-170000-d-prc-imp currently creates the marker and closing entry through the engine without recording or validating checkout identity. The project-aware runtime plan in 20260712-104530-d-tac-1mb binds sessions to a logical project, but one repository ID spans multiple worktrees; the local adapter therefore still needs a distinct canonical store/checkout authority, a directory-bound Git finalizer, and a landing check that prevents an unmerged worktree commit from being described as canonically shipped.

The attached exploration compares three shapes. The recommended direction is one canonical graph authority per implementation instance, with every agent runtime's worktree treated only as the artifact workspace; following the engine into the worktree or orchestrating explicit dual authorities both open larger session-migration and reconciliation surfaces. The unresolved gap is to turn that direction into a mechanical binding, resume check, runtime-specific launch coverage, and cross-worktree test matrix rather than another agent-followed convention.
