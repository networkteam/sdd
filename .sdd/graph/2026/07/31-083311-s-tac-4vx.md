The engine's capture procedure cannot express a multi-target supersede, so retiring two entries with one replacement has to leave the engine and run on the `sdd` CLI. Its `supersedes` param is declared as a single entry ID and rejects an array outright — `start capture: param "supersedes": expected entry ID (string)` — while every other layer of the system accepts several: supersede validation checks only type agreement (decision→decision), the fork lint fires solely when one entry carries two superseders, so a merge of two chains onto a single head passes silently, `sdd new --supersedes` takes a comma-separated list, and this graph already contains entries that supersede two predecessors at once. The capture surface is the only place the shape is unavailable, and 20260703-094500-d-prc-cap is where it lives — that procedure establishes that supersede captures are not a separate move but the shared spine entered through params, which makes the param arity the whole constraint.

**The instance.** Correcting the delivery-as-convergence rule (20260730-171311-d-cpt-0cv) required superseding both the original contract and the successor that claimed in prose to replace it but never wrote the edge. Neither single-target option was acceptable: retiring only the original leaves two live copies of one rule, and closing the successor instead would strand the attention it had earned, because closure deliberately does not inherit. So the entry was written through the CLI with pre-flight skipped, outside the engine's playback-and-confirm path — the confirmation was given by hand in dialogue instead, which is a substitute for the gate, not the gate.

**Why this is more than an inconvenience.** It is precisely the failure shape 20260707-134311-d-cpt-476 names: an operation not reachable through an engine capability, forcing a fall back to a host-local command — the same defect as the groom procedure's CLI-based stale-marker removal and `sdd lint` fork detection that the directive already governs. The fallback worked here only because the graph is local. On a remote or hosted graph the CLI is not on the agent's path and does not point at the same graph, so a correction of this shape would have been unwritable rather than merely awkward.

**What is not settled.** Whether the fix is simply widening the param to a list, or whether a merge deserves a deliberate shape of its own. Retiring two lineages with one entry is not the same act as retiring one, and the playback probably ought to say so — naming both predecessors and what each contributes — rather than rendering a longer list the user is left to read carefully. The natural home is 20260726-193730-d-tac-zrh, whose reusable new-draft construction and validation boundary already owns what capture can legally build and where per-kind structural invariants live; folding this in there avoids a second pass over the same boundary.
