`sdd index --repo` and `sdd index --all-repos` accept `--force` but do not force connected repo member indexes, leaving the expected repair path ineffective for corrupt or stale connected stores. Surfaced by the inner code evaluation 20260709-152356-s-tac-6n3 while checking the eager connected-index surface added in 20260709-141700-s-tac-jbs. The placement plan 20260708-185833-d-tac-nhx asked for `sdd index --repo <id>` and `sdd index --all-repos` as the eager, visible pre-indexing path; because this command already has a `--force` flag described as re-embedding every entry, a user would reasonably expect it to repair both local and selected connected indexes. The implementation only passes `Force` to the local `BuildIndexCmd`. The connected side uses `BuildConnectedIndexesCmd`, which has no force field, and the handler always calls `LazyFill` for each member repo. That means a connected index whose manifest fingerprint still matches, but whose chromem store is corrupt or otherwise stale, will be skipped instead of rebuilt. This is not an architectural placement problem — the handler-side spine is in the right package — but a reliability and UX gap in the command contract exposed by the slice-4 code review.
