After the connected index is built, cross-repo queries run noticeably slower than local ones — roughly 1–3s versus ~0.6s — with the cause suspected but not yet profiled. Observed during the outer validation of cross-repo references (20260708-151819-s-tac-cr0): a tiny local graph answered in ~0.18s, the local sdd graph in ~0.6s once warm, and the cross-repo query (the local second graph plus the connected sdd cache) in ~1.15s, 2.35s, 3.17s across runs. Prime suspects, reasoning from the code paths: each CLI invocation is a fresh process that cold-loads the whole flat chromem index from disk (sdd's is 129 MB), and the cross-repo path probably opens the connected cache store more than once per query — the prepare/lazy-fill step opens it, then the search finder opens it again; on top of that each cross-repo query runs a cooldown-gated git freshness check, which likely explains the run-to-run variance (a pull firing when the cooldown lapses) more than the absolute number. This strains the search-index plan's explicit bet that a flat scan is 'sufficient at current and projected scale' (20260504-235258-d-tac-lqr), because cross-repo multiplies large graphs per query. Note one mitigation already exists structurally: the long-lived MCP server can keep indexes warm, so this is largely a CLI cold-start cost, not inherent; and the machine-global single-load index direction (20260708-164528-s-tac-eql) would reduce it further. Low priority — profiling to confirm where the time actually goes is deferred.
