The procedure language conflates declared state, report collection, expression routing, and agent-visible projection behind a closed Go-owned type system, limiting graph-local procedure extensibility and forcing bespoke engine predicates for ordinary data-dependent behavior. This gap supersedes the narrower generic-state-projection question (20260719-135225-s-cpt-m8n): subsequent procedure design exposed that projection policy, state typing, expression power, collection semantics, validation reuse, and diagnostics are one connected authoring-model problem rather than independent refinements.

The limitation is deliberate v1 architecture, not an accidental missing operator. The workflow-engine plan chose a deliberately poor guard grammar made only of Boolean combinations of zero-argument registered predicates and a closed engine-owned variable vocabulary (20260702-220449-d-tac-ry0); the shipped core implements exactly that contract (20260702-235429-s-tac-8io). Procedure state can use arbitrary field names, but values are limited to registered base types and `list<T>`. Procedures cannot declare local records or enums, guards cannot read a state field or compare it with a literal, and simple routing such as `entryKind == "aspiration"` requires a purpose-built Go predicate. Model validation can then leak into alternative transition expressions instead of remaining at one reusable boundary.

The live kind-gate failure demonstrates the cost. Alternative transitions were all evaluated for diagnostics, so one incomplete draft received actor, role, focus, and ordinary-entry failures together (20260722-141852-s-tac-dhn). Full type capture deliberately does not wait for this redesign: its plan uses temporary explicit kind predicates plus one central `reportedDraftValid` helper and current optional-collect behavior (20260726-193730-d-tac-zrh). That contained approach is a compatibility bridge, not the target procedure language.

Collection currently overloads per-report and accumulated-state semantics. A nonoptional `collect` field is required in the report schema for each call and participates in the step's missing list; an optional collect is patchable without resending and does not gate cascade. Domain completeness is separately expressed by predicates. The redesign must distinguish three things explicitly: fields a report at this step may patch, conditions accumulated state must satisfy before the step can leave, and structural validity of the accumulated domain object. Incremental reports must remain possible without weakening completion or duplicating required-field rules.

The target state model has two layers. The generic engine owns a composable core type algebra and permits procedure-local enum and record declarations, so a project-authored procedure can introduce its own typed state without adding Go fields or engine base types. The application registers namespaced framework types and pure helpers—such as `sdd.entry-kind`, `sdd.entry-draft`, `sdd.ref`, and `sdd.validEntry`—that carry SDD model semantics. Required-field and kind validation stays in those reusable model helpers; graph-dependent validity and session evidence remain distinct helpers. Graph and session objects are opaque to expressions and are queried only through controlled registered functions.

Expressions operate over the declared typed environment and need at least field access, literals and equality, Boolean composition, collection operations, and calls into a closed helper set. They must be side-effect-free, terminating, deterministic, and statically checked when a procedure loads. Load-time macros may provide concise syntax, but only as expansion sugar; they cannot become another home for domain validation. Expr is a candidate to evaluate, not a selected dependency: a design plan must compare its Go integration, type checking, diagnostics, function-exposure boundary, dependency surface, and reversibility against a smaller owned evaluator.

Projection belongs to the same declaration model. The concrete missing-state-on-resume failure has already been fixed: resume serves now carry a generic collected-state map with trust machinery excluded and deterministic truncation and omission (20260719-190406-s-tac-y9a). What remains open is declarative policy—normal versus resume timing, field visibility, deduplication, compression, omission, and whether current state alone is sufficient or a filtered trajectory and completed-ancestor context is sometimes necessary. Whatever shape is chosen must preserve the handover-fidelity invariant that durable intent is shown or explicitly named when compressed or omitted (20260719-124405-d-cpt-0tm).

One further meta-layer remains intentionally open inside the investigation: shared executable type definitions could themselves become graph entries, allowing procedures to extend a graph-resident model. That would introduce loading, trust, versioning, supersession, validation, and cross-repository dependency semantics for code-like graph content, so it is not assumed by the local-type design. The follow-up design must evaluate and either bound or defer that layer explicitly.

A coherent engine-design plan should therefore treat state declarations, types, expressions and helpers, collect/completeness semantics, relevant diagnostics, and serve projection as one authoring contract. It must preserve the current engine's host-neutral procedure loading, pure evaluation, report trust boundary, replay determinism, explicit compression, and single model-validation source while making project-local procedures genuinely extensible.
