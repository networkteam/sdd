Shipped compact param signatures in the shell's live move listing (commit 0cf9ec8), so a caller sees each move's accepted start inputs where the moves are offered rather than only through a rejected start_procedure call (closes s-tac-ay5). The engine's procedureList now renders `- <canonical>(<name>?: <type>, ...) — <summary>` per move — e.g. `capture(anchor?: entry-id, closes?: list<entry-id>, supersedes?: entry-id)`, `engage(anchorHint?: text)` — with paramless moves left bare and optional params marked by a trailing `?`. Params are parsed straight from each head's spec (ParseSpec, no registry validation needed) and rendered in name order via VarType.String().

This is the runtime mirror of the `next` serve fix (builds-on s-tac-xeq), which surfaced schema on the serve that offers the next choice. start_procedure's own input schema can't carry per-procedure params — it is reflected from a Go struct once at server startup, while procedures are graph entries resolved per session — so the fix rides the shell-orientation serve where moves are already enumerated. Two rejected alternatives: a dedicated describe-procedure read tool (full-schema fidelity but adds a tool and a lookup the caller must know to make) and enriching only the rejection errors (cheapest but keeps discovery-by-rejection, which the gap called an avoidable failed call). The listing is served once per session, so the signatures cost little on the hottest serve.

Verified: go vet, golangci-lint, and the full engine + mcpserver suites green, plus a new test asserting the orientation carries the capture signature and that paramless moves render without empty parens.
