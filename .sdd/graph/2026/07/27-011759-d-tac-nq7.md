The sdd CLI adopts github.com/erikgeiser/promptkit for its interactive prompt surface, composing promptkit's models through the existing shared program runner rather than delegating to its RunPrompt. The deciding reason is discoverability: promptkit's prompts put more of what the user can do on screen — labelled options, filtering, pagination, validation — where the hand-rolled components make each of those something we build one at a time, and where a typed y/N affordance can vanish entirely. Christopher's call.

This supersedes by capability, not by fault, the four generic prompt components delivered days earlier as the final slice of the coordinator-lifecycle directive (20260723-141831-s-tac-i0d), which collapsed six hand-rolled models into four with independently verified behaviour preservation. That consolidation was the right move for the code we owned; the question this answers is the next one — whether owning it at all still pays once the surface is consolidated and still growing. `sdd init` alone prompts for graph directory, participant, language, agent targets, scope, overwrite-modified and session-store relocation.

The adoption is bound by four constraints, three of them found by running the library rather than reading it (20260726-204112-s-prc-ogp).

Compose, never delegate. promptkit's prompts are ordinary bubbletea models — verified by driving a selection.Model through Init, Update and View from caller-owned code — so they are embedded and run through the shared runner, keeping it the sole tea.NewProgram site as the coordinator-lifecycle directive requires (20260723-114725-d-tac-z6r). RunPrompt is barred: it would construct its own program and route around the per-surface policy the terminal-experience architecture depends on (20260628-131545-d-cpt-dgk) — coordinator on stderr with no signal handler so ctrl+c cancels the work context instead of killing teardown, prompts on interactive defaults.

WrapMode is set explicitly at every call site. selection.New defaults it to promptkit.Truncate: rendering the real relocation prompt at width 60 cut it at the terminal edge and discarded the rest — the same defect just repaired in 20260726-203525-s-tac-q8r, and in one respect worse, because the library drops the text itself rather than the terminal clipping what was written. promptkit.WordWrap preserves everything on word boundaries and is the default this project takes. Reading the source suggested the opposite conclusion, since promptkit imports reflow's wordwrap and exports a WordWrap helper; only executing it revealed which one New installs.

Filtering is opt-in, not inherited. selection.New installs a filter unconditionally, so a two-option confirm renders a "Type to filter choices" line until it is disabled — noise on a binary choice, valuable on a long list. Each prompt decides.

Styling reconciles with the existing palette. promptkit's templates and styles are brought under internal/styles and the concept-keyed colour scheme (20260628-130407-d-cpt-vye) rather than shipping their own theme alongside it.

The cost accepted: one more dependency on a pre-1.0 charm stack, tracked as maintenance surface rather than effort. It is reversible — the models are ordinary bubbletea widgets behind our own facade — and it adds no second TUI runtime, since promptkit v0.12.0 requires the same charm v2 module paths at equal or lower versions than this repo already carries (bubbletea v2.0.2 against our v2.0.7), so Go resolves to ours. Most of internal/cliout/tui's prompt code is deleted in exchange, including the width plumbing added by the repair that raised this.

Deliberately not done here: this stays out of the relocation repair, whose branch merely carries this entry. Folding a dependency migration into a data-migration fix is the compounding described in 20260726-200257-s-prc-cbl. It gets its own session, and the follow-up must verify the adopted prompts the way the defect was found — rendered at a real width, not asserted.
