SDD's auto-commit hangs indefinitely — rather than failing — when it runs inside a long-lived MCP server (`sdd serve`) and the host git signs commits but the server process can't reach the ssh-agent. `gitCommit` shells out via plain `exec.Command` (no timeout) and inherits the server's controlling terminal, so the `git commit` → `ssh-keygen -Y sign` subprocess, finding no agent, tries to read the key passphrase from the TTY and is suspended by SIGTTIN, never returning. The entry and its attachment are written to disk but never committed; the `next` MCP call blocks to the client's 300s timeout and reports only a generic "timed out awaiting tools/call"; the stuck subprocess is not reaped, wedging the session. This slips past the failure-only graceful-degradation design (s-prc-1yb) precisely because a hang is not a failure. It is environment-triggered: the identical commit succeeds under Claude Code, which forwards `SSH_AUTH_SOCK` to the server, whereas Codex launches the server with a filtered env that drops it. Empirically, with no controlling terminal `ssh-keygen` fails in ~0s instead of hanging — the lever a fix can pull. An environment-side mitigation (forwarding `SSH_AUTH_SOCK` via `env_vars`) belongs in the pending init Codex-registration work (d-tac-wfl). Surfaced dogfooding the v1 engine's narrow MCP surface (d-tac-ry0) in a Codex session.
