The vector index is stored locally per repo and duplicated into a per-connected-repo cache, so a repository that is both developed and connected is embedded twice on the same machine — the index should instead live in one machine-global, content-addressed store shared across checkout, worktrees, and connected cache. Surfaced during the outer validation of cross-repo references (20260708-151819-s-tac-cr0): the first cross-repo search spent ~35 minutes re-embedding a graph that was already embedded 129 MB deep in its own .sdd/index, because the connected-repo cache builds a separate index (~/.cache/sdd/<repo-id>/.index) of the same content under the same embedder. This is not per-local-repo waste — the cache index is keyed by repo-id under the global cache root and is reused across every local graph that connects to that repo, which is correct; the duplication is specifically between a repo's own local index and its cache index when you both develop and connect it (dogfooding), plus a third copy per worktree, which today is carried by a Claude-Code-only .worktreeinclude file copy — a harness dependency at odds with the agent-agnostic foundation (20260628-123931-d-stg-dn6). The storage model predates cross-repo: the search-index plan (20260504-235258-d-tac-lqr) deliberately chose local, per-participant, gitignored, rebuildable indexes — trading coordination cost for per-participant experimentation across embedding models — and put committed/distributed indexes and background-daemon indexing out of scope; the cross-repo design (20260606-003344-d-cpt-s6q) then added 'the local repo keeps its own index, the cache holds the others.' But cross-repo introduced a single shared embedder (one vector space), which undercuts the per-participant-embedder-freedom rationale that justified keeping indexes local and unshared — so the storage question is reopened, not inherited. Proposed direction (not yet a committed decision): one machine-global, content-addressed index per (repo-id, embedder-fingerprint) under the cache root, shared by the checkout, its worktrees, and the connected cache — safe because the index is additive and content-hashed and reads already intersect with entries present in the current graph (d-tac-lqr's branch reconciliation), so a single store serves many branches; with no .sdd/index in the working tree, the .worktreeinclude index copy disappears too. Migrate an existing local index into the store via `sdd init` (the post-clone / post-update contract), move-if-absent / merge-or-skip, never clobber. Open mechanics for the eventual decision: how to key identity-less (no repo_id) repos, and concurrent multi-process writers (chromem-go persistence is not built for multi-process writes).
