The engine flow is SDD's main working mode: /sdd-engine — procedures served step by step over the sdd MCP server — is the primary way to run sessions, and the skill-driven /sdd flow will be deprecated soon rather than kept in indefinite parallel operation. This makes committed direction out of the endgame the engine planning activity (20260702-180130-d-tac-tdh) already named — dogfooding replaces the skill flow outright, the thin skill replaces /sdd, and the full renders retire — and sharpens the engine architecture directive (20260702-174833-d-cpt-3yw), which shipped the engine MCP-first as the dogfooding driver but left primacy implicit. The reasons are practical: process investment lands in procedure specs where guide and gate derive from one source while the corresponding /sdd skill prose is frozen under the authority rule, so the skill flow only falls further behind; and running two flows confuses agents in live use — a Codex run selected the legacy $sdd skill over $sdd-engine after compaction, recorded with the note that removing the legacy skill may resolve the ambiguity (20260710-234710-s-tac-53t). The call surfaced during docs structure planning (20260715-174037-d-cpt-eke), where deciding which flow the user documentation leads with forced it: docs present engine mode as the way SDD works, with /sdd at most a legacy note. Deprecation mechanics are follow-up work this directive demands, not settled here — what retires when, what remains as a pointer skill, how installed renders and sdd init behave, and the communication to existing users.
