The engine's capture write gate rejects an entry with a bare `validation failed: N issue(s)` that names neither the failing rule nor the offending field, journals no event for the failure, and offers no recovery transition — so the agent can neither see nor fix what broke, and the capture instance wedges. This is a second, independent instance of the write-gate opacity first recorded from the focus/involvement side (s-prc-g0j), reproduced here from an unrelated cause while running the capture procedure (d-prc-cap) in another project: a `plan` decision was captured with `closes` pointing at a design-exploration *decision*, which the graph validator rejects (only a `done` signal — or a `directive` closing a contract/aspiration/procedure — may close a decision; every other decision-closes-decision must use `supersedes`). The write surfaced that as nothing but `validation failed: 1 issue(s)`.

The originating session's event log makes the opacity three-layered: (1) the returned message names neither the violated rule nor the offending field; (2) the failing write command wrote no result or error event at all — the log ends at the `playback → write` transition, leaving no durable trace to diagnose from; (3) the instance then sits at the `write` gate with no pending chooser, so neither adjust nor abort is reachable — the only escape is park-and-restart.

Two failure modes compound it beyond what s-prc-g0j recorded. First, the message does not distinguish mechanical graph-validation from LLM pre-flight, and the two have completely different recovery paths: the agent read the rejection as a pre-flight finding and spent the session chasing the user-only override — which only skips pre-flight, never mechanical validation, so it could never have worked. Second, `closes` is a frozen start parameter, not a field the adjust chooser exposes (adjust collects only body/refs/topics/confidence/intent), so even a fully legible error could not have been corrected in place. Diagnosing the real rule required reading the Go source (`handler_new_entry.go`, `graph.go`) — the same push-only reach failure recorded in s-cpt-7wc, hit again from the error-diagnosis side.

What the gap calls for: write-gate rejections must surface as an actionable re-serve — naming the failing rule and field, distinguishing mechanical validation from pre-flight, journaling the failure so a post-mortem is possible, and routing back to a step that can actually fix it (frozen start params like `closes` included) — rather than an opaque, unlogged wedge.
