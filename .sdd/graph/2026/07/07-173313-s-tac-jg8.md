Graph loading in the sdd codebase happens at three different lifetimes — per-call in finders, per-write in handlers, and a held per-session snapshot in the workflow engine — and a code-level review found no hard CQRS break but a real drift: the engine's snapshot freshness rests on a hand-maintained refresh protocol that is one forgotten call away from silent staleness. CLI commands and MCP free read tools load per call through Finder.LoadGraph, the single IO loader the read side has owned since the CQRS migration; handlers reload per write through their injected reader — both conform to the layering (d-cpt-ah1). The engine, though, holds a mutable graph field that the MCP shell reassigns imperatively: refresh calls sit after each writing command and at the entry of the advance verbs, so post-write freshness inside a session is verified correct today — a capture's fidelity step does see the just-written entry — but the contract is manual and distributed, with no compile-time or test guard; a future write command that forgets its refresh would silently serve a stale snapshot, and serves outside the advance verbs (re-knocked session start, park, abandon) already render orientation material against the last-refreshed snapshot. Conceptually, ownership of "what the current graph is" belongs to the read side, not a mutable engine field poked from outside — the same drift family as the open read-side leak (s-tac-m09), where query structs courier pre-resolved graph data into finders. The engine core and MCP shell shipped under the v1 engine plan (d-tac-ry0) without an explicit graph-lifetime decision; the free reads also rebuild the full graph from disk on every call beside the session snapshot, a cost that multiplies under multi-repo fan-out. Surfaced while refresh-reviewing the cross-repo references plan (d-tac-rpm), whose model.MultiGraph must thread every read path — CLI, MCP read tools, engine serves, capture-time resolution — through one graph-access seam. The attached review maps every load/hold/read site with file-level evidence and recommends the resolution shape: a finder-owned GraphSource ("give me the current graph", request/advance-scoped memoization, invalidate-on-write) replacing the engine's mutable field with a read-through provider and deleting the scattered refresh calls — giving MultiGraph exactly one insertion point, with cache clone/pull staying handler-side.
