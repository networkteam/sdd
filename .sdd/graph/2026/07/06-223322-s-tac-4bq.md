The engine's `show` tool already resolves an unambiguous short ID to its full entry, but nothing advertises that, so agents resolve short IDs by reading graph files off disk — a path that silently breaks for any agent whose graph isn't mounted locally.

Observed across two fresh sdd-engine sessions: handed a pasted short ID in the `d-tac-…` form the framework itself tells agents to cite in dialogue, the agent first reached for `search` (content retrieval over summaries and bodies, where a bare suffix matches nothing), then fell through to `ls`/`find` over the graph directory. That works on a local checkout and fails the moment the graph lives behind a remote or hosted server — directly against the agent-agnostic foundations directive (d-stg-dn6).

The resolver was present the whole time. `finders/show.go` runs every id through the graph's short-form resolver, so `show` on a short ID returns the full entry — the same unambiguous `{type}-{layer}-{suffix}` resolution the CLI shipped in s-tac-mca, inherited on the MCP surface for free. Two things hid it: `show`'s `ids` field is documented as "full entry IDs to show", which reads as *short IDs won't work*; and `search` resolves nothing, so the natural first reach is the wrong tool. (The anchor gate also pins a strict full-ID pattern, so a short ID must be resolved before it can be reported — resolution belongs up front regardless.) The observation surfaced while dogfooding the v1 engine (d-tac-ry0).

Agreed fix, kept minimal — no procedure branching:
- Correct `show`'s `ids` description to state it accepts an unambiguous short ID (`{type}-{layer}-{suffix}`) and resolves it to the full entry.
- Extend the dialogue shell's served orientation — at its existing "Cite entries by short ID in conversation; pass full IDs to tools" line — so that, because reads are free, an agent resolves any short ID to its full form via `show` up front (before or while doing anything else) and never resolves an ID by reading graph files. The MCP server instructions, which already flag the read tools as always free, reinforce the same point.

A dedicated `search` ID-lookup mode was considered and set aside as redundant: `show` already covers resolution.
