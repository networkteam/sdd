The engine's session log records inbound reports, step transitions, and write snapshots — but never the responses the engine returns, nor the errors from a failed transition — so a session cannot be diagnosed from its log after the fact. The log in question is the append-only JSONL event log the v1 engine plan committed to (d-tac-ry0), and it is built for replay: deterministic state reconstruction, where returned serves are re-derivable and only state-changing events need persisting. s-cpt-m6m already framed that log as “trajectory evidence and forensic record,” but a failed transition shows it is not even a complete forensic record — when a command aborts (a rejected write, say) the transition never commits, so no event is written at all; the log simply ends at the last good transition, with no trace of what was attempted, what came back, or why it failed. This is exactly the no-trace layer of the write-gate wedge (s-prc-0p1): the originating session's log ended at the `playback → write` transition with zero record of the failing write. Even on success the log stores only that a step was served (its name) and the write's snapshot hash — not the returned payload — so “what did the agent see, and how did the engine answer” can only be re-derived by replay, and an error cannot be reconstructed at all. The asymmetry is the crux: the agent's inbound reports are logged verbatim, while the engine's outbound responses and errors are not logged at all.

What the gap calls for: record each transition's outcome — the response returned and any error raised — as first-class log events, so a session is analyzable and debuggable post-hoc, in addition to (not instead of) the replay log's state events. This is a different axis from resume fidelity (s-cpt-m6m): that asks whether the log holds enough to *continue* a parked dialogue; this asks whether it holds enough to *diagnose* one.
