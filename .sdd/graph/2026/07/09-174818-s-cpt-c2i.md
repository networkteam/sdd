Nothing prevents two `sdd serve` connections from binding and driving the same engine session at once, so a second connection can silently relabel, advance, or abandon an in-flight move in a session another connection is actively working — observed live in this very session. Each agent harness runs its own `sdd serve` process, sessions persist as append-only JSONL event logs, and resume_session binds a connection to a session by replaying that log; nothing marks a session as exclusively held by a live connection, so two connections can operate one session concurrently with no mutual exclusion. This session (s_20260709-161700-ed59582d) caught it in the act: at 16:43:30, 54 ms after this connection's own capture served its summary-verification step, a concurrent Codex connection bound the same live session, relabeled it 'Cross-repo references release plan', started its own move instance, and at 16:43:51 abandoned that in-flight instance with the reason 'User asked for a fresh session, not continuation of the existing cross-repo release readiness thread' — a reason from the other agent's dialogue, not this one's. The append-only log now carries duplicate seq numbers (13–19) and two distinct i_3 instances from the two connections, so the log's own ordering and instance-identity guarantees broke under concurrent writers. Two facets, then: a foreign connection can mutate and tear down in-flight moves in a live session, and the shared event log is not safe under concurrent writers. Harm is bounded by graph immutability — committed entries are durable, and this connection's captures completed intact — but session-level state (label, move position, open-thread and in-flight-instance lifecycle) can be trampled and the event log corrupted. This is the enforcement rung of the concurrent-session risk the liveness-visibility gap (20260706-231416-s-tac-y2z) raised from the display side: flagging liveness in the open-threads listing helps a well-behaved agent avoid accidentally resuming an active session, but a listing hint cannot structurally stop a concurrent bind — the guarantee has to live below the display. It also reopens the concurrent-session-management concern closed as premature (20260408-172318-s-cpt-rgf) explicitly to be revisited 'once concurrent sessions become a regular workflow pattern' — a condition now plainly met, with human and AI agents routinely running parallel sessions against this graph. Fix direction, not yet decided: a session-level exclusive hold keyed per session, acquired by the `sdd serve` process that binds it — a live-bound session refuses or defers a second connection's bind/resume, with clean takeover only once the holder is genuinely gone. Full forensic evidence — the interleaved event timeline and the abandon record — is attached.
