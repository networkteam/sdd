Every `sdd serve` process re-embeds the entire graph on its first phrase search: the 2026-07-13 root-runtime rebase (76ab150) wired the runtime's SearchIndexStore port to the process-local, empty-at-start MemorySearchIndexStore, dropping the machine-global disk index (`<cacheRoot>/index/<repo-key>/<fingerprint>`, centralized locking, introduced in 5038f85) that the CLI path still uses — `sdd search --query` stays warm and fast while every new MCP session pays a full cold re-embed, and dependency-repo runtimes in the same process share the same empty store.

Measured 2026-07-16 on the myhogast-sdd graph (257 entries, qwen3-embedding:8b via local ollama): document batches of 64 chunks took 42-64s each and a cold first phrase search answered after roughly 8 minutes; once the index is warm in the process, the query embed itself takes about 200ms. Until today the cost was masked by the invalid-spec regression (20260716-115947-s-tac-szl): vector search failed at the spec gate before any embedding started, so fixing that gate exposes this cost to every session.

Hypothesis: the serve path needs an adapter implementing the application SearchIndexStore port on top of the existing persistent machine-global index store, so MCP sessions share the CLI's warm cache instead of re-embedding per process.
