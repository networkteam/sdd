The acknowledged offline session-store migration is unusable on a real store: it aborts on the format's own recent history, and its acknowledgement prompt is invisible on a real terminal. Both defects were found by the first outer validation run against this repository's accumulated store (20260726-203237-s-tac-jit) and are folded into one finding because they share one surface — `sdd init`'s relocation path — and Christopher wants them fixed urgently, before the pending identity transition can complete on any real machine.

First defect — strict decoding rejects the format's own history. Session logs are classified solely on presence of a top-level `version` key (local/local_sessionstore.go:552): absent means legacy and the file is copied byte-for-byte untouched; present means current and every line is strictly decoded with `DisallowUnknownFields` (local/local_sessionrelocate.go:1667, :1732). The `Holder` field was deleted from the session model on 2026-07-18 in commit c80af3a without bumping the codec version, so any session written before that commit carries `version:1` and a `Holder` object — classified as current, structurally unreadable, and indistinguishable by the codec-version gate sitting directly below the decode. One such file aborts the entire sweep during manifest planning, so nothing migrates at all. The tolerance boundary was drawn once at the pre-0.16 legacy line and then treated as permanent while the format moved underneath it. This regresses the permanent read-compatibility contract (20260602-203349-d-cpt-i2x), whose rule is that a format-breaking change ships its conversion path rather than leaving older records unreadable. The fix must restore that property for session persistence — the working model is the earlier legacy-session migration (20260714-140424-s-tac-fco), which tolerated the old shape and converted it. Whether tolerance comes from relaxing the decode on the read path, from a codec bump with an explicit upcast for removed fields, or from widening the legacy escape is open and belongs in dialogue; what is not open is that a current binary must read every session shape it has ever written, and that one unreadable payload must not abort the whole sweep.

Second defect — the acknowledgement gate is implemented and unreachable. The confirm does fire on an interactive stdin (cmd/sdd/main.go:1264) and does render `[y/N]` with a focused input (internal/cliout/tui/prompt.go:121). But the prompt string (cmd/sdd/main.go:1305) concatenates a two-clause payload census, the instruction to stop every `sdd serve` process and restart its agent sessions, and the question into a single ~330-character sentence, which bubbletea's inline renderer truncates at terminal width — cut mid-word, with the affordance and cursor off-screen. The user reads a status line, presses a key, and the always-default-N resolution silently routes to the declined branch; the view is then cleared on exit, leaving no trace in scrollback. The committed acknowledgement path is therefore effectively unreachable interactively, which leaves the explicit-acknowledgement directive (20260723-192701-d-tac-g7r) unmet in practice, and breaches the terminal-experience architecture's per-command UX commitment and coordinator-owned terminal (20260628-131545-d-cpt-dgk). The machine-shaped prompt text is part of the same defect rather than a separate one: even correctly wrapped, a sentence fusing a payload census, a precondition instruction, and a question does not read as a decision to make. A fix must make the census, the precondition, and the question distinct lines with the `[y/N]` affordance always visible, and must not depend on the terminal being wide.

Both defects sit in the delivered store-relocation slice of the closed branch-binding plan (20260722-112853-d-tac-ln1); the decided migration semantics — acknowledged, move-if-absent, identity rewrite, tombstone, resumable manifest — stay unchanged, and the safety design held in the failing run (loud failure during planning, before any payload moved, store intact). One sequencing constraint: the simplification gap over the same relocation core (20260726-195959-s-tac-wg5) already targets the two parallel transaction engines this fix must touch, so the two efforts should be ordered deliberately rather than run into each other. Finally, the reason this reached a real machine at all is that no run was ever made against a real historically accumulated store — whatever fix lands should be proven the way the earlier migration was, on a copy of a real repository rather than a fixture.
