Every artifact authored in this repository must keep two audiences explicitly separated: instructions that govern how *this* project is developed, and reference knowledge that ships as the generic SDD framework. The discipline exists because this graph dogfoods SDD to build SDD — the framework's own development is conducted through the framework — so both audiences are permanently co-present in the same sessions and often the same files, and the nearest surface is rarely the right one. SDD's target scope is deliberately broad: it must serve many kinds of project, and not necessarily software implementation at all — a roastery, a design practice, an operations team are as much the target as a Go codebase. Anything absorbed from this repository's own habits into a framework surface narrows that scope silently, and the narrowing is hard to notice precisely because it reads as correct here.

The test is audience, not location. Ask who the content is for: if it only makes sense to someone working on this repository — its language and layering choices, its build and commit mechanics — it is project guidance and must stay project-local. If it would still hold for a project SDD knows nothing about — the kind and layer vocabularies, the ref-kind taxonomy, retirement paths, immutability and derived status, the evaluation lenses, and the generic procedures defining the graph moves every project needs — it is framework knowledge and belongs in what ships. Process machinery is governed by the same test as reference knowledge, and procedures are the clearest case of it: the generic move ships, while whatever specializes that move for one project stays local. The surfaces holding either side are themselves in motion, the project-local home most of all while the rule system is still in flight (20260622-084244-d-tac-eho), so a discipline pinned to particular files would be obsolete before it was useful; the boundary is what endures. The two failure directions across it are asymmetric, which is why the discipline is worth naming at all. A framework surface that quietly hardcodes a software-implementation assumption is expensive to unwind, because it reaches every project that adopts SDD and there is no signal from inside this repository that anything is wrong. Project guidance that restates framework knowledge is cheaper, but it drifts out of sync with the shipped definition and then competes with it as a second source of truth.

This is the same base-versus-project line that host-neutrality draws for procedure specs (20260707-142556-d-cpt-70z), generalized from procedures to all authored content, and it rests on the cheap-versus-expensive-to-change axis of the foundations directive (20260628-123931-d-stg-dn6): framework surfaces are the expensive layer and carry the neutrality discipline, project guidance is the cheap, local, freely-coupled layer. It also serves the aspiration that non-developer participants — business owners, domain experts, operators — engage SDD directly (20260422-122523-d-stg-x0l), which presupposes a framework that never assumed its users were building software. The intent is guiding rather than pending: there is no completion point, and the rule applies as standing context to every authoring decision about where a piece of content belongs.
