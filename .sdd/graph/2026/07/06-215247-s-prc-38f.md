SDD has no dedicated procedure for authoring plans or specs — today, writing a plan is just recording an ordinary entry, the same flow used for anything else, with no step that helps shape the plan itself. What a good plan needs for a given project is never described in one place; it just happens. The knowledge is scattered and implicit — a project contract like this repo's CQRS decomposition (d-cpt-ah1) is only one example, alongside AGENTS.md / CLAUDE.md project notes, whatever context the user supplies in the moment, and whatever the agent picks up by looking around the repo — and none of it is a repeatable procedure. A plan/spec-authoring procedure would instead guide the universal authoring arc: ground the draft, break the work into acceptance criteria, and make each one genuinely verifiable by naming how it will be checked — a test, or another verification or validation method — the inner (verification) and outer (validation) checking the evaluate procedure (d-prc-evl) later carries out, then play it back. The procedure SDD ships must stay generic: it knows nothing about any particular framework or codebase shape, and there may be no CLI actions or layers at all, so what a good plan must contain for a specific project is supplied per project, never baked in. That per-project shape is exactly what the coming rule system delivers: the contract→rule migration (d-cpt-30v) folds today's contracts into graph-resident `rule` entries, and the rule `activation` block — `when` for semantic discovery, `matches` for mechanical selection (d-tac-eho) — is how a project's own plan-shaping rules would attach to and fire inside the generic authoring procedure, rather than being loaded globally at the pre-flight gate. Surfaced while planning the summary-hash rip-out, when the question “do we have a procedure for creating a good plan?” exposed that today the answer is no.
