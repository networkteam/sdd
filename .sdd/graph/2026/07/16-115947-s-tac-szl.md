Vector search over MCP fails on every phrase query with `sdd: embedding executor returned invalid spec` when the embedding provider discovers its dimensionality lazily — ollama without a configured `dimensions` value — while the same query succeeds through the CLI (`sdd search --query`) in the same repo and config. Observed 2026-07-16 against the myhogast-sdd graph (sdd 0.16.1, qwen3-embedding:8b via ollama); reproducible on every MCP `search` call carrying a phrase.

This is a regression from the 2026-07-13 root-runtime rebase: 9598a01 added the spec gate in `application.vectorSearch` (Fingerprint set and Dimensions > 0, checked before any embed call), and 76ab150 wired `Dimensions: embedder.Dimensions()` into the serve-side executor — but the ollama embedder holds dims 0 until its first embed response, and the CLI search path never consults `Dimensions()`, which is why it kept working.

Hypothesis: the spec gate and the index-namespace identity demand information a lazy embedder only has after its first real use. Since every vector search embeds the query anyway, dimensionality always arrives with the first genuine call — no probe needed. Fix direction: key the index namespace by fingerprint alone (the fingerprint already pins the model and with it the dimensionality) and enforce dimension consistency where vectors actually meet — embed-batch validation, reconcile, nearest.
