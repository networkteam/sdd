Groom's stale-marker removal now runs through an engine transition instead of the `sdd wip done` CLI, closing the portability gap s-tac-prp. Commit e28a7ad adds a transition-only `wipRemove` command to the MCP shell's registry (reads a report-supplied `staleMarker`, calls the same `handler.FinishWIP` as `wipDone`, no state-colliding writes) and wires it into the groom procedure (20260706-171500-d-prc-grm): a `staleMarker` state field, a `removeMarker` walk option (`collect: [staleMarker], call: wipRemove`), and the walk prose rewritten to take that option rather than shell out. Reusing `wipDone` directly was impossible — its `Writes: [wipMarker]` collides with the state declaration that `collect` requires, per the spec loader's checkCommandWrites invariant — so a dedicated command reading a state-declarable field was the minimal fix. It adds zero MCP tools (transition-only, closed registry) and realizes the host-neutral-procedures directive (20260707-134311-d-cpt-476) for groom's marker path. Verified: a new engine table test drives sweep → removeMarker → wipRemove end-to-end; full `go test`, `go vet`, and `golangci-lint` are green; the built binary's `sdd serve` loads the edited base spec against the production registry. The directive's other groom violation — the sweep step's `sdd lint` fork-detection probe (20260707-134223-s-tac-n5a) — stays open, deliberately out of scope pending its query-vs-reframe decision.
