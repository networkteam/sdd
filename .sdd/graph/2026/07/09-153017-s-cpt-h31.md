The engine offers no discoverable surface for an agent to reorient after its own working context is compacted mid-session: recovery guidance lives only in volatile served prose, and the one call that re-serves a live session's position is both mis-named and, by architecture rule, never offered as resumable. Observed live in an engine-mode session on another project — after a mid-session context compaction, the agent lost its session handle, its open-move instance handle, and the current step's report schema, while the server-side session state stayed fully intact (the MCP connection remained bound the whole time). Recovery took several turns of thrash: the agent reached for the session-start door (which does re-serve, but reads like starting fresh and alarmed the user), then fell back to reading the raw session log off disk to re-identify the anchored move, and finally re-derived the step's fields from memory because no served surface returns a running move's schema without advancing it. The root cause is a channel mismatch against the tier model (d-cpt-h99): tier zero — the connection-time instructions that survive compaction — carries only what an agent needs to not misread a read (signals and decisions, immutability, the door), not how to reorient after losing its place; the reorientation affordances (resume_session, list_sessions) are described only in the tier-one session-start serve, which compaction flattens. So the agent kept the tools it had already used (start_session, next) but lost awareness of the ones it had only read about — and those, plus start_session's re-serve, are all framed for parked or fresh sessions, never a live session whose agent-side context was wiped in place (d-cpt-h99 deliberately does not offer a live-connection session as resumable). This is the same push-only-in-a-volatile-channel shape as the reference-knowledge reach gap (s-cpt-7wc), re-instanced for live session position rather than static reference facts. It is orthogonal to resume fidelity, which is already proven (s-cpt-osk): the parked-and-resumed state survives a full client restart byte-for-byte — the failure here is purely the client-side reach back to that intact state after an in-place compaction.
