Worktree workflow for sdd is harness + git + a skill-resident process recipe — the sdd CLI owns no part of the worktree lifecycle. The seamless experience of moving an agent's session into a worktree and back can only come from the agent harness (`EnterWorktree`/`ExitWorktree` in Claude Code), because a CLI subprocess structurally cannot relocate its caller's working directory; the remaining steps are generic git plumbing (`git worktree add`, merge, `git branch -d`). Neither half justifies a `sdd wip --worktree` command. Instead the worktree process guidance — when to suggest a worktree, how to drive `EnterWorktree`/`ExitWorktree`, and the two-gate conclude (one confirmation to start, one to merge) — lives in the bundled `/sdd` skill, so `sdd init` ships it to every sdd repo and refreshes it on upgrade rather than each repo hand-copying a CLAUDE.md section. This grounds in the agent-agnostic-foundations directive (d-stg-574): the recipe is Claude-Code-specific, and the skill bundle is exactly the cheap-to-add agent-specific layer that directive separates from the expensive-to-change neutral CLI core. Repo-specific setup stays in each repo's files — a `.worktreeinclude` carrying `.sdd/config.local.yaml` + `.sdd/index/` (plus, for dogfooding, the built `bin/sdd`), a `.gitignore` entry for `.claude/worktrees/`, and `worktree.baseRef: "head"`. The decision reverses the commitment to integrate worktree lifecycle into the CLI (d-tac-fla) and retires its implementation plan (d-tac-u07), returning to the original out-of-CLI stance (d-tac-ar2) on scope grounds rather than the session-friction grounds later thought resolved by `/add-dir`. It resolves the three worktree friction points (s-prc-8bp) through this division of labor. The merge-pull half of the sync-strategy directive (d-tac-4ff) stays wanted on its own merit — background sync must not rewrite the shared graph's history — while its content-equivalence merged-check becomes unnecessary once no CLI teardown needs guarding. Adopted as a lightweight experiment at medium confidence; escalate to CLI tooling only if practice shows the skill-plus-harness approach insufficient. See [design note](./07-022834-d-cpt-927/worktree-scope.md) for the rejected CLI-guarded alternative, the `.worktreeinclude` analysis, the recipe sketch, and open follow-ups.
