Synthesis on the workflow-MCP direction, reshaping the decisions queued after the experiment verdict. First: the MCP surface should split into two separately servable tool sets — low-level graph-operation tools (the CLI-parity surface trimmed of its expensive parts: attachments, sync-as-tools, cache machinery — thin dispatch into existing handlers, days not weeks) and the high-level dialogue-loop tools the experiment evaluated. They serve different consumer classes: programmatic agent runtimes want primitives, chat agents need guidance; Christopher is near-certain on the separation. Second: the preferred first consumer for the low-level set is not a minimal demo but porting the full skill and instruction set to a Mastra workflow (20260525-204836-d-cpt-t3j) — a hosted, standalone SDD agent usable by people who bring no agent of their own, potentially itself exposing MCP so other agents can act on it. This revives the original specialist-as-agent shape (20260531-161611-s-cpt-r57) as a distinct product surface serving non-developer access (20260422-122523-d-stg-x0l), while the verdict's no-server-side-intelligence conclusion (20260611-001444-s-cpt-h5c) continues to hold for the lean state-machine path chat agents use. Third, crystallized as a contract candidate: framework concepts and situational instructions must live in exactly one source and render into every surface — skill, state-machine tool responses, hosted agent prompts — because duplicated instruction text has repeatedly missed a surface during framework iteration; this gives the skill-portability direction (20260525-184931-s-cpt-z7l) its anchor. Consequence for the queued decisions: the CLI-parity plan (20260527-210616-d-tac-0v4) is a re-scope candidate rather than a retirement, and the next direction session should settle the two-path directive, the single-source contract, the focus supersession, and the slice-2 plan together.
