Worktree isolation silently fails: after an agent enters a git worktree (`EnterWorktree`), work can land against the base checkout on `main` instead of the isolated worktree, because entering moves only the **shell's working directory** — other surfaces keep resolving to the base repo regardless of CWD. Two surfaces showed this, same root cause:

1. **File-edit tools.** Read/Edit/Write take absolute paths and have no working directory. Paths read during grounding *before* entering keep targeting the base repo, so edits land on `main` while shell commands (git, grep, build) run in the worktree. The change tears in half — neither tree is complete.
2. **`devbox run`.** It resolves to the base project root, so `devbox run build` / `validate-skills` operate on `main` even from a worktree shell; the worktree had to be built directly (`go build`, validator run by hand) instead.

It is a structural trap, not a slip. No friction signals the mistake — wrong-tree paths resolve to real files, so Edit reports success. Verification gives false comfort — tests build the worktree's unedited source and pass on old code; the only tell was green tests beside a freshly built binary missing the feature. And the shared base/main tree means two "isolated" sessions both leaking onto it collide — the hazard the never-`git add -A` rule already guards against. The strongest evidence it is structural rather than a personal lapse: a concurrent session hit the identical failure at the same time, on two distinct surfaces.

Current guidance does not prevent it. The worktree recipe covers marker → enter → conclude but never says "re-anchor to the worktree after entering — re-Read before editing, run tooling from the worktree root," and the general "prefer absolute paths" advice points straight at the trap because the held paths are base paths. This is grounded in the finding that structural enforcement transfers while instruction-carried discipline does not (s-cpt-h5c): trusting the agent to remember a path/root swap is instruction-carried; a hook or harness remap is structural.

Candidate fix directions, to weigh later (not decided here): a re-anchor discipline note in the worktree recipe (re-Read at worktree paths; run tooling from the worktree root, `direnv allow` it); a guard rejecting Edit/Write whose target is outside the active worktree; or `EnterWorktree` warning on / rewriting later edits and tooling that resolve to the base checkout.
