Bring the git-worktree lifecycle back into `sdd wip`, reversing the April stance that kept worktree management out of the CLI (d-tac-ar2), now that `/add-dir` removes the directory-bound-session friction that justified it. `sdd wip start --worktree` records the current branch as the base in the marker, creates the feature branch and worktree (`git worktree add`), and copies the local state a fresh copy needs — `.sdd/config.local.yaml` and the `.sdd/index/` vector index — so search works immediately without re-embedding; it then prints the session-continuation choice (`/add-dir` to continue in this session, or a fresh session in the worktree). The CLI owns the resource lifecycle but not the merge: the agent and skill drive concluding the work — sync the base into the feature branch inside the worktree, build and test there, capture the done signal in the worktree, then `cd` back to the base worktree and merge the feature branch into its captured base. `sdd wip done` then does cleanup only: it rejects unless the current branch equals the marker's base branch (so it can never run inside the worktree it will remove), runs the content-based merged check, removes the marker, deletes the merged branch, and removes the worktree (path re-derived via `git worktree list`). Plain `--branch` (checkout-only, no worktree) is unchanged; this adds `--worktree` as the opt-in path. The lightweight alternative — keep worktrees manual and only document the recipe — was rejected because the index carry-over is error-prone by hand and the conclude flow needs tool-level guards, not just a note. The attached overview ([worktree-lifecycle.md](./01-214708-d-tac-fla/worktree-lifecycle.md)) gives the end-to-end flow with the git interactions; detailed mechanics (exact files copied, marker commit placement, `--branch`+`--worktree` composition) are deferred to a follow-up plan.
