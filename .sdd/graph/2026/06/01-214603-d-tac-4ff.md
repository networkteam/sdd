Make the conclude flow robust against history rewrites by changing SDD's background sync from `git pull --rebase` to a merge pull, and by switching `sdd wip done`'s branch-merged check from commit-ancestry to content equivalence. Merge-pull only adds a merge commit and never rewrites existing commits, so a branch already merged into the base stays an ancestor and the orphaning seen in the conclude incident cannot arise from our own sync; it is also gentler for agent-driven wrap-ups, since a conflict is resolved once rather than once per replayed commit. Because a user or another machine can still `git pull --rebase` manually, the content-based merged check (patch-equivalence, e.g. `git cherry`) is required, not optional — it keeps `wip done` correct regardless of how anyone pulled. The trade-off accepted: merge commits add noise to `git log`, but SDD's narrative surface is the graph and catch-up, not `git log`, so the cost is cosmetic. This changes the pull strategy established by the background-sync infra (d-tac-hsu) while keeping its fetch-cooldown and merge-tree conflict prediction, and requires updating the rebase-shaped conflict guidance (s-prc-jpx). Detailed mechanics — the exact patch-equivalence command, and how or whether sync is paused during a wrap-up — are deferred to the follow-up plan.
