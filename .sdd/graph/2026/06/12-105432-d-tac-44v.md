Take the summary-skip hash over a stable, durable semantic basis instead of the full rendered prompt, closing both facets of the hash instability at the root. Today the skip-hash is `ComputePromptHash(RenderSummaryPrompt(entry).Combined())` — a hash of the entire LLM prompt — which embeds inputs that aren't stable across the create→read boundary: neighbor prose from `refs`/`closes`/`supersedes` targets (drifts on any neighbor re-summarize or `--text` edit) and an `Attachments:` line built from `--attach` CLI order at create but from an alphabetical directory scan at read. The fix hashes the entry's own durable fields (body, type, layer, kind, refs id+kind+desc, closes, supersedes, confidence) plus neighbor identity (id, not prose), excluding neighbor prose, the rendered attachment list, and derived state. The LLM prompt is unchanged — neighbor summaries and attachment context still flow into generation; only the skip-hash basis changes. Migration is accept-either-basis: an entry is current if its stored hash matches either the legacy rendered-prompt basis or the new basis, so settled graphs regenerate nothing and entries migrate only when naturally re-summarized; the legacy basis is dropped once repos have drifted over. Addresses the neighbor-prose coupling (s-tac-pfn) and the attachment-list born-stale facet (s-tac-gcd); see the attached design for alternatives and migration mechanics.

## Acceptance criteria

- [ ] A single canonical hash-basis function computes the skip-hash from durable semantic inputs only — excluding neighbor summary prose, the rendered attachment list, and derived status.
- [ ] Re-summarizing or `--text`-editing any entry leaves the skip-hash of every entry that refs/closes/supersedes it unchanged (neighbor-prose facet; pinned regression test).
- [ ] An `--attach` entry's skip-hash is identical at create (`BuildEntry`, CLI order) and at read (`LoadGraph`, directory scan) for any attachment count or order — the create-vs-load matrix is all MATCH (attachment facet; pinned regression test).
- [ ] Dual-accept migration: an entry whose stored hash matches either the legacy rendered-prompt basis or the new basis is not flagged stale; a settled graph reports zero stale after upgrade with no re-summarize.
- [ ] `sdd new`, `sdd summarize`, and `sdd lint` write and check via the new basis plus dual-accept; new and regenerated summaries store the new-basis hash.
- [ ] The summary-generation prompt is unchanged — neighbor summaries and attachment context still included.
- [ ] `go vet`, `go test -race`, and `golangci-lint` are clean; both facet reproductions land as pinned regression tests.
