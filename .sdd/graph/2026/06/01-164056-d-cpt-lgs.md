Resolve the conflict-free / tooling-separation question by managing the coupling between sdd tooling and the decision graph through version discipline, not physical separation. The graph's conflict-free property already follows from append-only immutability (d-cpt-e1i) and needs no new contract; this directive declines the proposed binding "keep tooling physically separate" contract in favor of version discipline.

The mutable tooling — CLI binary, installed skills — stays coherent through three mechanisms rather than a separate repo or branch: the `minimum_version` write gate already shipped in `sdd init` (d-tac-r5g) enforces version-to-participate; the binary stays backwards-compatible to at least *read* older graphs; and a standing practice that participants do not hand-edit installed tooling, since `sdd init` and git hooks own those files. Physical separation is rejected because the coupling is real — a newer graph format needs a newer CLI, which needs current skills — so there is no clean split, and separation only adds ceremony without removing the version dependency.

The skill-overwrite incident that prompted the question was reframed with Jonathan as a developer-experience issue, not a framework gap. In the sdd repo itself the local binary is an uncommitted dev build with no tagged version, so it stamps no `minimum_version` and the gate cannot catch a stale binary clobbering newer committed skills; tagged external repos are already protected. The decided fix keeps the dev binary fresh automatically: committed git hooks (post-merge, post-rewrite, post-checkout) rebuild `bin/sdd` via `devbox run build` on every pull, rebase, and branch switch, with `core.hooksPath` wired by the devbox `init_hook` so a fresh `direnv allow` self-configures. A devbox `init_hook` build (wrong granularity — fires on shell init, misses in-shell pulls) and a lazy build-on-invoke wrapper (per-call latency tax) were considered and rejected. CLAUDE.md gets a lean update so the build command and auto-rebuild behavior stay consistent for agents. Implementation is tracked as execution under this directive (WIP + closing done signal); see the attached design for the mechanism and alternatives.
