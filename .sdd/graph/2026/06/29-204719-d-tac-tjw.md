Run a throw-away spike of one candidate architecture for keeping an agent reliably in an explicit working mode — to learn whether it holds, not to commit to it. Low confidence, exploratory; one idea among possible others. It applies the guest-surface enforcement principle (s-cpt-1dz): three layers, each at the surface it can control — (1) goal-driving over a stateful server that holds the mode and hands the agent its next goal plus a report-back format (needs no ownership of the agent's tools); (2) a hard gate on SDD's own write tool, sdd new / pre-flight, where the recorded entry must meet the active mode's requirements; (3) a Claude-Code Stop-hook backstop that shells to the sdd CLI on turn-end and blocks plus re-drives if a goal is still open (verified feasible — a Stop hook can block and re-feed context, and reaches state via the CLI since native MCP-from-hook is unreliable). The spike should probe the honest limits the principle names: the goal-driving and hook layers raise the floor against silent skipping but do not guarantee good execution, and enforcement only ever checks the artifact/state, never the agent's process. A from-scratch design run independently converged on server-held state plus tool-surface enforcement, corroborating the direction. Motivated by the concrete mode-checkpoint miss (s-prc-70o); a flavor of the staged-MCP stateful-workflow experiment (d-cpt-313); enforces the working-modes architecture (d-prc-1ob).
