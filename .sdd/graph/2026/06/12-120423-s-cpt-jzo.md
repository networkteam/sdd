Evaluated alternatives to the networkteam/gollm fork for SDD's LLM access layer and found no candidate clearly beats keeping the fork once dependency hygiene is weighed in. The trigger was the gpt-5 `max_tokens` incompatibility (s-tac-t96), which widened into a fork-vs-replace question. The survey covered mozilla-ai/any-llm-go, joakimcarlsson/ai, cloudwego/eino, zendev-sh/goai, and tmc/langchaingo against: Anthropic+OpenAI+Ollama support, Anthropic prompt caching with cache-read/creation token readback, system/user split, per-call usage, retry+backoff, correct gpt-5 `max_completion_tokens`, and — decisively — no heavyweight AWS/Google transitive trees (the d-cpt-n3y hygiene principle, which our current tree confirms still holds: no aws-sdk, no google.golang.org/api). Two findings dominate: any-llm-go is disqualified outright, having no Anthropic prompt caching at all; and the best feature drop-in (joakimcarlsson/ai) and the most mature option (cloudwego/eino) both build on the official anthropics/anthropic-sdk-go, which bundles Bedrock and drags the full aws-sdk-go-v2 stack into the graph — so adopting either regresses d-cpt-n3y. The only feature-complete option that keeps the tree clean is zendev-sh/goai (stdlib-only, hand-rolled providers, explicit caching + retry + system/user split), but it is pre-1.0, ~130 stars, near-solo, with the gpt-5 token-field switch unverified. MLX is a non-differentiator: no Go library supports it natively; all reach it through an OpenAI-compatible base URL, the same path the existing embedder already uses. The chosen direction: patch the fork's OpenAI request builder to emit `max_completion_tokens` now (the small move that unblocks gpt-5), and keep goai on a watch-list as the clean off-ramp from the fork once it matures — revisiting joakimcarlsson/ai only if the AWS-SDK cost is later judged acceptable, which is a d-cpt-n3y call. See [evaluation](./12-120423-s-cpt-jzo/gollm-alternatives-eval.md) for the full comparison.
