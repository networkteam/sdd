Embedding calls are uninstrumented — the stats sink shipped for the chat path (s-tac-bmw, `.sdd/stats/llm.jsonl`) records nothing for embeddings, so there are no per-batch timings or token-in counts to compare providers on. The `Embedder` interface (`embedder.go`) returns only `([][]float32, error)`: no duration, no usage, and neither `openaiEmbedder` nor `ollamaEmbedder` touches the stats sink. Both providers already return the data SDD discards — omlx/OpenAI sends `usage.prompt_tokens` (parsed away in `openaiEmbedResponse`), Ollama's `/api/embed` returns `prompt_eval_count` plus `total_duration`/`load_duration` (parsed away in `ollamaEmbedResponse`) — and per-batch wall-time is measurable client-side around the HTTP call regardless of provider. The gap surfaced trying to compare ollama `qwen3-embedding:8b` against omlx `Qwen3-Embedding-8B-4bit-DWQ`: omlx worked but didn't feel faster, and with no recorded numbers the comparison can't be settled on fact. This is the embedding-axis counterpart of the chat-path observability gap (s-tac-sae) that the sink work closed; closing it means routing an embedding-shaped `CallStat` (op, provider, model, tokens-in, batch size, duration) through the same sink.
