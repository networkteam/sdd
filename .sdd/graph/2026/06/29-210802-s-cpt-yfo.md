The goal-driving enforcement loop runs as many small iterations — user -> agent -> sdd MCP (returns instructions plus the next goal, composed from the mode's playbook move and applicable rules) -> agent works with its own tools -> agent reports back -> the MCP evaluates the work and either transitions or sets the next goal. Its latency budget follows one rule: keep the per-iteration hot path deterministic, and spend LLM judgment only at infrequent high-stakes gates. The real costs are not the MCP round-trips (cheap) but in-loop LLM evaluations and iteration granularity — each iteration is an agent turn. So most report-backs pass a cheap mechanical check (expected shape, required fields, matches-selected binding rules), while the multi-second LLM evaluation fires only at capture/transition, the same low-frequency point pre-flight already occupies. Goal granularity — meaningful chunks, not micro-steps — is the main latency dial; parallelized LLM calls, prompt caching, and the deterministic always-loaded rule when-index are the supporting mitigations. This operationalizes the guest-surface enforcement principle (s-cpt-1dz) into a concrete cycle, and is the loop the enforcement spike (d-tac-tjw) must measure for friction.
