`sdd wip done`'s branch-merged check is ancestry-based and gives false negatives when the base branch is rewritten mid-wrap-up, refusing to delete a branch whose work is fully merged. Observed in a real worktree conclude: after the feature branch was fast-forwarded into main, SDD's own background sync ran `git pull --rebase`, which replayed main's local commits under new hashes and orphaned the branch tip; `git merge-base --is-ancestor` then reported "not merged", so `wip done` preserved a branch whose content was verifiably on main, and recovery required manual git forensics and a force-delete. Two root causes compound: the merged check relies on literal commit ancestry rather than content equivalence, and the multi-step conclude flow (sync, merge, capture, teardown) is not atomic against the background sync (d-tac-hsu), which can rewrite history on its cooldown between any two steps. The bug is independent of worktrees — it affects `wip done`'s branch deletion for any branch — and it is strong evidence that tool-level guards beat agent-followed text guidance, since recovery here depended on an unusually meticulous agent.
