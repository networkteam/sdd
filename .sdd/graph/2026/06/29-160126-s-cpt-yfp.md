Evaluation is work, recorded as a done signal that references the evaluation move it followed — the same loop as implementation, where a done records what was done and surfaces what comes next. This answers the evaluation-capture gap (s-prc-10m): the *record* of an evaluation is a done, and the findings it raises (gaps, insights, decisions) are surfaced-by it, rather than the ad-hoc fact-signal route. The done's typed reference to its move (e.g. evaluated-via) makes an under-evaluation coverage map computable over **graph entries** — recorded work × axis/move, aggregated by topic — strictly graph-resident and contingent on faithful capture: an evaluation not recorded as a done-with-reference reads as a false gap, which is why that reference needs a structural pre-flight check, not agent memory. Extending coverage to the code layer (which code is under-inspected) needs a separate code↔entry mechanism SDD lacks today; the targeted-review ambition is gated on that. Evaluation moves are graph-resident, project-customizable procedures — the moves-half of s-cpt-k8i — distinct from rules (d-tac-eho), which are checkpoints a rule could use to enforce the expected moves were run. The model reasons from done-is-not-terminal (s-cpt-9qn): mechanical checks are a precondition of the done, while evaluation is a further loop with its own done. Open: whether inner/outer dissolve into freely-customizable moves or persist as the two axes (internally-sound / works-in-use) that project-specific moves realize.
