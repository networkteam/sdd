Topic labels can't evolve after assignment — there is no way to rename a label, merge two labels, deprecate one, or correct which entries carry it. Inline `topics:` share the entry's immutability, so a label written inline can never be changed; annotation-assigned topics can only change by superseding the annotation, and the framework-concepts note records the limitation directly ("no alias mechanism in v1"). The workaround it offers — a new annotation re-assigning members under the new label — leaves the old label attached: inline cases are untouched and the old annotation keeps declaring it unless separately retired, so effective topic sets accumulate stale labels over time. Surfaced concretely while reshaping the backfill taxonomy: renaming `ux/cli` → `cli/ux` and folding `catch-up-scaling` → `skill/catch-up` cannot be applied to the entries already carrying those labels inline. What we want is for the taxonomy to stay coherent as it matures — an entry's effective topic set should reflect the current set of labels, and reshaping the taxonomy should take effect across existing entries rather than only newly captured ones, without the graph collecting dead or duplicate labels. Distinct from the grooming-surface gap (s-cpt-ghy), which covers backfilling untagged entries rather than evolving labels already in use.
