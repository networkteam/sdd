SDD has no process model for coexisting with an external system of record — an issue tracker, email, or chat thread a team already treats as authoritative — when SDD is used in a real project. The inbound direction is conceptually covered by the intake model (20260603-172628-d-cpt-fbi), which treats external channels as transport and ingests items as intake signals; but the outbound direction is unmodeled: when the graph produces an artifact (a ticket, an email) that feeds the external system, there is no named pattern for emitting it, recording it durably, or mirroring its later status back into the graph. Two concrete sub-problems recur. First, an outbound artifact lives outside Git, so a done signal that merely references it (a ticket number) fails the durability check — the working answer is to attach a snapshot of the sent artifact, but that move is emergent and unnamed. Second, creating an outbound artifact is usually a partial step that addresses a directive without closing it; the directive closes only when the external work lands, so the round-trip lifecycle (graph → external work → status back) has no model. Underneath both sits a tension with the no-parallel-artifacts aspiration (20260422-123237-d-stg-3k0): it treats the graph as the sole record and external trackers as unnecessary, yet in a customer project the tracker genuinely is the team's system of record and SDD sits beside it, not instead of it. Resolving this likely means qualifying the aspiration's scope (reasoning record vs. execution/coordination system) and naming the outbound emit-and-mirror pattern as the counterpart to intake — easing the same incremental-adoption friction the adoption gap raises (20260407-215428-s-stg-qg0).
