Cross-agent research establishes that Codex — and the wider ecosystem — has converged on the open Agent Skills standard (agentskills.io) that SDD's skills already largely follow: SKILL.md with `name` (matching its directory) and `description`, on-demand `references/` loading, and progressive disclosure are all standard, and even `allowed-tools` is specified. This makes a thin port to Codex viable without the build-time template rendering the portability gap (z7l) assumed necessary: skills install into Codex's `.agents/skills/` (which follows symlinks), project instructions bridge from a shared `AGENTS.md` into `CLAUDE.md`, Claude-only frontmatter is silently ignored, the `sdd-version`/content-hash stamps fit under `metadata:`, and `compatibility:` can mark a skill's intended runtime. So format was never the obstacle. The real risk is behavioral — whether a foreign agent follows the instruction-carried loop (run catch-up first, dialogue before capture, and the sub-skill pattern recast as "when situation X, invoke skill Y") — which the experiment finding (h5c) says foreign agents drop. The thin-port evaluation on Codex (qy8) measures exactly this, including whether instructed sub-skill invocation works without Claude Code's native Skill tool. Per-agent deviations (Claude's dynamic context injection vs instructing Codex to run the command) are an implementation concern handled by per-agent rendering — the single-source-into-every-surface approach the rendering-contract candidate (oql) already named — not a portability blocker. This is orthogonal to the MCP-gate path: an independent reading on instruction-carried discipline in service of agent-agnosticism, not a step toward structural enforcement. It also re-grounds the multi-agent install-model gap (vye) toward a committed list of supported agents that `sdd init` renders per agent.
