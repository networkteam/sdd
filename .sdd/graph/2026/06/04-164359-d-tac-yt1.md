Drop the open-signal completeness scan from the decision_refs pre-flight check. Today the check injects the full set of active open signals (gaps + questions) into the validator prompt so it can flag a decision that answers an open signal without referencing it. Remove that: delete the OpenSignals context population (preflight.go), the `{{ if .OpenSignals }}` block in decision_refs.tmpl, and retune the ref-completeness check to judge grounding and completeness against the referenced entries only, rather than scanning the whole open set.

Rationale: the scan has shown little observed value — it rarely if ever catches a genuine missed ref. The job it was built for now lives at the skill layer: the Widen → Inspect grounding moves make the agent search and read the related space before drafting (validated by fresh-session evals, s-prc-lud), and vector search makes that widening cheap — work that has to happen at capture anyway. The injection is also brute-force and scales badly: as the graph grows the open-signal set balloons, inflating prompt size and latency on every decision capture, and it risks biasing the validator by diluting attention from the proposed entry toward unrelated open signals. As a side benefit it removes the most volatile content from the intended-cacheable decision_refs system prompt (s-tac-osb).

The open-signal definition is unchanged — a signal is still "addressed" when a decision refs it, and derived status still computes from that. We drop only the capture-time pre-flight enforcement of ref-completeness, not the graph semantics.

Alternatives rejected: scoping the injected pool to vector-nearest open signals (still adds per-call cost and validator dilution for marginal catch value, and duplicates skill-side widening); moving the list to the user block instead of dropping it (preserves the cache prefix but keeps the scaling and bias costs).
