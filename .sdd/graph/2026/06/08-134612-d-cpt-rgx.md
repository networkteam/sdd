Settle how supersede forks are detected and resolved. A fork — an entry superseded by more than one successor — is a problem only when it leaves a live head-resolution ambiguity: more than one currently-active head (not closed, not superseded). The fork lint therefore warns only on live forks; a settled fork, where every branch has since closed or been superseded further, needs no action and stays quiet. This narrows the broader check first shipped (s-tac-4ly), which flagged any entry with more than one immediate superseder regardless of whether its branches were still open — running that lint over the live graph turned up exactly such a benign case, a fork whose branches had long since closed, which is the empirical prompt for this narrowing.

A live fork is resolved by converging forward, never by editing — the graph is immutable. Capture one new entry whose supersedes names the current head of each competing branch; this collapses the fork into a diamond where every branch leads to the same new head, so resolution is unambiguous and the lint falls silent once the branches are superseded. The fork remains in history, settled downstream. Forks are best prevented at capture: superseding an entry that already has an active successor should target that successor (the live head) instead, keeping chains linear.
