`--attach` entries can be born stale — their summary-skip hash drifts on first read, with no edit. The summary prompt renders an `Attachments:` line, and that list is built differently on the two sides of the create→read boundary: `sdd new` (`BuildEntry`) lists the `--attach` targets in CLI order, while `LoadGraph` discards that and re-derives the list by scanning the attachment directory — every file, in alphabetical `os.ReadDir` order. When order or set diverges (a different order, or directory files that weren't individual `--attach` args), the rendered line differs, so the create-time stored hash never matches the read-time recompute and `sdd lint` flags it. The resolved `./11-180913-s-tac-gcd` body link is not a factor — it resolves identically both ways; only the rendered attachment list diverges. This is a second facet of the same root as the neighbor-prose coupling (s-tac-pfn): the skip-hash is taken over the full rendered prompt, so it tracks inputs that aren't stable across create→read. Reproduced across a create-vs-load matrix (attached). Fix direction: hash durable, canonical inputs (a canonical attachment set, or exclude the rendered list) rather than the rendered prompt string.
