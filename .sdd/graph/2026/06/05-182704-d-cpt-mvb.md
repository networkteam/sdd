Establishes the terminal-experience architecture for the sdd CLI, serving two consumer modes that must stay distinct: interactive TTY humans and non-TTY consumers (agents, pipes, scripts). For TTY humans a single output coordinator owns the terminal so transient progress, leveled observability logging, and styled feedback never corrupt each other or the TUI; agents need none of that — the TUI is a human affordance — so non-TTY mode emits clean structured results on stdout and structured slog on stderr, with no progress animation or decoration. The architecture must not conflate the two: TTY detection plus `--format` selects the wiring, extending the audience-separation principle the three-renderer refinement (d-cpt-5f4) set for output rendering to the whole progress/feedback/logging surface. Refines the output policy (d-cpt-rkj) by replacing its naive "operational logging to stderr" with a TUI-aware leveled slog handler on the human path — a raw stderr logger interleaved with charmbracelet components corrupts redraws, the concrete constraint this addresses — while preserving clean stdout and structured stderr logs for agents. Commits to four capabilities, each with its parallel non-TTY behavior: (1) transient progress messages distinct from log lines; (2) leveled slog observability routed through the coordinator rather than a second writer fighting for the terminal; (3) reusable styled error/success/warning feedback components; (4) a per-command UX design naming what each command shows transiently versus persists. The mechanism honors the CQRS contract (d-cpt-ah1): handlers and finders carry no terminal-UI code, exposing optional progress/feedback reporter callbacks on command and query structs (generalizing the existing result-callback pattern), wired to a TTY or plain/structured renderer only at the CLI layer. Implementation, the per-command UX matrix, and acceptance criteria are deferred to a follow-up plan; this directive captures the requirements so planning starts grounded.
