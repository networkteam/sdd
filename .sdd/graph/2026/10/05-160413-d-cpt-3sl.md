SDD gets built-in evaluation of its LLM operations, pre-flight, the writing guide and summarize: an `sdd` command runs them over shipped specimens for each provider, model and parameter combination listed in a matrix config, takes keys from the normal config, and judges the responses, so anyone can measure how a configuration, a prompt change or a response-structure change performs before relying on it.

The eval suites under the `eval` build tag were built to tune prompts and cannot settle comparisons. The provider comparison (20260901-093840-s-tac-ahc) assembled its matrix by hand. The paired evaluation of the PR #10 prompt changes (20260907-103331-s-tac-vsr) needed throwaway recording overlays and analysis scripts, and its result was in effect inconclusive. A parse failure and a wrong answer count as the same failed run, semantic expectations are asserted by substring, three runs per case cannot separate two configurations, and every specimen is English, although two of the four invalid-JSON failures came from German graphs. The structured-output directive (20261004-134853-d-cpt-sw8) leaves exactly the question these suites cannot answer: whether a quote inside valid JSON still lets its reader locate the passage.

Only format is checked mechanically: the response is valid and conforms to the schema. Everything else is a typed question to a judge. Each finding is classified: does it hold, does its axis fit, does its quote identify exactly one passage that is in the draft, which also covers quotes taken from outside the draft (20260901-220355-s-tac-owp). Each specimen is asked whether its expected concerns were raised and whether any finding is spurious. No semantic question is answered by string comparison.

The judge is a provider abstraction answering with probabilities, so a classifier such as TypeSafe's [Jev](https://docs.typesafe.ai), a locally run classifier model, or an LLM judge eliciting confidence can serve it; a local classifier serves projects that may not send material to a hosted service. The judge receives, as JSON, the parts of the operation's input the questions need plus the operation's response, not the full prompt, because irrelevant input lowers accuracy. Judges are calibrated against labeled good and bad specimens, and calibration decides which judge serves which question family. Today's summarize judge answers in booleans and was calibrated on bad summaries only.

Specimens and labels are data shipped with the binary, so every specimen is anonymized. They include German drafts and a panel of drafts carrying characters that broke output before: typographic quotes of several languages, ASCII quotes, braces, backslashes. Every captured incident becomes a specimen, the eval-corpus discipline 20260610-000139-s-prc-xr9 proposed for pre-flight.

Every run records the raw responses, the prompt revision, the response-structure mode and the judge identity, so earlier runs can be judged again without new model calls. Two configurations are compared side by side on the same specimens, with the verdict regression, no worse, or inconclusive. An evaluation lands as a done signal with its results attached, and the last accepted result is the baseline.

The research behind this design is attached as [eval-research.md](./05-160413-d-cpt-3sl/eval-research.md). The dialogue changed it in two places: quote quality is a judge question instead of a byte comparison, and evaluation is a built-in command instead of test code.

Left to the plan: runs per specimen and regression margins, who labels specimens, retiring the substring predicates, whether prompt revision enters the public `Identity`, reconciling the summarize suite's judge with the stored-summary sweep judge, which encode conflicting length contracts, and how an LLM judge elicits probabilities.
