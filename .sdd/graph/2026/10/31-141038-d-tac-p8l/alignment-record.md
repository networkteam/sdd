# Structured LLM responses: alignment record (2026-10-31)

Settled in dialogue between Christopher and Claude. The plan's body holds the commitment; this record holds the facts and trade-offs behind it.

## Opper, as documented (read 2026-10-31)

- An EU gateway hosted in Stockholm (AWS `eu-north-1`, plus evroc), serving about 700 models. There is a DPA, and customer data is not used for training. On the Gateway plan prompts and outputs are not stored. EU-only inference and zero retention are model-access rules that must be configured; without them a model call can leave the EU. Source: https://docs.opper.ai/overview/security.md
- OpenAI-compatible base URL `https://api.opper.ai/v3/compat`, with routes `/chat/completions`, `/responses`, `/embeddings` and `/decisions`. Auth is `Authorization: Bearer <key>`. Model names carry a provider prefix (`openai/gpt-5-mini`, `anthropic/claude-sonnet-4-6`). Source: https://docs.opper.ai/build/gateway/drop-in-sdks.md
- The Anthropic Messages route is `/v3/compat/v1/messages` (Anthropic SDK base URL `https://api.opper.ai/v3/compat`, with the key as `x-api-key` or bearer). The docs do not say whether Anthropic's structured output passes through on this route.
- Structured output uses `response_format: {type: "json_schema", …}` on the OpenAI-compatible chat route. "The gateway validates the response against the schema before returning it", and on non-compliance "the call fails with a validation error rather than silently returning malformed JSON." The docs say neither whether generation is constrained nor how strictness varies by model. Under 20261004-135748-d-tac-ndh, valid-or-loud-error counts as enforcement; a live test per model confirms it. Source: https://docs.opper.ai/build/gateway/structured-output.md
- Evaluation models (for the 20261005-160413-d-cpt-3sl follow-up): `typesafe/jev-1.13.0`, `jev-1.14.0`, `openai/gpt-6-luna-decisions` and `sference/clef`. They are served at `POST /v3/compat/v1/systemone` (TypeSafe System One: `state` plus named `noul`/`choice`/`score` questions, answered with probabilities) and at `POST /v3/compat/decisions` (OpenAI Decisions format). The same project key works. Opper makes no calibration claim ("Answers and token counts can vary between calls"). Jev 1.13 allows 64k context in total, 32k for state plus the longest question. Source: https://docs.opper.ai/build/gateway/evaluations.md

## Code facts found while aligning

- The gollm fork's OpenAI provider picks `max_completion_tokens` and drops `temperature` by model-name prefix (`o…`, `gpt-5…`, a contained `4o`/`-o`) in `providers/openai.go` (`needsMaxCompletionTokens`, `supportsTemperature`). With Opper's prefixes, every `openai/*` model matches only because "openai" starts with "o"; `anthropic/*` never matches. This prefix matching was extended for gpt-5 in 20260614-130830-s-tac-4gm.
- The fork's Anthropic provider hardcodes `https://api.anthropic.com/v1/messages` (`providers/anthropic.go`). That contradicts 20260921-181638-d-cpt-cnu ("a provider path may not hardcode a vendor's URL").
- SDD's factory supports `claude-cli`, `anthropic`, `openai` and `ollama`. Only `openai` takes a configured base URL (`cfg.Endpoint`), and Ollama has its own endpoint option.
- `pkg/sddtest` holds the conformance suites (`RunEmbedderTests` and others). The eval suites live under `internal/llmops/*_eval_test.go` and `internal/llm/gollm/ollama_eval_test.go`, and read `SDD_EVAL_CONFIG`, `SDD_EVAL_PROVIDER`, `SDD_EVAL_MODEL` and `SDD_EVAL_PARAMS`.
- `.github/workflows/ci.yaml` runs tests and lint on every pull request and on pushes to `main`.

## Choices and rejected alternatives

- **Provider requirement.** SDD requires structured output support from every provider it integrates and always sends the schema. It does not detect or refuse an endpoint that ignores the schema: if such an endpoint then returns invalid JSON, parsing fails loudly, as 20261004-135748-d-tac-ndh already accepts. A refusal mechanism for non-enforcing paths was dropped, since no way to identify such a path in advance exists and every integrated provider supports structured output.
- **Scope of the judge.** The judge, its calibration, the judgment evals and the `sdd eval` command stay with 20261005-160413-d-cpt-3sl as a follow-up. Building them here was rejected: structured responses fix the format failure on their own, and the judge is a separate, larger build. The plan keeps raw responses so the judge can score them later without new model calls. The cost: until then, quote and finding quality under structured responses go unmeasured. A before/after run of the existing eval suites was considered and dropped as too much work for what it shows; instead the new format evals are run on the unchanged code first, to show they catch the failure.
- **Test structure.** Each test layer owns one concern; an overlap of concerns points to a structural issue (Christopher). A live conformance suite in `pkg/sddtest` was proposed and rejected. That package holds deterministic contract suites for public ports, run in CI against local and third-party adapters. A live echo through a model cannot separate transport from model. And no outside host needs a Runner contract suite yet. Character preservation is instead asserted by deterministic adapter wire tests over faked provider responses. Live coverage per provider comes from the format evals of the real checks.
- **`sdd eval` replaces the eval-tag suites.** One runner over one dataset, not two: running both would duplicate logic and let the two drift apart. The deterministic `go test` layers stay. This plan's format evals are eval-tag tests reading the example set from data files, as a stopgap that 20261005-160413-d-cpt-3sl retires; the CI workflow then calls `sdd eval`. Building a minimal `sdd eval` here was rejected, because it pulls part of the follow-up forward.
- **Where the judge runs** is no constraint for evals: eval material is anonymized or already public in this repository.
- **Fork parameters.** Name-prefix detection is replaced by a default: `max_completion_tokens` always, `temperature` only when configured. Current models are reasoning models. Unverified: whether every OpenAI-compatible server accepts `max_completion_tokens`; the live runs against the named endpoints settle it.
- **PR #21.** Asking the contributor to anonymize and then merging was preferred, but is not possible: the PR comes from the `Format-D/sdd` organization fork with maintainer edits off. Its cases move into the implementation branch anonymized, and #21 is closed with thanks.
- **CI triggers.** Manual dispatch and a label on pull requests from this repository. Never on every push. `pull_request_target` is rejected, because it would run fork code with the key. Fork PRs never receive the secret.
- **CI coverage.** One Opper key covers the OpenAI adapter (OpenAI and Anthropic models behind it) and, once its base URL is configurable, the native Anthropic adapter through Opper's Anthropic route. The Claude CLI and Ollama stay local runs.
- **Out of scope.** Anthropic prompt caching through Opper's OpenAI-compatible route is a follow-up, since no Anthropic use through Opper is planned. Summarize stays a plain-text purpose (20261004-134853-d-cpt-sw8).
