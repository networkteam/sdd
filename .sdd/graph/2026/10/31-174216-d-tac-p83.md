`sdd eval` (20261005-160413-d-cpt-3sl) follows the structured-output plan (20261031-141038-d-tac-p8l) and becomes the one runner for live evaluation of SDD's LLM operations: it replaces the eval-tag suites in `internal/llmops`, reads the example set from the data files that plan creates, and the GitHub Actions eval workflow switches to calling it. The deterministic `go test` layers stay. Each test layer owns one concern; two runners over one dataset would duplicate logic and drift apart.

`sdd eval` reports every metric against a baseline kept as a file in Git, so any new run, local or in the workflow, compares against it, together with the delta; accepting a result means committing it as the new baseline. Every run writes its result in baseline format, and the workflow uploads it as an artifact, so an accepted run's result is downloaded from the run and committed. The run fails when an invariant such as schema validity breaks or a guarded metric regresses beyond its threshold; an inconclusive comparison is reported without failing the run. Threshold values are set when the command is planned.

Its first judge candidate is TypeSafe's Jev, served by Opper's System One endpoint: typed yes/no, choice and score questions over a JSON state, answered with probabilities, the shape the research attached to 20261005-160413-d-cpt-3sl designed the judge interface around. It is reached with the same Opper key the plan's GitHub Actions workflow already holds; Opper also serves OpenAI's decisions model. Opper claims no calibration, so calibration stays SDD's. Where the judge runs is no constraint for SDD's own examples, since they are anonymized or already public in this repository.

The first judged run scores the raw responses the plan's stopgap evals recorded, so quote and finding quality under structured output, which the plan leaves unmeasured, is measured without new model calls. Opper's evaluation API, as documented, is in the plan's alignment record.
