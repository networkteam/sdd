LLM operations that expect structure run only on provider paths that enforce a response schema natively: an adapter or endpoint that cannot enforce one is refused for those operations, and a request carrying a schema fails loudly there instead of falling back to free-text JSON. This answers the question on non-enforcing adapters that the structured-output directive (20261004-134853-d-cpt-sw8) left open; that directive keeps applying.

The alternative, keeping non-enforcing paths on free-text JSON with today's prompt rules and parser, was rejected: it keeps alive the failure class that directive exists to remove, and a silent fallback hides which guarantee a run had. The restriction costs little today. By their API documentation the claude CLI, OpenAI, Anthropic and Ollama all support native enforcement; only the claude CLI's `--json-schema` flag and the OpenAI provider's strict `response_format` in the `networkteam/gollm` fork exist in our dependencies, and neither is exercised through SDD yet. It bites on OpenAI-compatible endpoints reached through a configured base URL (20260921-181638-d-cpt-cnu), some of which silently ignore `response_format`. Such endpoints stay reachable for text purposes such as summarize, and qualify for structured purposes only if they enforce. One that silently ignores the schema cannot be refused in advance; its unconstrained output then fails parsing, loudly.

With every remaining path enforcing the schema, the prompts' JSON construction rules lose their job: the shared escaping partial and the output-format instructions go, while the prompts keep describing what each field means.

This holds for now: when a provider a user needs cannot enforce a schema, the restriction is revisited.
