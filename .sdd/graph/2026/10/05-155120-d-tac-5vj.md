The transitive declared-dependency closure is computed by one walk in `internal/model` that serve's access gate and the CLI both use, while each composition supplies the step from a node to the dependencies it declares, resolved its own way.

The walk is generic over its key: `DependencyClosure(ctx, root, resolver)` yields every key reached from root once, breadth-first, never root itself, and breaking out of the loop stops it; the resolver answers `Dependencies(ctx, key)`. The context travels in the call chain and no resolver stores it. The CLI resolver is keyed by `RepoID` (20261005-154635-d-tac-1a7): it answers the local repo from its per-repo config and a connected dependency from its cached committed config, read through the reader the local composition already uses for dependency caches (20260903-221901-s-tac-u5j); a repo it cannot read stays in the closure with nothing reached behind it, so the export can mark it unavailable. The serve resolver is keyed by `ProjectID` and built per walk: it reads each project's declarations as today, resolves each through `AccessResolver.ResolveDependency`, and leaves out what does not resolve. `inDependencyClosure` becomes a loop over the walk that stops at the target, implementing the closure rule of 20260903-152247-d-cpt-yjc unchanged, and the existing gate tests pass unchanged. `MultiGraph` stays the cross-graph read model over graphs only, assembled inside the finder's graph source (20260707-175137-d-tac-i6f): local graph, direct dependencies as the bare-ID resolution scope, never widened to the closure, and member graphs loaded lazily. The export computes the closure with the CLI resolver, so its query no longer carries a dependency list; cited-entry selection takes the closure as a typed scope; and the CLI refreshes caches between closure computations until nothing changes, then assembles the graphs once.

Why: Christopher's review of the experimental graph export (https://github.com/networkteam/sdd/pull/22) objected to a closure function taking root, direct dependencies and a reader callback as arguments, and the export had copied serve's walk because `inDependencyClosure` is private to the application. The two walks share their traversal but not their resolution: the CLI resolves a declared repo ID to a connected-repo cache, the same answer whoever declares it, while serve resolves it per principal and per declaring project to an access-checked runtime, and the keys coincide only in the local composition. A visitor, proposed by Christopher, separates the two; in Go its form is an iterator over a resolver interface.

Alternatives weighed: `MultiGraph` owning the closure through a lazily loaded declaration stage per member was rejected, because serve builds a `MultiGraph` too and its declarations resolve per principal, so its member source would need a declaration method that always refuses, and running serve's walk through the assembly would make the model learn principals, contexts, project identities and snapshot release. A separate repo-metadata assembly was rejected as a second assembly over the same caches that must agree with the first on connected set, loader and invalidation. Keeping two walks was rejected because an access gate and a reader would drift. The shared part is small; it earns the generic interface through consistency between the gate and the reader, not through saved code. The comparison of the two walks, interface sketches, data flow and the alternatives in detail are in the [design record](./05-155120-d-tac-5vj/dependency-closure-design.md).

The work lands in the follow-up pull request to #22 that also types repo IDs, with serve moved in its own commit. The directive is fulfilled when serve's gate and the CLI both walk the closure through the shared walk, the export's copy of the walk is gone, and `MultiGraph` carries no declaration API.
