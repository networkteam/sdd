A generated summary can carry the model's reasoning into the graph: in another project, the summary check served a summary holding two drafts joined by a literal `</think>` tag.

Actual. A user of that project reported it; the capturing agent noticed the tag at the summary check, the capture step that serves the generated summary to the agent to confirm or correct before the capture ends. It is one occurrence, observed second-hand. Not yet known: which provider, model and thinking setting served the call, which sdd version ran, and whether the stored summary kept the tag. All three are requested from the reporter.

Expected. A summary is one summary, a pointer to the body that asserts nothing the body does not state (20260901-112834-d-cpt-75a). A reasoning trace or a second draft is neither.

What the code shows. The summarize operation trims whitespace from the model's answer text and stores it; nothing checks the text further. Through the gollm adapter with Ollama, sdd keeps only the response's answer field and leaves separating reasoning from answer to Ollama's thinking setting. The capture's two LLM checks, pre-flight and the writing guide, expect JSON and are moving to schema-enforced output (20261004-134853-d-cpt-sw8); summarize, a text purpose, stays outside that guarantee. This repo has run the setup the provider evaluation recommends (20260901-093840-s-tac-ahc), glm-5.3-flash on Ollama Cloud with thinking on, since late August, and its graph holds no summary with the tag.

Candidate causes, unverified: Ollama's separation failing for a thinking model; sdd's call shape, which uses Ollama's generate endpoint with the system prompt pasted into the user text; or a provider other than Ollama.
