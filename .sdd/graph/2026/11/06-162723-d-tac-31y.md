SDD's LLM configuration moves to named provider entries and per-capability selections: an entry declares, for each of generate, embed and classify it serves, the protocol it speaks and its base URL, plus its key and rate limit, and the `generate`, `embed` and `classify` selections each name an entry and a model.

The provider clients (20261106-155245-d-cpt-eit) serve three capabilities from one client family, while today's config has separate `llm` and `embedding` blocks, each with its own provider list and key map, so a key is stored twice and a third capability would need a third block. Capabilities often need different providers, such as embeddings on a local Ollama, generation through a gateway and classification at TypeSafe, and one protocol may be needed under two names, such as OpenAI itself and an EU gateway speaking its protocol.

Entries live under `llm.providers` with names of the user's choosing. The protocol per capability names the wire format: `openai-chat`, `anthropic-messages`, `ollama-chat` or `claude-cli` for generate; `openai-embeddings` or `ollama-embed` for embed; `systemone` or `openai-decisions` for classify. Built-in presets `openai`, `anthropic`, `ollama` and `opper` carry protocols and URLs, so a user adds only a key, and an entry of the same name overrides a preset field by field. Keys stay secret and belong in user-global or machine-local config (20260708-184318-d-cpt-6cq).

A selection carries the entry, model, parameters and timeout. Generate and classify take per-operation selections that replace the default whole, since parameters are specific to a provider. This is the per-operation model choice 20260902-114838-d-tac-cov left as a separate decision; the provider evaluation found the operations differ in what they need (20260901-093840-s-tac-ahc). Embed stays one selection, because documents and queries must land in one vector space.

Existing configurations keep working. The legacy `llm` and `embedding` keys keep their current meaning, including how endpoints are read today, and map to two implicit provider entries, never merged, so a chat key and an embedding key for the same vendor stay apart. A new selection, when set, wins for its capability; the legacy keys it shadows are not reported, as for any known key a run does not consult (20260921-174543-d-cpt-tv9), and the `sdd config` provenance view shows which one is live. Older binaries read the new keys tolerantly and keep using the legacy ones. `sdd config set` writes only new keys.

`sdd config get` shows the expanded configuration: every preset with its protocols and URLs under a `preset` source, the implicit entries with the legacy key each value came from, and the resolved selections, keys masked as today.

The schema stays private to the SDD binary (20260830-234501-d-cpt-q6n); a host composing `pkg/llm` configures its clients its own way. The full example, the mapping of every legacy key, the alternatives weighed and what is left to the plan are in the [design record](./06-162723-d-tac-31y/llm-config-shape.md).
