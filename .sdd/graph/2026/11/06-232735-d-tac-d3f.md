A host composing the shared MCP wrapper may register tools of its own on the same MCP server as SDD's, so every agent reaches them through the one endpoint it already uses. mcpapp registers SDD's tools onto a server the host supplies, and host tools sit beside them without changing or replacing any of SDD's.

The need comes from a hosted composition. A host may keep state of its own that agents should change through tools, for example agent-written views of the graph that a web UI renders. Remote MCP clients, an assistant built into the host's UI and background agents running SDD procedures should all reach those tools through the connector they already use. A second endpoint for host tools would mean a second connector per user, the cost the one-endpoint wrapper (20260902-000146-d-tac-1z6) removed for projects. Today no seam exists. `mcpapp.New` creates the MCP server privately, `Options` carries no tools, and `registerTools` adds exactly SDD's fourteen.

This moves the boundary the public-API plan (20260712-104530-d-tac-1mb) drew, under which integrations supply infrastructure and authorization only and SDD owns all application semantics. A host may now add behavior of its own beside SDD's. It still may not change or replace SDD's tools, procedures, reads or write gates. Host tools stay outside SDD's process. They run no procedure, write nothing to the graph, and SDD's served instructions never name them, because served text names only what every deployment reaches (20260707-134311-d-cpt-476) and a host tool exists in one composition. Each host tool describes itself.

The shape inverts ownership of the server. The host constructs the `mcp.Server`, calls a registration function in mcpapp that adds SDD's tools to it, and adds its own tools through the SDK. The host owns the server's name and version, its instructions, composed around SDD's instructions text, which mcpapp exports, the transport and handler options, and the lifecycle, including refusing calls during shutdown and closing connections. `mcpapp.New` remains as a wrapper that creates a server named `sdd`, registers onto it and keeps `Handler`, `RunStdio` and `Shutdown`, so the local `sdd serve` and compositions without tools of their own keep their code. The alternative weighed was an extension seam on the server mcpapp owns, such as a tool list in `Options`. The inverted shape was chosen because it gives the host control of the whole server rather than one more option.

The host resolves and authorizes the caller of its own tools from the same authenticated request data its middleware sets for SDD's tools; mcpapp exports no identity helper. Sessions belong to the composition (20260903-152247-d-cpt-yjc), so a host tool that needs a dialogue's session reads it from the host's own session store. SDD's server instructions and tool-contract snapshot stay SDD's own. The MCP SDK replaces a tool registered under an existing name without error, so a host tool named like one of SDD's silently replaces it. This is accepted, and avoiding it is the host's responsibility.
