Integrating an outside source into SDD splits into parts that live in different places: ingestion appends the source's occurrences as events to the project event store, a host's triggers start a background agent on a project procedure, the procedure decides what the graph holds, and configuration names the source and its credentials.

This is the current sketch from a meeting between Christopher and Benno Weinzierl on 2026-11-06 and a follow-up dialogue, worked through for an issue tracker (issues, merge requests, comments) as the first case. It gives 20260906-113911-s-cpt-ikx the concrete scenario it asked for, on top of the event store of 20261107-115150-d-cpt-0mu, and follows the transport posture of 20260818-142224-d-stg-com: the graph takes in what matters while the issue tracker's mechanics stay outside. The same parts should hold for the other sources the graph names, email and chat (20260603-172628-d-cpt-fbi), CI runs and deployments (ikx), and living documents (20260617-170228-s-cpt-jnr). Thinking those through in parallel tests whether the mechanism is generic.

**The parts and where they live.**

- Ingestion receives pushes such as webhooks, or polls, and appends events of the source's own types.
- Triggers decide which events start work, with debounce and thresholds: a burst of edits on an item waits for quiet, for example five minutes, and runs at the latest after fifteen; a comment is more likely to trigger than a label change or a commit. A trigger constructs the procedure's input, or the agent's prompt, from the events that fired it, and starts a background agent. Triggers belong to a host, not to core.
- The procedure is a project procedure in the graph, which may depend on its environment (20260707-142556-d-cpt-70z). It says what the agent reads, such as the item's other events and the source through its tools, how the item maps into the graph, and what the agent may write. The team adjusts it in dialogue.
- Reading the source goes through the agent's own tools, a CLI or an MCP server, or through engine abilities a deployment registers (20260814-171302-s-cpt-5zq).
- Configuration names the source per project. Credentials stay in configuration or with the host, never in a graph.

**One sketch of the mapping, for issue tracker items.** The incoming item lands as an intake (fbi). The procedure, run by a background agent that a host's trigger starts mechanically, proposes draft captures connected to it and to the entries it touches, depending on its instructions and the agent's confidence: a comment may become a point of view (20261106-225324-s-cpt-d5x), or a gap when the agent is confident, but never a directive. A draft is not a finished entry, so it neither poses demand nor reads as ground truth, which keeps the intake model's caution; whether drafts become a state of their own is 20261106-225558-s-cpt-z3j. Writing without a user needs a procedure written for non-interactive sessions, which 20260827-232430-d-cpt-voa leaves possible. The meeting stressed the mechanism over this mapping, which each project tries out for itself.

**Locally pull, with a running process push.** A local setup has no reachable endpoint and no process running triggers, so it integrates by pull: an agent with the source's tools runs the procedure when someone asks, as Christopher works with an issue tracker today. Push, with webhooks, triggers and background agents, needs a host that runs continuously.

**Many projects, one procedure.** A team with dozens of projects on one issue tracker should not maintain the procedure dozens of times. A shared graph holds it, every project declares that graph as a dependency, and per-project values such as the issue tracker project, labels or a confidence threshold come from project configuration. 20260819-171110-s-tac-4km names this scenario and the dependency ordering of 20261026-182211-d-cpt-lwu anticipates it. Two limits stand today: the engine's serving primitives do not follow supersession across repos (4km), and a project cannot override a dependency's procedure, because supersedes stay within one graph (20260529-131915-d-cpt-v8t).

**Scale.** A graph holding every issue tracker item and its draft captures grows large. Keeping the material in the graph is worth it, because a session working on a subject sees what just arrived on it. The cost is an optimization problem: caching the graph across operations, where today each operation reads it afresh.
