SDD gets a project event store as a base capability: core defines its interface, the event envelope and the agent tools to append and query events, writers define their own event types, each composition supplies the implementation, and the local default is a simple store in JSON files.

**Why SDD needs it.** Some occurrences matter to the project without belonging in the graph, and nothing holds them today. WIP markers carry in-flight work between participants as files in Git (20260923-121943-d-tac-lqh), a channel that proved wrong for them (20260923-182850-s-cpt-ct5); they are the store's first use and move into it. Changes an outside system pushes, such as an issue tracker's webhooks, need a place to land and wait until a procedure reads them, often debounced well after arrival. Querying the outside tool on demand, which agents already do, covers reading but not arrival. Procedures need tools to write and read both kinds. An entry per occurrence would flood the graph, while the movement should stay visible to humans and agents alike (20260422-122317-d-stg-qlt).

**A store, not a stream.** Core needs append and query by item, entry and time. Delivery to subscribers matters only to whatever reacts on arrival, and reacting needs a running process, so triggers and background agents are host concerns outside this decision. Projections are not planned: the in-flight view ct5 expected to replace WIP markers is a query over the store. This narrows the project event stream of 20260906-113911-s-cpt-ikx and ct5 and settles the persistence both left open, decided by Christopher and Benno Weinzierl in a meeting on 2026-11-06 and a follow-up dialogue.

**One envelope, types owned by their writers.** Every event carries a type name, a time, who or what wrote it, a subject and a payload. The subject is an external identity URI, entry IDs, or both. It is the same external identity entries will carry for an outside item (20260617-170228-s-cpt-jnr), decided separately, so a procedure can join events and entries for one item. The payload is opaque to core. Whoever writes a type owns its payload shape and its retention: core writes its own types under the reserved `sdd.` namespace, such as WIP markers, and a connector or a project procedure writes others, such as a tracker's comment events. Core cannot know every source's events, so ownership follows the writer, not a place of declaration.

**In core, implemented per composition.** Core holds the interface, the envelope, the tools and its own types because base procedures and served instructions will name them, and they name only what every composition provides (20260707-134311-d-cpt-476). A composition may connect to a hosted store through an API configured with its address and a key. The local default is a simple JSON store rather than a no-op, because WIP markers need somewhere to live.

**Events are not the record.** The graph stays the project's only durable record (20260727-224047-d-cpt-u8o), so every event may expire under its type's retention: a tracker's change notifications lose interest after a longer period, and a WIP marker's events can go once its run ends. Events may reference entries, but entries do not reference events, since an event may expire; an entry points at an outside item through its external identity instead. ct5's light delivery still holds: a lost event costs one observation, never consistency.

Open: the store's query surface.
