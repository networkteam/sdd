SDD's OpenAI-compatible embedding adapter cannot reach a gateway that mounts its compatible API under a prefix other than `/v1`: it appends a fixed `/v1/embeddings` to `embedding.endpoint`, so no configuration points it at Opper's documented embeddings endpoint `https://api.opper.ai/v3/compat/embeddings`.

**Actual.** `internal/llm/embed/openai.go` builds the request URL as `endpoint + "/v1/embeddings"`. Opper documents `https://api.opper.ai/v3/compat` as its OpenAI-compatible base URL and lists `POST /v3/compat/embeddings` (docs.opper.ai, drop-in SDKs page, read 2026-11-02). With that base configured, SDD requests `/v3/compat/v1/embeddings`, which answers 404. With `https://api.opper.ai` configured, SDD requests `/v1/embeddings`, a route Opper does not document that currently returns embeddings in the shape SDD expects; a search over `evroc/qwen3-embedding-8b` worked end to end this way. It surfaced while preparing a global config that routes embeddings through Opper. The chat side takes a different form: `llm.endpoint` holds the full chat-completions URL (`…/v3/compat/chat/completions`), so the two `endpoint` keys mean different things.

**Expected.** A configurable base URL reaches any gateway speaking the OpenAI-compatible protocol, and the embedding side is named as already working that way (20260921-181638-d-cpt-cnu). Reaching a gateway at its documented compatible path is part of that reach; depending on an undocumented route is not.

**Deviation.** The fixed `/v1` segment limits the embedding endpoint to gateways that serve the compatible API at `/v1` below the configured URL, so Opper embeddings work only through a route Opper can drop without notice.
