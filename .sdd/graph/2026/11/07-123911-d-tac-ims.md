The README serves someone who lands on the GitHub repository and sends them on to the documentation site, which carries everything else. The site is where people get to know and understand SDD, where its vision and working modes are communicated, where agents research it, and where users look things up; with no public landing page for SDD yet, it also stands in for one. Most README readers arrive through a link, a search result or a mention and do not use SDD yet. A smaller group comes for the source, to embed SDD in a Go application, or to contribute, and agents reading the repository start there too. The README gives them what only it can: what SDD is and whether it fits them, that the repository is SDD's open source core, the fastest way to try it (install, then a pointer to getting started on the site), and for developers how to build from source, embed or contribute. Once public information about the hosted SDD product exists, the README also highlights it as a quick way to get started.

Someone already working with SDD is in a session with their agent and looks things up on the site, so the README never needs to be complete. Getting started, configuration, the entry kinds, the vision and every later topic live on the site.

Christopher settled this while reviewing the first getting-started draft for 20260821-181419-d-tac-hq1, which sent readers to README sections for LLM and embedding configuration. Two surfaces describing the same setup drift apart: the research behind that draft found README statements the code contradicts, among them an `sdd init` flag that does not exist and a count of two LLM calls per capture where there are three. Keeping each topic in one place, the site, removes that drift. A README section that repeats reference material breaks this directive.
